## 一、这份指南解决什么问题

设计文档目前有两种坏法，而且同时存在：

| 坏法 | 表现 | 真实案例 |
|---|---|---|
| **流水账** | 修订记录、排查过程、QA findings 流水、工具输出粘贴 | dsh-vscode-agent 一份根因分析文档 676 KB，文首连排 15 条修订记录；teamcodingknowledge `文档 560` 有 **22.8% 的篇幅**是修订痕迹 |
| **内部电报** | 结论没有证据、没有"为什么"、没有"为什么不选别的" | 通篇只有结论，读者"看了又感觉什么都没看到" |

两种坏法的共同点：**文档里的话与读者的需要不匹配**。所以本指南不设篇幅上限，只给一条判据和一把尺子。

### 一句话原则

> **删噪声，不删设计信息。**
> 凡是"读者要据此做决策、写代码、验收"的内容，一条都不能省；凡是"只记录我们怎么走到这里"的内容，一条都不该留。
> **压缩的对象永远是冗余与过程，从来不是结论、判据与理由。**

理论依据是格莱斯（Grice）合作原则的四条准则（数量 / 质量 / 关联 / 方式），它原本的定义就是"提供**恰好所需**的信息量，不多也不少"——两个极端由同一条准则管。辅证是 RFC 编辑的成熟实践：目标是"清晰、一致、可读"，同时立有最高原则「**不得改变文本的原意**」（[RFC 7322 §2](https://datatracker.ietf.org/doc/html/rfc7322)）。

## 二、五条准则

> **判据正本在「写作契约」的「一、写作准则」节**——
> 那份随角色契约**每次派发内联**；本 skill 按需拉取，随附**正／反例对照**。
> **两者若有出入，以契约为准**（单一事实源）。本节的作用是"把判据讲透"，不是"再定义一遍判据"。
>
> 判据常驻契约，示例按需拉取
> ——这是**「契约 vs skill」的分工**。**判据是操作性的**：*单次注入的规则若无法在一次判断中
> 全部用完，即属外在负荷，应继续切分*；**理论名不作依据**（认知负荷理论用于此**未找到对照实验**，
> 属外推，纪律见 `contracts/_shared/contract-conventions.md`「角色切分依据」节）。

### 准则一：数量——信息量正好，既不多也不少

**充足侧**：每个结论必须答得出三问，缺一条即不合格：

| 问 | 答什么 | 反例 |
|---|---|---|
| **是什么** | 一句话说清结论，不含逃逸表述 | "建议进一步评估连接池参数" |
| **凭什么** | 数据、源码位置（`文件:行号`）、命令与输出、官方出处 | "经测试连接池有问题"（无位置、无命令、无数字） |
| **为什么不选别的** | 至少一个被否决的候选方案 + 一句话理由 | 只给一个方案，读者不知道还有没有别的路 |

**必要侧**：段落或附表若满足"删掉它，读者仍能下同一个判断、做同一个决定"，即为冗余，删掉或移出正文。

**可用一把尺子量（复述测试）**：让一个不了解上下文的人只读这一节，然后复述"结论是什么、凭什么、还有哪些没选"。
- 他**复述不出来** → 信息量不足（电报侧）；
- 他能复述出来、而你写的**远多于**他复述的 → 有冗余（流水账侧）。

### 准则二：质量——只写能站住的话

- 禁止无依据的定量断言（"X 次操作会触发 Y"必须先有实测数据）。
- 禁止用"大概/应该/可能/估计"描述根因或结论。
- 每个数字标注**来源、时间、环境**——同一命令在不同环境跑出的数字不是同一个事实。
- 无法证实的内容要么补证、要么显式标注"未证实"，不得混在已验证结论里陈述。

### 准则三：关联——只写与当前设计有关的

正文只承载**当前这一版设计**。以下一律不属于正文：探索路径、试错记录、假设推演过程、与用户的问答回放、工具输出整段粘贴、QA findings 处置流水、多轮修订对照、版本历史。

判据：一个段落只要删掉后"对设计的描述不缺失"，它就不该在正文里。

### 准则四：方式——让人一次读懂

- **自足**：默认读者是新人，不知道上下文、不知道你的探索过程。术语首次出现给一句白话解释，关键指标写明口径。
- **单一事实源**：同一条信息（接口字段、表结构、任务清单）在文档里只出现一次，别处写"见 §X"。
- **结构化优先**：枚举、对照、清单用表格；一条一个意思。
- **术语必核来源**：非通行叫法必须在源码标识符、配置键、上游官方文档或人类材料里出现过；只在模型自己写的文档里出现过的拼接词判为自造词，改用通行说法。

### 准则五：取舍——删噪声，不删设计信息（刹车条）

- 任何一次"简化"，判据只能是"这段是噪声"，不能是"这篇太长了"。
- 当读者看不懂某段时，**正确动作是把链路补全**（补定义、补背景、补取舍、补依据），**不是把它删掉**。
- "逐字保真"只适用于把外部原文归档到 `.dsh/tmp/` 留证，**不适用于 `docs/` 下的设计文档正文**。

### 修订语义：整体重写，不追加

文档永久代表**当前正确的那一版设计**。收到评审意见后：读全文 → 把新结论直接写进对应章节的最终形态 → 同步订正连带章节 → 以"没读过旧版的人"的视角通篇复检 → 台账加一行。

**正文里不允许出现**："修订记录/版本历史"章节、"（原为…现改为…）"、"上一轮 QA 判定"、"v1.x 更正"、"就地注记"。版本只在头部留一行。

### 回环期纪律：每一轮都重新施加

架构师→QA→架构师→QA… 的回环里，**规则不会自动保持**：第 3 轮时首轮的准则已经滑出注意力，而"在上一版基础上打补丁"是最省事的动作。真实案例里，一份文档第 4 轮以"原句逐字保留 + 就地追加注记"的方式修订，最终 **22.8% 的正文是修订痕迹**。

所以每一轮重派都要重新施加四条：

| 纪律 | 具体要求 |
|---|---|
| **整体重写** | 重写受影响的章节，不是在旧文上追加或注记。发现正文还有旧结论残留时，**改写成唯一正确的表述**，不在旁边加"（已更正）" |
| **净增长 ≤ 0** | 本轮修订后的行数与字节数不得超过上一轮。确需新增设计结论的（首轮遗漏、用户扩范围），要说明"这是设计内容、不是本轮过程"；**先删本轮噪声，再补新结论** |
| **全篇自洽复检** | 改完通读一遍，确认没有前后矛盾——"只改点名的几处、不做全篇复查"正是上一轮修订引入新矛盾的来源 |
| **变更进台账** | 版本只在头部一行，明细写 `{{paths.changelog}}` |

QA 每轮会记录三个数：**行数 / 字节数 / 修订痕迹命中数**，并与上一轮对比。三者中出现「**净增长 + 痕迹增加 + 零修复**」同时成立，就停止回环、升级用户裁决——这一条是为"文档随轮次失控"专设的停点。

> 关键：**"不许变长"拦的是过程沉积，不是设计生长。** 首轮漏了一个子系统时，文档当然该变长；要的是说清新增长的是设计结论，而不是这轮的经过。

## 三、文档结构模板

```
# {编号} {标题}
> 状态：待评审 | 版本：vX.Y | 日期：YYYY-MM-DD
> 需求来源：{用户原话摘要或需求编号} | 变更台账：{{paths.changelog}}#{编号}

## 一、需求复述（我理解要解决的问题、验收标准、明确不做）
## 二、关键结论（方案 / 关键取舍 / 影响面）
## 三、范围（做什么、不做什么）
## 四、方案设计（架构图 / 时序图 / 接口定义 / ER 图）
## 五、可行性与数据验证（结论 + 依据，不贴过程）
## 六、可维护性与性能分析（定量指标，含口径）
## 七、附加（数据库/表设计、接口设计）
## 八、决策记录（最终决策 + 被否决方案与理由一句话）
## 九、实施清单（[目标角色] + 涉及文件 + 验收判据）

> 评审人：待定 | 状态：待终审 | 日期
```

三块内容的去处：

| 块 | 放哪 | 谁读 |
|---|---|---|
| 正文（唯一设计事实源） | `docs/{编号}-{标题}.md` | 人 + 下游全部角色 |
| 变更台账（一行一版） | `{{paths.changelog}}` | 审计追溯，日常阅读不需要打开 |
| 过程留痕（探针、原始输出、中间稿、旧版对照） | `.dsh/tmp/architect/` | 回环时按需，闭环即清 |

## 四、样例 A：一份合格的设计文档（完整实例）

下面是一份**合格**的设计文档全文。它的特点：每个结论都带依据与位置、给了被否决的方案、没有一句过程叙述、没有版本历史。**注意它的篇幅并不短——因为该有的信息都在。**

```markdown
# 213 缓存穿透防护设计

> 状态：待评审 | 版本：v1.0 | 日期：2026-09-17
> 需求来源：用户 2026-09-17 提问"商品详情接口在压测下把数据库打满，怎么防？"
> 变更台账：{{paths.changelog}}#213

## 一、需求复述

**要解决的问题**：商品详情接口在缓存未命中时会直接查库；压测时大量不存在的商品 ID 反复击穿缓存，数据库连接被打满。

**验收标准**：在 3000 QPS、缓存命中率 0% 的最坏情况下，数据库 QPS 不超过 200（依据：现有连接池上限 200，见 §五）。

**明确不做**：不改缓存介质（仍用 Redis），不改商品表结构，不引入新的中间件。

**一处需要用户确认的理解**：用户说的"打满"是连接数打满，不是 CPU 打满。依据是压测时的连接池监控（见 §五）。若实际是 CPU 瓶颈，本设计不适用。

## 二、关键结论

1. 采用**空值缓存 + 布隆过滤器前置**双层防护：布隆过滤器挡住绝大多数不存在的 ID，空值缓存兜住漏网的。
2. 关键取舍：**不用互斥锁重建**——它会把并发请求串行化，在 3000 QPS 下首字节延迟从 12 ms 涨到 400 ms 以上（实测数据见 §五），代价高于收益。
3. 影响面：改动集中在 `ProductDetailService` 与缓存层，不涉及对外接口契约。

## 三、范围

**做什么**：布隆过滤器实现与预热、空值缓存（TTL 60 秒）、缓存层的空值判定、监控埋点。

**不做什么**：

| 不做的事 | 理由 |
|---|---|
| 不做缓存一致性改造 | 属另一主题，擅自扩大范围会拖长评审与实施 |
| 不做商品表索引优化 | 本次瓶颈在"不存在的 ID 反复查库"，索引对不存在的 ID 无效 |
| 不改连接池上限 | 提高上限只是把问题推后，且会加剧数据库压力 |

## 四、方案设计

（此处放架构图 / 时序图 / 接口定义 / ER 图。图必须能回答"请求怎么走、在哪一层被挡住"。）

## 五、可行性与数据验证

| 维度 | 结论 | 依据 |
|---|---|---|
| 技术可行性 | 可行 | 布隆过滤器有成熟的 Redis 模块可用；空值缓存是既有缓存层加一个分支 |
| 数据支撑 | 见下表 | 2026-09-17 14:20 在测试环境（8C16G，Redis 6.2，MySQL 8.0）采样 |
| 资源可行性 | 零新增硬件 | 布隆过滤器约 12 MB 内存，复用现有 Redis |
| 未证实项 | 布隆过滤器的误判率需在上线前实测 | 现有数据只支撑理论估算（1% 在 100 万条、0.1% 误判率配置下） |
```

### 这份样例为什么合格

| 体现的准则 | 具体位置 |
|---|---|
| 数量·充足 | §一 复述并指出"一处需要用户确认的理解"；每个结论都有依据；§八 两条明确的"否决 + 理由" |
| 数量·必要 | 全文没有一句"我先看了什么、然后试了什么"；没有修订记录 |
| 质量 | 每个数字带时间与环境；未证实项显式列出 |
| 关联 | 不做的三件事都给了理由，且都不是本设计的主题 |
| 方式 | 表格承载对照信息；术语（布隆过滤器、误判率、TTL）都是通行词 |

## 五、样例 B：一份流水账的清洗对照（真实案例）

### 5.1 原型：teamcodingknowledge `文档 560--design.md（他项目原型）`

这是一份**内容质量很高**的真实设计文档——根因分析扎实、数据充分、决策记录完整，QA 第 4 轮判 **PASS**。它的问题不在"没有设计信息"，而在**设计信息被修订痕迹包围**。

**实测规模**（清洗前的基线，逐段统计）：

| 区段 | 行数 | 占全文 | 性质 |
|---|---|---|---|
| 全文 | **1545** | 100% | — |
| L1–20 frontmatter（含 10 条 `related` 引用，逐条说明是哪一轮的探针批次与审计报告） | 20 | 1.3% | 过程 |
| L22–31 头部元信息（版本状态 + 本版性质 + 探针纪律 + 凭证纪律 + 时间基准 + 动态数值纪律） | 10 | 0.6% | 混合 |

### 5.4 清洗过程中必须警惕的三件事

**第一件：不要顺手把"证据"当冗余删掉。** 这份文档里到处是形如「长度 22，SHA256 前 12 位 `322651c726ca`（inode 109838351）」的内容——它们是**设计判据**（用来判断某处凭证是不是漂移值），不是过程噪声。判断标准回到准则一：**删掉它，读者还能不能验证这个结论？** 不能，就留着。

**第二件：不要把"改对了"写成"又改了一遍"。** 清洗时若发现正文里还有旧结论残留，正确动作是**把它改写为唯一正确的表述**，而不是在旁边加一句"（已更正）"。后者会让文档重新长出修订痕迹。

**第三件（2026-09-17 试点实测得出，最容易翻车）：不要顺手把"数值"当排版删掉。**

560 的第一次重写试点是**规则判据被实测反向收紧**的案例，值得完整记录：

| | 结果 |
|---|---|
| 规模 | 1545 行 → 974 行；206,694 → 110,065 字节（**−46.7%**） |
| 修订痕迹 | **0 命中**（D10 通过）✅ |
| 设计标识符 | D-560-1~21 / Q1~14 / CL-1~10 / PX-01~10 / R-560-1~9 **零真缺失** ✅ |
| 代理配置 26 项 | A6+B9+C11 **逐组一致** ✅ |
| **数值判据** | ❌ 压掉了 PID `18473`、字节数 `48042`/`41776`、epoch `1970`、mtime nanos `42.812773694`、该项目声明的远程入口脚本 行数 `346`、`config.py` 的函数行号 `23-51`/`111-131` 等 |

**全部结构指标都通过了，但这一版仍是错的**——因为它把探针输出的"排版"连同"数值"一起抹平了。

根因是判据选错了：架构师当时用的边界是"**读者能否复跑这条命令**"。这条判据太松——PID、文件大小、端口、时间戳**都能复跑一遍拿到**，可是没有服务器访问权的读者**据此下不了判断**，等于把判据换成了"你自己去查"。

**收紧后的边界（现已写进契约）：判据是"读者能否据此下判断"，一句话——可以压排版，不能压证据。**

| 可以压缩的 | 必须逐字保留的 |
|---|---|
| 命令的书写形式（长命令折行、路径别名简化） | **命令本身**（复跑要用，含参数与路径） |
| 输出中与结论无关的排版、分隔线、重复表头 | **数值型判据**：端口、文件大小与字节数、计数、时间戳（含 nanos 级）、PID、epoch、百分比、耗时、SHA256 前缀、inode |
| 同一结论在多处重复的表述（留一处） | **判定结论的那几行输出**（如 `CONNECT tunnel failed, response 501`、`postgresql.status=ok`） |
| 探针的探索顺序、试错分支 | **每个探针的采样时刻与环境** |
| 章节编号引用（重排后会失效，改按标题引用） | **被引用文档/文件的标识与行号**（`文件:行号`、`文档 552 #8`） |

**这件事的普遍意义**：这份指南用一整节讲"不要写成流水账"，而 560 试点证明**过度压缩是同一枚硬币的另一面**。两个极端由同一条准则管——准则一"数量：不多也不少"。所以清洗存量时，**必须同时准备两个方向的检查**：删噪声的检查（D9/D10）和数值留痕的检查（D13）。只做前者，就会从流水账滑到电报体。

**工具化核对**（不靠人肉记忆，见 `{{paths.tools}}verify-rewrite.mjs`）：清洗或重写后跑一次
```
node {{paths.tools}}verify-rewrite.mjs --original <原稿> --rewrite <改后稿>
```
它会报出体量、标识符留存、数值指纹留存、修订痕迹、结构、超长行六项。**注意区分"真缺失"与"正则伪影"**——例如从 `文档 552` 里会抓出假编号 `D-2`，从 `#1` 里会割出 `#1`。工具已内置这个分类（第 2b 节），只看"真缺失"列。

## 六、QA 侧：审计报告写法与样例

### 6.1 两条原则

1. **证据要，但只引用不搬运。** QA 必须亲自核实（这条完全正确，一个字不改），但留证方式不是把原文贴进报告：**引用 `文件:行号`、引用命令、给结论性数字，大段输出落 `.dsh/tmp/audits/<phase>/_raw/` 并只写路径。**
2. **不得要求超出设计需要的证据。** 判"证据不足"的判据是"读者能否据此下判断"（准则一的三问），**不是"作者是否贴了原始输出"**。要求把命令回显、日志原文、源码全文放进设计文档或审计 json 的，一律不属于"证据不足"。

### 6.2 审计产物规范

| 项 | 上限 / 要求 |
|---|---|
| 证据字段 | ≤300 字符；只写「文件:行号 / 命令 / 结论数字 / 原始产物路径」 |
| 单份审计 json | ≤8 KB（超出说明把原文搬进来了） |
| `overall_reason` | ≤400 字符 |
| 最终消息 `summary` | ≤200 字符（既有要求，不变） |
| QA 额外写的 markdown 报告 | ≤150 行，只写结论与判定依据，不复制被审计文档的内容 |
| 逐轮增量 | 回环第 N 轮只列「本轮新增 findings + 上轮 FAIL 项复核结果 + 未受影响项一行带过」，不重复已 PASS 项的结构与证据 |
| 大段输出 | 落 `.dsh/tmp/audits/<phase>/_raw/`，报告里只写路径 |

> 参照：清洗前 teamcodingknowledge 的 `.dsh/tmp/audits/` 有 83 个文件 / 1212 KB，单份设计审计 json 达 11–38 KB；dsh-vscode-agent 的审计目录里留存着 190 KB 的源码全文拷贝与 129 KB 的测试输出，用途仅是证明"我亲自跑了"。**这些都是可以避免的搬运成本。**

## 七、写之前先自查（10 问）

写完或审完，逐条过一遍：

1. **§一 需求复述对得上用户原话吗？** 有含糊的地方，先抛回确认，别往下写。
2. **每个结论都答得出"是什么 / 凭什么 / 为什么不选别的"吗？** 缺哪条补哪条。
3. **做一次复述测试**：一个不了解上下文的人只读这一节，能复述出结论与依据吗？复述不出来的部分补全；他复述出来的远少于你写的，删多余的。
4. **正文里还有"原为…现改为…"、"v1.x 更正"、"上一轮 QA"吗？** 有就改为唯一正确的表述。
   > 注意"版本号"的两种形态都要查：**"v1.x + 改了什么"**（显式修订叙述）与**"嵌在标题或散文里的（vN 更新）"**（隐蔽形态）。后者在存量文档里很常见，实测 409 有 5 处，其中还有一处是"修订史伪装成内容"的 `v1.0 结论 | v1.1 结论` 对比表——**只保留现行结论那一列**。
5. **有没有"修订记录 / 变更记录 / QA 回环响应表"章节？** 有就移入 `{{paths.changelog}}`。
6. **同一张表 / 同一组字段在文档里出现两次以上了吗？** 留一处，别处写"见 §X"。
   > 去重时注意：工具会把"正确去重"和"真丢失"分开报。原稿出现 ≥2 次、改后留 ≥1 次是**去重**（对的）；原稿只出现 1 次却没了才是**真丢失**。
7. **每个数字都标了来源、时间、环境吗？** 没标就补。
8. **非通行的叫法都能说出出处吗？** 说不出就改成通行说法。
9. **（回环第 2 轮起）这篇比上一轮变长了吗？** 变长就要说清"新增的是设计结论，不是这轮的经过"；说不清就先删噪声再补结论。
10. **（清洗 / 重写场景）压缩后做过"数值留痕核对"吗？** 把原稿里的端口、字节数、计数、时间戳（含 nanos）、PID、epoch、SHA256 前缀、inode、被引用文件的行号逐一在改后稿检索一遍——**缺一个就补回来**。别靠记忆，跑 `node {{paths.tools}}verify-rewrite.mjs --original <原稿> --rewrite <改后稿>`（**只看第 3 节的「设计正文比对」真缺失列**，忽略正则伪影与"去重"列）。

> **第 10 问为什么单列一问**：560 首轮重写时，全部结构指标通过、标识符零缺失，**但这一版仍是错的**——它把探针输出的"排版"连同"数值"一起抹平了。教训是"可以压排版，不能压证据"，而**排版与证据的分界只有逐个数值检索才能守住**。
