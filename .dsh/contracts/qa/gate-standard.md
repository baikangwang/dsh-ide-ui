# contracts/qa — QA 把关与检查标准（敏捷模式，形态 B，按角色注入）

> 来源基线（**模式仓库 agent-mode 的历史溯源，目标项目不需要 `baseline/`**）：baseline/project/agents/QA.md、baseline/global/rules/03-工程规范.mdc(评审/评分)
> 注入时机：编排者检查阶段（设计→QA→评审→开发→QA→部署→QA→测试）
> **本文件只写敏捷模式专属的检查项。两模式完全相同的 QA 规则在 `_shared/qa-common.md`**——
> 对抗式审计纪律、不确定性安全通道（P8）、审计产物规范、工具触发规则、内置约束、
> QA 报告格式、最小留存台账（P3c）/周期时间采集（P2a）/规则复审机制（P9）、行数口径，**全部读那一份**。
> **不在这里重抄一遍**：同一份内容两处存放，实测已经漂移过。
> v5（2026-09-17）：设计审计由 D1–D12 扩为 **D1–D13**，新增「数值证据完整」；D8/D9/D13 三条成组执行（分别治"结论缺依据 / 过程留痕 / 数值被压掉"）。起因：560 首轮重写试点 D1–D12 全过、修订痕迹清零，仍丢了 PID/字节数/epoch 等数值型判据。核对工具 `{{paths.tools}}verify-rewrite.mjs`。

## 职责：质量检查
```
A1 设计审计：架构师 → QA（D1-D13）→ 通过/回环架构师
A1 代码审计：开发专家 → QA（C1-C6）→ 通过/回环开发专家
A1 部署审计：部署专家 → QA（P1-P5）→ 通过/回环部署专家
```
不审计 A2 简链（分析报告）。

## 检查流转
```
A1：架构师→QA设计→用户评审→开发→QA代码→部署→QA部署→测试
   不通过 → 回环修正 → 再审（回环控制按进展检查点，见 `_shared/qa-common.md`）
```
**进展检查点、控制律唯一事实源、终止条件的报告义务、一次审计跑全**——见 `_shared/qa-common.md`「检查流转的通用部分」。**本节不写停止条件**：契约只描述"发现什么"，不描述"何时停"。

## 审计标准

### 设计审计（架构师）— A1
| # | 检查项 | 标准 |
|---|--------|------|
| D1 | 文档结构 | 9 节结构齐全，且 §一 为需求复述、§二 为关键结论 |
| D2 | 范围明确 | 「包含」和「不包含」均列出，不做的项附理由 |
| D3 | 设计可视化 | 至少 1 个 Mermaid 或 ASCII ER 图 |
| D4 | 定量分析 | 数据须标来源、时间、环境；无来源的"实测"数字 = FAIL |
| D5 | 决策记录 | 只保留最终决策与被否决方案 + 理由一句话；出现"某轮评审意见"并入 D10 判负 |
| D6 | 实施清单 | 每项含 [目标角色] + 涉及文件 + 验收判据 |
| D7 | 评审状态 | 标注「待评审」 |
| **D8** | **充足性（治电报）** | 每个结论都回答了"是什么/凭什么/为什么不选别的"三问；无孤立短语、无未定义术语、无"无头无尾"的结论 | 抽 3 个关键结论逐条对照三问；缺任一问 = FAIL，finding 指出是哪个结论缺哪一问 |
| **D9** | **必要性（治流水账）** | 正文无过程留痕、无问答回放、无工具输出粘贴、无重复信息；同一条信息只出现一次 | 通读全文；发现任一类即 FAIL，finding 给行号与原文片段 |
| **D10** | **时效与单一事实源** | 正文无旧版结论残留、无"原为…现改为…"、无"就地注记"、无修订记录章节；全篇口径一致 | 全文检索 `修订\|变更记录\|版本历史\|原为\|上一轮\|更正\|就地注记\|v\d+\.\d+`；命中即 FAIL |
| **D11** | **术语来源** | 每个非通行术语能指出真实来源（源码标识符/配置键/上游文档/人类材料），首次出现附白话解释；无自造词 | 抽检 3 处非通行叫法，架构师须给出出处；给不出 = FAIL |
| **D12** | **可读性与修订度量** | ① 单文档 >3000 行或单行 >500 字符时须给出"为何不拆/该长行是否必要"的理由（提示项，不算 FAIL）；② **记录本轮三个数：行数 / 字节数 / D10 痕迹命中数**（**行数口径见 `_shared/qa-common.md`「行数口径」节**），并与上一轮对比 | 亲自统计；理由不成立时并入 D9 判负 |
| **D13** | **数值证据完整（清洗/重写场景必查）** | 逐一核对原稿中的**数值型判据**是否留存：端口、文件大小与字节数、计数、时间戳（含 nanos 级）、PID、epoch、SHA256 前缀、inode、被引用文件行号。**缺任一即 FAIL**，要求补回 | 跑 `node {{paths.verify_rewrite}} --original <原稿> --rewrite <改后稿>`，看第 2b 节"真缺失"列；**注意区分真缺失与正则伪影**（工具对二者已内置分类） |

**D8 / D9 / D13 三条成组执行**：D8 查"结论缺依据"（少了）、D9 查"过程留痕"（多了）、D13 查"数值判据是否被当排版压掉"（压缩过头）。**D8 与 D9 互为刹车**，防止审计把文档逼向任一极端；D13 是 560 试点实测后新增的第三条防线——**结构指标全过、修订痕迹清零，仍可能因数值丢失而不可核验**。**只查其中一条或两条视为审计不完整。**

**D13 与「对向红线」的分界**：D13 治**数值**，对向红线治**原文**。要求把命令回显、日志原文搬进文档 = 越界（判 PASS）；探针输出的数值在压缩中丢失 = 证据缺失（判 FAIL）。一句话：**可以压排版，不能压证据。**

**针对修订痕迹的判负要求**（对应实际发生过的放行）：凡在**正文**发现"v1.x 更正/原为…现改为…/就地注记/上一轮 QA"这类修订说明，或发现存在"QA 回环响应表 / 修订记录 / 本版修订摘要"这类章节，**一律判 D10 FAIL，并要求架构师做整体重写**（把这些内容移出正文、写入 `{{paths.changelog}}`）。**不接受"补一句时点声明"这类打补丁式处理**——补声明会让痕迹越加越多。

**回环期追加判据**：第 N 轮（N≥2）审计时，除全部检查项外，还须报告：
- 本轮**净增长**（行数与字节数相对上一轮的差；**行数口径见 `_shared/qa-common.md`「行数口径」节**）
- 本轮**修订痕迹命中数**相对上一轮的变化
- 本轮**修复的 FAIL 项数**
- 三者组合为"净增长 > 0 **且** 痕迹命中数增加 **且** 修复数为 0"时，在 findings 中标记 `CONTROL_LOSS`，编排者据此停止回环、升级用户裁决

### 代码审计（开发专家）— A1

> **v6（2026-09-18）**：C2–C6 此前**硬编码 compute-core 的 Java 取值**——`application.yaml`、
> `com.unicloud.exception`、`@Slf4j`、`gradlew build`、MyBatis Mapper XML。
> 这是 **P10d「契约去项目字面量」的同一缺陷，此前漏改了本节**。
> 后果具体：本项目（`javascript` + `build: none`）与任何非 Java 项目接入后，
> **C2–C6 五条全部不适用，却被写成必须通过**——项目永远过不了关卡。
> 现改为**由 `profile.yaml` 的 `tech_stack` 决定是否适用**。

| # | 检查项 | 标准 | 脚本化 |
|---|--------|------|--------|
| C1 | 变更范围 | 与设计文档「实施清单」一致 | **否**——唯一必须人工的一条 |
| C2 | 包/模块分层 | 文件路径符合 `tech_stack.package_layout`；**未声明则「不适用」** | 是 |
| C3 | 无硬编码 | **仅**敏感值不落源码（明文密钥、口令、令牌）——**SQL 相关判定已并入 C6**，见下 | 是 |
| C4 | 错误处理与日志 | 异常用 `package_layout.exception` 声明的包（若声明）；关键路径按级别记日志 | 是 |
| C5 | 编译/构建验证 | 跑 `tech_stack.build` 声明的命令（`none` 则「不适用」） | 是 |
| C6 | 数据访问参数化 | **参数化查询**（禁止字符串拼接 SQL——**自 2026-09-18 由 C3 并入**）；ORM 映射文件路径与接口一致（项目未用 ORM 则「不适用」） | 是 |

> **`tech_stack.build` 的两种写法都合法，别写第三种**（2026-09-19 第九轮明确）：
> - **标量式**：`build: <可执行命令>`（如 `npm run compile`），或 `build: none` 表示**无构建系统**。
> - **嵌套式**：`build:` 下挂 `compile: <可执行命令>`。
>
> 两种写法**只描述同一个事实：本项目的构建命令是什么**。
> 因此**不要写工具名**（`msbuild`、`gradle`、`tsc` 之类）——那既不是可执行命令，
> 也不在白名单里，`code-gate` 只能给出 `REVIEW`（要求人工执行并附输出），
> **闸门等于没跑**。要写就写真正能跑通的那一行命令。
> 工具名想留就另立键（如 `tech_stack.build_tool`），**不要占用 `build`**。
>
> **为什么要把这条写进契约**：`C5` 的三种结论里 `N/A` 与 `REVIEW` 都**不阻断**，
> 于是"填了工具名"或"用了嵌套写法却因实现缺陷拿不到命令"都会**静默降级**成
> 一个看起来正常的结论。本项目实测两种情形都发生过。

**C2–C6 已下沉到脚本**：`node {{paths.tools}}code-gate.mjs --scope <变更文件清单>`。
**C1 保留人工**——它是唯一判不了形式的一条。

**「不适用」是合法结论，不是 FAIL。** 项目未声明某项技术栈时，对应检查项报告 `N/A`。
把不适用当 FAIL，会让非该技术栈的项目永远过不了关——这正是上面那条缺陷的实质。

> **脚本通过 ≠ 质量合格。** 这一条必须写死：`code-gate.mjs` 只能证明**可形式化的那部分**成立，
> **C1 与 QA 抽检判断不可省**。把代码质量做成"过脚本就算过"，是把手段当成了目的
> （§0 原则 5 的同一形态）。

### 代码评审归属（P1a，2026-09-18 新增）

**此前"代码评审"没有任何角色被指派**——`_shared/engineering-rules.md`「评审把关」只说
"评审通过后，由实施角色在评审记录中填写评审人、评审时间、评审结果、评审意见"，
**格式、路径、填写人都没写死**，是一条悬空定义。

| 角色 | 做什么 | 粒度 |
|---|---|---|
| **开发专家** | 合并前**自查**：对产出的 diff **逐文件**对照实施清单 | 全量 |
| **QA** | **抽检，不是逐行**：触及对外接口 / 数据格式 / 配置键语义 / 并发·事务的文件**全查**，其余抽 1–2 个 | 抽样 |

**代码评审记录**（补齐上面那处悬空）：

| 项 | 值 |
|---|---|
| **格式** | Markdown 表：`文件 \| 自查结论 \| 依据(行号或命令)` |
| **路径** | `.dsh/tmp/developer/review-record.md` |
| **填写人** | 开发专家 |
| **评审人** | QA 抽检记录者（在抽检结论中引用本文件） |
| **必填** | 变更文件清单、逐文件一行自查结论、C1–C6 脚本输出摘要、**未覆盖项与理由** |

> 落在 `.dsh/tmp/` 意味着它**随闭环被删除**——这是有意的：评审记录是**过程证据**，
> 而按链留存的是运行台账（每链一行），不是全部过程文件（见 `_shared/qa-common.md`「最小留存台账」节）。

### 部署审计（部署专家）— A1

> **v6（2026-09-18）**：P2–P5 此前**硬编码 compute-core 的 Java/Gradle/Harbor 取值**——
> `gradlew build -x test`、`gradlew clean`、Dockerfile 与 Harbor 路径、`REGISTRY/IMAGE/SERVICE/PLATFORM/VERSION`
> 五个变量名。这与 C2–C6 是**同一缺陷**（P10d「契约去项目字面量」漏改了本节），
> 后果同样具体：非该技术栈的项目接入后，**P2–P5 全部不适用却被写成必须通过**。
> 现改为**由 `profile.yaml` 的 `tech_stack.build` / `deploy` 决定是否适用**。

| # | 检查项 | 标准 |
|---|--------|------|
| P1 | 文件位置与语法 | 构建/部署入口文件在项目根，语法正确（**通用，恒适用**） |
| P2 | build 目标 | 存在且调用 `profile.yaml` 的 `tech_stack.build` 声明的命令；**`build: none` 则「不适用」** |
| P3 | 制品目标 | 存在镜像/制品构建目标，引用的 Dockerfile 与仓库路径**实际存在**；**项目无制品发布则「不适用」** |
| P4 | clean 目标 | 存在且调用 profile 声明的清理命令；**无 build 则「不适用」** |
| P5 | 变量定义 | 所需变量（镜像仓库、服务名、版本等）**以 profile 的 `deploy` 声明为准**，不预设变量名 |

**「不适用」是合法结论，不是 FAIL**——同 C2–C6。判据是"声明了却没做到"才失败，而不是"没声明也要求做到"。
