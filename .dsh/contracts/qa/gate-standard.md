## QA 立场：对抗式审计纪律（2026-09-02）

- **对抗立场**：QA 是质量把关人，不是被审计角色的协助者，双方利益对立。默认怀疑、逐项证伪：先找不合规证据，再谈放行；不因进度压力或对方"已声称完成/已通过"而降低标准。
- **证据优先（求实）**：每项判定必须基于亲自取得的证据——亲自读取的文件与行号，或亲自执行的验证命令及其输出摘要。仅凭被审计方的 summary/声称/承诺不得判 PASS；无法核实 = FAIL（finding 标注「证据缺失，无法核实」）。
- **复现验证（较真）**：凡声称"编译/测试通过、已修改、已部署"，必须亲自复现关键验证（以本契约各检查项定义的命令为准）；代码改动逐文件 read 对照实施清单，不采信变更摘要。
- **零容忍臆造**：发现虚报（声称与事实不符、伪造命令输出、臆造文件内容）→ 整轮直接 FAIL，finding 标注「虚报」并在 summary 向编排者标记；不因其余项通过而放行。
- **规范唯一判据**：本契约 D/C/P 检查项标准是唯一判据，不存在"基本符合/大体满足"——每项只有 PASS/FAIL；标准未覆盖但明显偏离规范精神的，判 FAIL 并写明依据。
- **不得要求超出设计需要的证据**（对向红线）：判"证据不足"的判据是"读者能否据此下判断"（准则一的三问），**不是"作者是否贴了原始输出"**。要求把命令回显、日志原文、源码全文放进设计文档或审计 json 的，一律不属于"证据不足"，应按"引用路径可核验"判 PASS。反之，**结论三问（是什么/凭什么/为什么不选别的）任一答不出，必须判 FAIL——即使它写得很长、格式很齐**。

## 审计标准

### 设计审计（架构师）— A1
| # | 检查项 | 标准 |
|---|--------|------|
| D1 | 文档结构 | 9 节结构齐全，且 §一 为需求复述、§二 为关键结论 |
| D2 | 范围明确 | 「包含」和「不包含」均列出，不做的项附理由 |
| D3 | 设计可视化 | 至少 1 个 Mermaid 或 ASCII ER 图 |
| D4 | 定量分析 | 数据须标来源、时间、环境；无来源的"实测"数字 = FAIL |
| D5 | 决策记录 | 只保留最终决策与被否决方案 + 理由一句话；出现"某轮评审意见"并入 D10 判负 |
| D6 | 实施清单 | 每项含 [目标角色] + 涉及文件 + 验收判据 |
| D7 | 评审状态 | 标注「待评审」 |
| **D8** | **充足性（治电报）** | 每个结论都回答了"是什么/凭什么/为什么不选别的"三问；无孤立短语、无未定义术语、无"无头无尾"的结论 | 抽 3 个关键结论逐条对照三问；缺任一问 = FAIL，finding 指出是哪个结论缺哪一问 |
| **D9** | **必要性（治流水账）** | 正文无过程留痕、无问答回放、无工具输出粘贴、无重复信息；同一条信息只出现一次 | 通读全文；发现任一类即 FAIL，finding 给行号与原文片段 |
| **D10** | **时效与单一事实源** | 正文无旧版结论残留、无"原为…现改为…"、无"就地注记"、无修订记录章节；全篇口径一致 | 全文检索 `修订\|变更记录\|版本历史\|原为\|上一轮\|更正\|就地注记\|v\d+\.\d+`；命中即 FAIL |
| **D11** | **术语来源** | 每个非通行术语能指出真实来源（源码标识符/配置键/上游文档/人类材料），首次出现附白话解释；无自造词 | 抽检 3 处非通行叫法，架构师须给出出处；给不出 = FAIL |
| **D12** | **可读性与修订度量** | ① 单文档 >3000 行或单行 >500 字符时须给出"为何不拆/该长行是否必要"的理由（提示项，不算 FAIL）；② **记录本轮三个数：行数 / 字节数 / D10 痕迹命中数**（**行数口径见本契约末「行数口径」节**），并与上一轮对比 | 亲自统计；理由不成立时并入 D9 判负 |
| **D13** | **数值证据完整（清洗/重写场景必查）** | 逐一核对原稿中的**数值型判据**是否留存：端口、文件大小与字节数、计数、时间戳（含 nanos 级）、PID、epoch、SHA256 前缀、inode、被引用文件行号。**缺任一即 FAIL**，要求补回 | 跑 `node {{paths.verify_rewrite}} --original <原稿> --rewrite <改后稿>`，看第 2b 节"真缺失"列；**注意区分真缺失与正则伪影**（工具对二者已内置分类） |

**D8 / D9 / D13 三条成组执行**：D8 查"结论缺依据"（少了）、D9 查"过程留痕"（多了）、D13 查"数值判据是否被当排版压掉"（压缩过头）。**D8 与 D9 互为刹车**，防止审计把文档逼向任一极端；D13 是 560 试点实测后新增的第三条防线——**结构指标全过、修订痕迹清零，仍可能因数值丢失而不可核验**。**只查其中一条或两条视为审计不完整。**

**D13 与「对向红线」的分界**：D13 治**数值**，对向红线治**原文**。要求把命令回显、日志原文搬进文档 = 越界（判 PASS）；探针输出的数值在压缩中丢失 = 证据缺失（判 FAIL）。一句话：**可以压排版，不能压证据。**

**针对修订痕迹的判负要求**（对应实际发生过的放行）：凡在**正文**发现"v1.x 更正/原为…现改为…/就地注记/上一轮 QA"这类修订说明，或发现存在"QA 回环响应表 / 修订记录 / 本版修订摘要"这类章节，**一律判 D10 FAIL，并要求架构师做整体重写**（把这些内容移出正文、写入 `{{paths.changelog}}`）。**不接受"补一句时点声明"这类打补丁式处理**——补声明会让痕迹越加越多。

**回环期追加判据**：第 N 轮（N≥2）审计时，除全部检查项外，还须报告：
- 本轮**净增长**（行数与字节数相对上一轮的差；**行数口径见本契约末「行数口径」节**）
- 本轮**修订痕迹命中数**相对上一轮的变化
- 本轮**修复的 FAIL 项数**
- 三者组合为"净增长 > 0 **且** 痕迹命中数增加 **且** 修复数为 0"时，在 findings 中标记 `CONTROL_LOSS`，编排者据此停止回环、升级用户裁决

### 代码审计（开发专家）— A1

> **v6（2026-09-18）**：C2–C6 此前**硬编码 compute-core 的 Java 取值**——`application.yaml`、
> `com.unicloud.exception`、`@Slf4j`、`gradlew build`、MyBatis Mapper XML。
> 这是 **P10d「契约去项目字面量」的同一缺陷，此前漏改了本节**。
> 后果具体：本项目（`javascript` + `build: none`）与任何非 Java 项目接入后，
> **C2–C6 五条全部不适用，却被写成必须通过**——项目永远过不了关卡。
> 现改为**由 `profile.yaml` 的 `tech_stack` 决定是否适用**。

| # | 检查项 | 标准 | 脚本化 |
|---|--------|------|--------|
| C1 | 变更范围 | 与设计文档「实施清单」一致 | **否**——唯一必须人工的一条 |
| C2 | 包/模块分层 | 文件路径符合 `tech_stack.package_layout`；**未声明则「不适用」** | 是 |
| C3 | 无硬编码 | **仅**敏感值不落源码（明文密钥、口令、令牌）——**SQL 相关判定已并入 C6**，见下 | 是 |
| C4 | 错误处理与日志 | 异常用 `package_layout.exception` 声明的包（若声明）；关键路径按级别记日志 | 是 |
| C5 | 编译/构建验证 | 跑 `tech_stack.build` 声明的命令（`none` 则「不适用」） | 是 |
| C6 | 数据访问参数化 | **参数化查询**（禁止字符串拼接 SQL——**自 2026-09-18 由 C3 并入**）；ORM 映射文件路径与接口一致（项目未用 ORM 则「不适用」） | 是 |

> **`tech_stack.build` 的两种写法都合法，别写第三种**（2026-09-19 第九轮明确）：
> - **标量式**：`build: <可执行命令>`（如 `npm run compile`），或 `build: none` 表示**无构建系统**。
> - **嵌套式**：`build:` 下挂 `compile: <可执行命令>`。
>
> 两种写法**只描述同一个事实：本项目的构建命令是什么**。
> 因此**不要写工具名**（`msbuild`、`gradle`、`tsc` 之类）——那既不是可执行命令，
> 也不在白名单里，`code-gate` 只能给出 `REVIEW`（要求人工执行并附输出），
> **闸门等于没跑**。要写就写真正能跑通的那一行命令。
> 工具名想留就另立键（如 `tech_stack.build_tool`），**不要占用 `build`**。
>
> **为什么要把这条写进契约**：`C5` 的三种结论里 `N/A` 与 `REVIEW` 都**不阻断**，
> 于是"填了工具名"或"用了嵌套写法却因实现缺陷拿不到命令"都会**静默降级**成
> 一个看起来正常的结论。本项目实测两种情形都发生过。

**C2–C6 已下沉到脚本**：`node {{paths.tools}}code-gate.mjs --scope <变更文件清单>`。
**C1 保留人工**——它是唯一判不了形式的一条。

**「不适用」是合法结论，不是 FAIL。** 项目未声明某项技术栈时，对应检查项报告 `N/A`。
把不适用当 FAIL，会让非该技术栈的项目永远过不了关——这正是上面那条缺陷的实质。

> **脚本通过 ≠ 质量合格。** 这一条必须写死：`code-gate.mjs` 只能证明**可形式化的那部分**成立，
> **C1 与 QA 抽检判断不可省**。把代码质量做成"过脚本就算过"，是把手段当成了目的
> （§0 原则 5 的同一形态）。

### 代码评审归属（P1a，2026-09-18 新增）

**此前"代码评审"没有任何角色被指派**——`_shared/engineering-baseline.md:42` 只说
"评审通过后，开发人员在评审记录中填写评审人、评审时间、评审结果、评审意见"，
**格式、路径、填写人都没写死**，是一条悬空定义。

| 角色 | 做什么 | 粒度 |
|---|---|---|
| **开发专家** | 合并前**自查**：对产出的 diff **逐文件**对照实施清单 | 全量 |
| **QA** | **抽检，不是逐行**：触及对外接口 / 数据格式 / 配置键语义 / 并发·事务的文件**全查**，其余抽 1–2 个 | 抽样 |

**代码评审记录**（补齐 `_shared:42` 的悬空）：

| 项 | 值 |
|---|---|
| **格式** | Markdown 表：`文件 \| 自查结论 \| 依据(行号或命令)` |
| **路径** | `.dsh/tmp/developer/review-record.md` |
| **填写人** | 开发专家 |
| **评审人** | QA 抽检记录者（在抽检结论中引用本文件） |
| **必填** | 变更文件清单、逐文件一行自查结论、C1–C6 脚本输出摘要、**未覆盖项与理由** |

> 落在 `.dsh/tmp/` 意味着它**随闭环被删除**——这是有意的：评审记录是**过程证据**，
> 而按链留存的是运行台账（每链一行），不是全部过程文件（见本契约「最小留存台账」节）。

### 部署审计（部署专家）— A1

> **v6（2026-09-18）**：P2–P5 此前**硬编码 compute-core 的 Java/Gradle/Harbor 取值**——
> `gradlew build -x test`、`gradlew clean`、Dockerfile 与 Harbor 路径、`REGISTRY/IMAGE/SERVICE/PLATFORM/VERSION`

|---|--------|------|

而不是"没声明也要求做到"。

## 检查流转
```
A1：架构师→QA设计→用户评审→开发→QA代码→部署→QA部署→测试
   不通过 → 回环修正 → 再审（回环控制按进展检查点，见下）
```
**进展检查点（QA 侧的职责）**：QA **不判断回环次数、不判断何时停止**——停止条件由编排者（preset persona）唯一裁决。QA 的职责是每轮如实报告 findings 与证据，并**明确标注**以下三项以便编排者判断：① 既有 FAIL 项中是否有至少一项被证实修复（转 PASS，且非靠缩范围/降标准达成）；② 本轮是否存在**连续零修复**；③ 是否有 D12 报告的 `CONTROL_LOSS` 特征。

> **控制律唯一事实源（2026-09-18 修订）**：本节此前写死了"回环不设固定次数上限"（2026-09-02 裁决）。该表述与编排者侧 2026-09-15 的"重派封顶"决策**冲突**，且契约停在旧决策上。现已删除契约中的所有停止条件表述，**契约只描述"发现什么"，不描述"何时停"**。

**设计阶段终止条件的报告义务**：出现 D12 报告的 `CONTROL_LOSS`（净增长 + 痕迹增加 + 零修复）时，QA **必须立即如实上报该特征**；**是否停止由编排者裁决**，QA 不自行终止。

**一次审计跑全**：QA 每一轮必须把本阶段**全部**检查项（设计阶段为 D1–D13）跑完并一次性给全 findings，不得"这轮只查结构、下轮再查冗余"。分批查会让架构师在信息不全的情况下改稿——那是文档越改越乱的直接来源。

## QA 报告格式
每轮审计输出两段（结构化结论内联回传 + 临时文件落盘）：

1. **子代理最终消息**（该角色 subagent 的最终消息，编排者直接消费）：
```json
{
  "blocked": true, "target": "架构师", "retry": 1, "phase": "design",
  "summary": "1-2 句关键结论（≤200 字符，调度用）",
  "confidence": "high | medium | low",
  "uncertainty": "≤200 字符：我不确定的是什么、需要什么才能确定；无不写",
  "criterion_issue": "≤200 字符：哪条判据本身不适用或有缺陷、为什么；无不写",
  "findings": [{"id":"D3","status":"FAIL","item":"缺少架构图","suggestion":"补充","evidence":"已通读设计文档全文，未发现 Mermaid/ASCII 图"}]
}
```

### 不确定性的安全通道（P8，2026-09-18 新增）

**问题**：本契约 §开头明示双方利益对立，而**此前没有任何机制**让子代理安全表达「我不确定」
「这条判据本身有问题」。要求人在对立位置上保持诚实，却不开一条不追责的通道，是**制度性伪命题**。

| 字段 | 用途 | 是否改变本轮判定 |
|---|---|---|
| `confidence` | 报告对**本轮结论**的置信度（high/medium/low） | 否 |
| `uncertainty` | 说清**不确定的是什么、需要什么才能确定** | 否 |
| `criterion_issue` | 质疑**判据本身**（不适用／有缺陷） | **否**——只进运行台账供规则复审（P9） |

**三条边界，必须一起落地（只落一半就会变成免责口子）**：

1. **如实报告「无法核实 / 不确定」不构成 FAIL；隐瞒不确定性后被查出，才构成 FAIL。**
2. **这与本契约的「无法核实 = FAIL」不冲突，两者管的是不同的东西**：
   - 「无法核实 = FAIL」是**对产物**的判断——证据不足即不通过；
   - 本条是**对报告行为**的保护——如实说出"我核不了"不受罚。

   **边界写不清，第 1 条就会被当作放宽标准的口子。**
3. **`criterion_issue` 不改变本轮判定**，只记录。它有意义的场合是**规则复审**（P9）：
   反复出现的 `criterion_issue` 是"该判据该改"的第一手证据。

> **证据强度要说实话**：本项理论依据是 Edmondson 心理安全感（1999）与 Project Aristotle。
> 前者是**51 个团队、单一制造企业、横断面研究**，单看是 **B 级因果强度**；后者**非同行评审**。
> 因此本项定位为**低成本试验，不作为高置信度改动**。**验收判据**：运行台账里能统计到
> `confidence` 分布与 `criterion_issue` 次数——**首月为 0 也是有效结果**（说明确实没人用，
> 或确实没有该报的），**不追指标**。

2. **完整审计文件**（临时产物，供追溯）：`.dsh/tmp/audits/qa_{phase}_{seq}.json`，
   含 timestamp/phase/agent/retry_count/total_checks/passed/failed/blocked/target_agent/findings（每项含 evidence）全字段；设计阶段另含 D12 的三个数（行数 / 字节数 / 痕迹命中数）与上一轮对比值；另含上述 `confidence` / `uncertainty` / `criterion_issue` 三字段。

### 审计产物规范（约束 QA 自己的产出）
- **证据只引用，不搬运**：证据字段 ≤300 字符，只写「文件:行号 / 命令 / 结论性数字 / 原始产物路径」；大段输出（命令回显、日志、源码片段）落 `.dsh/tmp/audits/<phase>/_raw/`，报告里只写路径
- **单份审计 json ≤8 KB**（超出说明把原文搬进来了）；`overall_reason` ≤400 字符；最终消息 `summary` ≤200 字符
- **QA 额外写的 markdown 报告 ≤150 行**：只写结论与判定依据，不复制被审计文档的内容
- **逐轮只给增量**：回环第 N 轮只列「本轮新增 findings + 上轮 FAIL 项复核结果 + 未受影响的项一行带过（沿用上轮判定）」，不重复已 PASS 项的结构与证据
- 判"证据不足"时按上面对向红线执行，不得把"没贴原始输出"当作证据不足

**闭环约定**：轮级回环取代上一轮时，`.dsh/tmp/audits/` 中该 phase 的旧审计由编排者随轮级闭环清理；
链级闭环时 `.dsh/reports/`（含最终一轮 QA 审计）随 `.dsh/tmp/` **一并直接删除**（2026-09-18 由"移入归档"改为删除：归档占交付件 97% 的体量且无人消费）；因此**最终一轮 QA 审计结论必须由编排者在删除之前向用户汇报**，不保留永久档案。

## 工具触发规则（2026-09-18 新增）

> **为什么补这一节**：实测能力脚本中**绝大多数从未被任何契约或预设点名**——它们已随模式分发到各项目，却没有任何一处告诉模型它们存在、何时该跑。**能力具备了，可达性没具备。** 本节补的是"何时必须跑"；用法另见 skill `agile-toolkit`。

**通用规则**：下列条件命中时**必须**执行对应脚本，并把命令与输出摘要作为 evidence 附进 finding。**未执行即下判断，该 finding 按无证据处理。**

| 触发条件 | 必须执行 | 判据 |
|---|---|---|
| 产出或修订 `{{paths.docs}}` 下正式文档后 | `node {{paths.verify_rewrite}} --original <原稿> --rewrite <改后稿>` | **只看第 2b 节"真缺失"列**（正则伪影不算缺失）；真缺失非空 → **D13 FAIL** |
| 同上，需逐个数值确认去留 | `num-diff.mjs` | 全量对撞明细 |
| 同一份文档**第二轮及以后**的修订 | `measure-netgrowth.mjs`（必要时 `measure-section-growth.mjs` 定位到节） | 净增长 > 0 且属过程沉淀 → FAIL |
| 怀疑**表格结构**被破坏（拍扁／表体删除／重复行） | `table-integrity.mjs`，按需加 `analyze-flatten.mjs` / `find-empty-table-body.mjs` / `row-duplication.mjs` | **须配原文对照**才有意义；只在"改前没有、改后有"时才算缺陷 |
| 怀疑**结论缺失**（不是"结论错"） | `detect-gaps.mjs` / `check-03-claims.mjs` | 只测"正文有没有那个结构"，**不测内容对不对** |

> **2026-09-18 第六、七轮改动**：本表原含"批量换入规范化稿前先 `--dry-run`"一行，

## 内置约束
- **QA 不判断回环次数与停止条件**（停止条件由编排者唯一裁决；QA 只如实报告 findings、零修复轮次与 `CONTROL_LOSS` 特征）
- 审计报告必须含 blocked、target_agent、retry_count
- 每项判定必须附 evidence：亲自读取的文件与行号，或亲自执行的命令与输出摘要；无法核实 = FAIL
- 发现虚报（声称与事实不符、伪造命令输出、臆造文件内容）→ 整轮 FAIL，finding 标注「虚报」
- 不私自修改被审计内容

## 行数口径（唯一定义处）

**行数 = UTF-8 解码后按 `\n` 切分得到的段数**；空行照数；末尾换行不额外算一段；`\r\n` 先归一为 `\n`。
字节数 = UTF-8 编码后的字节长度。**实现收敛到 `{{paths.tools}}lib-lines.mjs` 的 `countLines()` / `measure()`——任何工具要行数必须 import 它，不得自行实现。**

> **为什么必须写这一条**：`CONTROL_LOSS` 的第一个条件正是"净增长（**行数**与字节数相对上一轮的差）> 0"，
> 而契约对"字节数"规定了口径、对"**行数**"没有。实测同一份文件在两种工具下**行数差 26%**
> （`verify-rewrite-555.md`：本口径 167 行 vs PowerShell `Get-Content` 默认编码 123 行）——
> 差在**空行与末尾换行**的处理。**判据用的数没有定义，闸门就会因换工具而改变结论。**
>
> 口径自检（**随交付件走，目标项目可直接跑**）：`node {{paths.tools}}lib-lines.mjs --self-test`。
> 它把"三种常见实现量出三个数"固化为常驻对照证据，并在口径被改动时报 FAIL。

## 最小留存台账（P3c）与周期时间采集（P2a）

**每链闭环时，编排者向 `{{paths.run_ledger}}` 追加一行**。字段定义以该文件的表头为准；
**结构校验**：`node {{paths.tools}}ledger-check.mjs`。

### 为什么不存"全部审计文件"

链级闭环会清理 `.dsh/tmp/` 与 `.dsh/reports/`，**证物随之消失**——实测后果：无基线、无趋势、
无改进验证，且**至少 5 处文档把已不存在的审计 json 当证据引用**。

但留存全部审计文件也**已被否决**：那造成过 **83 文件 / 1212 KB** 的堆积。
**最小可行形式是"每链一行摘要"**——足够支撑趋势与规则复审（P9），又不重演堆积。

### 采集什么

| 字段组 | 字段 | 服务于 |
|---|---|---|
| 标识 | 链 id / 起止 | 定位 |
| 档位 | A0 / A1 / A2简 / A2标准 / A2深 | 分层比较（**不跨档位比**） |
| 流量 | 派发次数 / 重派次数 / 每环轮次 | **P2a 周期时间**：产出**分布**，不报均值 |
| 终局 | 结论（通过 / 升级用户 / 未闭环） | 趋势 |
| **失败分布** | **失败检查项的 id 分布**（如 `D8×2,D13×1`） | **P9 规则复审的输入** |

> **为什么记分布而不是总数**：总数只能说"这轮不好"；**分布才能指出是哪条规则在反复失守**——
> 也就是 P9 要删/合并/修订的那一条。

### 三条硬约束

1. **仅作诊断，不得作为考核指标**。派发次数、重派次数、轮次都属 Activity 类度量，最易 Goodhart 化
   （SPARK / §0 原则 5）。**它们只用来发现结构与趋势。**
2. **P2a 只报分布，不报均值**（§0 原则 8）。均值会把长尾藏起来，而长尾正是要看的。
3. **台账在产物之后写**——回执/台账**不得先于产物**（源头纪律：产物才是证物，台账只是索引）。
   写的时机是**链闭环、`.dsh/tmp/` 被删除之前**：先把数据摘出来，再删证物。

### 规则复审机制（P9，2026-09-18 新增）

**每 5 条链闭环触发一次规则复审**（N=5，按 `{{paths.run_ledger}}` 的数据行计数）。
产出一页清单，落 `{{paths.docs}}` 下的耐久位置（**不放 `.dsh/tmp/`——它会被闭环清空**）。
首次清单见 `{{paths.docs}}规则复审清单-2026-09-18.md`。

| 问句 | 目的 | 处置 |
|---|---|---|
| 哪条判据在最近 N 条链里**从未 FAIL**？ | 可能已无区分度 | 候选删除或降为抽样 |
| 哪条判据 FAIL 后**从未导致有意义的修改**？ | 可能只是噪声 | 候选修订 |
| 哪两条判据**总是同时 FAIL**？ | 可能是一件事被管两遍 | **候选合并** |
| 哪条规则**与其它规则冲突**？ | 调节器内部不一致 | 纠正 |

**硬判据：每次复审必须至少删掉或合并一条规则。** 若一条都删不掉，**报告为复审机制失效**——
这本身是有效结论，不是失败。

> **为什么必须有这条硬判据**：判据演进实测 **6 次全部来自事故驱动、全部是新增约束、
> 无一次删除或合并**。按 Senge 的「成长上限」原型，规则增长带来质量提升的同时也带来负荷增长，
> **负荷最终成为限制**。没有可证伪的产出要求，复审就会退化成「再写一页清单」。
> （Schön 反思性实践——反思应是常规而非例外；双环学习。）
>
> **前两次复审的能力不同，要说清楚**：第 1 次（2026-09-18）**运行台账数据行 0 条**，
> 因此**只能依据结构证据**（后两问），答不了前两问。这不是缺陷而是顺序——
> 测量系统必须先于控制图可信（Shewhart / Deming）。满 5 条链后，前两问即可回答。

### 台账为空时怎么算

**空表是有效状态。** 首次建立时**无历史数据可补录**——那些数据已随闭环被清掉。
**不得编造看起来合理的数字**：宁可表是空的。这本身是有效结论：
**在建立台账之前，本模式对自己的运行状况是不可观测的**，所有"改进了多少"的说法都缺少可核对的基线
（Shewhart / Deming：**测量系统必须先于控制图可信**）。
