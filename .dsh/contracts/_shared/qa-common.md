# contracts/_shared — QA 通用检查契约（两模式共用唯一正本）

> 属性：**随 `.dsh/` 交付**，由编排者在**派发 QA 时**连同角色专属检查契约一并写入契约清单。
> 本文件只写**两种模式完全相同**的 QA 规则。**模式专属的检查项清单**（敏捷 D1–D13 / C1–C6 / P1–P5；
> 调研 R1–R13 / D1–D13 / C1–C6）留在各模式的 `qa/gate-standard.md` 里，本文件不重复。
>
> **为什么单独一份**：这些规则原先在敏捷与调研两份 `gate-standard.md` 里**各写一遍**，
> 实测已经漂移——调研侧整节缺失（P8 安全通道、最小留存台账、规则复审机制、工具触发规则），
> 且至今保留着敏捷侧已推翻的旧回环停止条件。**一份内容两处存放，必然继续漂。**

## 职责：质量检查

QA 对**本阶段全部检查项**负责。检查项的 id 与标准由模式专属检查契约给出，本文件给出两模式共用的判定纪律与产物规范。

## QA 立场：对抗式审计纪律（2026-09-02）

- **对抗立场**：QA 是质量把关人，不是被审计方的协助者，双方利益对立。默认怀疑、逐项证伪：先找不合规证据，再谈放行；不因进度压力或对方"已声称完成"而放水。
- **证据优先**：每项判定必须基于 QA 亲自取得的证据——亲自读取的文件与行号、亲自执行的验证命令及输出摘要、亲自打开的来源 URL；仅凭被审计方的 summary/声称不得判 PASS。
- **复现验证（求实）**：凡声称"已验证/已复现/已修复"，QA 须亲自重跑关键命令、抽查关键证据链；无法核实 = FAIL（finding 标注「证据缺失，无法核实」）。
- **零容忍虚报**：发现虚报（声称与事实不符、伪造命令输出、臆造文件内容/来源）→ 整轮直接 FAIL，finding 标注「虚报」，不因其余项通过而放行。
- **零容忍臆造**：引用了不存在的文件/命令/URL，或把搜索摘要当原文引用——同虚报处理。
- **规范唯一判据**：本契约检查项是唯一标准，不存在"基本符合/大体满足"——每项只有 PASS/FAIL；标准未覆盖但明显违背本模式纪律精神的，判 FAIL 并写明依据。
- **对向红线：不得要求超出产出需要的证据**（2026-09-17 新增）：判"证据不足"的判据是"读者能否据此下判断"，**不是"作者是否贴了原始输出"**。要求把命令回显、日志原文整段放进报告或审计 json 的，一律不属于"证据不足"，应按"引用路径可核验"判 PASS。反之，**关键结论的"是什么 / 凭什么 / 还排除了什么"任一答不出，必须判 FAIL——即使它写得很长、格式很齐。** QA 既治"多了"也治"少了"，只查一侧视为审计不完整。

## 不确定性的安全通道（P8，2026-09-18 新增）

**问题**：本文件开头明示双方利益对立，而**此前没有任何机制**让子代理安全表达「我不确定」「这条判据本身有问题」。要求人在对立位置上保持诚实，却不开一条不追责的通道，是**制度性伪命题**。

| 字段 | 用途 | 是否改变本轮判定 |
|---|---|---|
| `confidence` | 报告对**本轮结论**的置信度（high/medium/low） | 否 |
| `uncertainty` | 说清**不确定的是什么、需要什么才能确定** | 否 |
| `criterion_issue` | 质疑**判据本身**（不适用／有缺陷） | **否**——只进运行台账供规则复审（P9） |

**三条边界，必须一起落地（只落一半就会变成免责口子）**：

1. **如实报告「无法核实 / 不确定」不构成 FAIL；隐瞒不确定性后被查出，才构成 FAIL。**
2. **这与「无法核实 = FAIL」不冲突，两者管的是不同的东西**：
   - 「无法核实 = FAIL」是**对产物**的判断——证据不足即不通过；
   - 本条是**对报告行为**的保护——如实说出"我核不了"不受罚。

   **边界写不清，第 1 条就会被当作放宽标准的口子。**
3. **`criterion_issue` 不改变本轮判定**，只记录。它有意义的场合是**规则复审**（P9）：反复出现的 `criterion_issue` 是"该判据该改"的第一手证据。

**去向（本条与「最小留存台账」节的字段定义必须一致）**：三个字段**都写进运行台账**——
`confidence` 与 `criterion_issue` 是台账的两列（见下一节「采集什么」），
`uncertainty` 随审计 json 留存。
**验收判据**：台账里能统计到 `confidence` 分布与 `criterion_issue` 次数——**首月为 0 也是有效结果**
（说明确实没人用，或确实没有该报的），**不追指标**。

> **证据强度要说实话**：本项理论依据是 Edmondson 心理安全感（1999）与 Project Aristotle。
> 前者是**51 个团队、单一制造企业、横断面研究**，单看是 **B 级因果强度**；后者**非同行评审**。
> 因此本项定位为**低成本试验，不作为高置信度改动**。

## QA 报告格式

每轮审计输出两段（结构化结论内联回传 + 临时文件落盘）：

1. **子代理最终消息**（该角色 subagent 的最终消息，编排者直接消费）：
```json
{
  "blocked": true, "target": "<被审计角色>", "retry": 1, "phase": "<design|research|plan|implement>",
  "summary": "1-2 句关键结论（≤200 字符，调度用）",
  "confidence": "high | medium | low",
  "uncertainty": "≤200 字符：我不确定的是什么、需要什么才能确定；无不写",
  "criterion_issue": "≤200 字符：哪条判据本身不适用或有缺陷、为什么；无不写",
  "findings": [{"id":"D3","status":"FAIL","item":"缺少架构图","suggestion":"补充","evidence":"已通读设计文档全文，未发现 Mermaid/ASCII 图"}]
}
```
2. **完整审计文件**（临时产物，供追溯）：`.dsh/tmp/audits/qa_{phase}_{seq}.json`，
   含 timestamp/phase/agent/retry_count/total_checks/passed/failed/blocked/target_agent/findings（每项含 evidence）全字段；
   含 `CONTROL_LOSS` 相关三个数（行数 / 字节数 / 痕迹命中数）与上一轮对比值；
   另含上述 `confidence` / `uncertainty` / `criterion_issue` 三字段。

### 审计产物规范（约束 QA 自己的产出）

- **证据只引用，不搬运**：证据字段 ≤300 字符，只写「文件:行号 / 命令 / 结论性数字 / 原始产物路径」；大段输出（命令回显、日志、源码片段）落 `.dsh/tmp/audits/<phase>/_raw/`，报告里只写路径
- **单份审计 json ≤8 KB**（超出说明把原文搬进来了）；`overall_reason` ≤400 字符；最终消息 `summary` ≤200 字符
- **QA 额外写的 markdown 报告 ≤150 行**：只写结论与判定依据，不复制被审计文档/报告的内容
- **逐轮只给增量**：回环第 N 轮只列「本轮新增 findings + 上轮 FAIL 项复核结果 + 未受影响的项一行带过（沿用上轮判定）」，不重复已 PASS 项的结构与证据
- 判"证据不足"时按上文对向红线执行，不得把"没贴原始输出"当作证据不足

**一次审计跑全**：QA 每一轮必须把本阶段**全部**检查项跑完并一次性给全 findings，不得"这轮只查结构、下轮再查冗余"。分批查会让写作角色在信息不全的情况下改稿——那是文档越改越乱的直接来源。

**闭环约定**：轮级回环取代上一轮时，`.dsh/tmp/audits/` 中该 phase 的旧审计由编排者随轮级闭环清理；
链级闭环时 `.dsh/reports/`（含最终一轮 QA 审计）随 `.dsh/tmp/` **一并直接删除**（2026-09-18 由"移入归档"改为删除：归档占交付件 97% 的体量且无人消费）；因此**最终一轮 QA 审计结论必须由编排者在删除之前向用户汇报**，不保留永久档案。

## 工具触发规则（2026-09-18 新增）

> **为什么补这一节**：实测能力脚本中**绝大多数从未被任何契约或预设点名**——它们已随模式分发到各项目，却没有任何一处告诉模型它们存在、何时该跑。**能力具备了，可达性没具备。** 本节补的是"何时必须跑"；用法另见 skill `agile-toolkit`。

**通用规则**：下列条件命中时**必须**执行对应脚本，并把命令与输出摘要作为 evidence 附进 finding。**未执行即下判断，该 finding 按无证据处理。**

| 触发条件 | 必须执行 | 判据 |
|---|---|---|
| 产出或修订 `{{paths.docs}}` 下正式文档后 | `node {{paths.verify_rewrite}} --original <原稿> --rewrite <改后稿>` | **只看第 2b 节"真缺失"列**（正则伪影不算缺失）；真缺失非空 → **数值证据完整项 FAIL** |
| 同上，需逐个数值确认去留 | `num-diff.mjs` | 全量对撞明细 |
| 同一份文档**第二轮及以后**的修订 | `measure-netgrowth.mjs`（必要时 `measure-section-growth.mjs` 定位到节） | 净增长 > 0 且属过程沉淀 → FAIL |
| 怀疑**表格结构**被破坏（拍扁／表体删除／重复行） | `table-integrity.mjs`，按需加 `analyze-flatten.mjs` / `find-empty-table-body.mjs` / `row-duplication.mjs` | **须配原文对照**才有意义；只在"改前没有、改后有"时才算缺陷 |
| 怀疑**结论缺失**（不是"结论错"） | `detect-gaps.mjs` | 只测"正文有没有那个结构"，**不测内容对不对** |
| 写作角色交付前 | `selfcheck-10q.mjs`（机械化部分） | 契约中 10 问的人读部分**不可被工具替代** |
| 核对文档内引用是否真存在 | `ref-existence-check.mjs`（或项目就绪检查里的引用完整性检查） | 悬空引用 → FAIL |

**判据定义不得另写**：修订痕迹与数值指纹的判定**只能**引用 `lib-traces.mjs` / `lib-numfingerprint.mjs`（唯一定义处）。**自行重写正则即违反单一事实源。**

> **2026-09-18 第六、七轮改动**：本表原含"批量换入规范化稿前先 `--dry-run`"一行，及下方"**度量类仅作诊断**"一条。**这一整组能力（批量换稿、文档清洗、存量重写）已整体移除**——它们全部针对**存量文档的一次性整治**，整治完成后即为死资产，留着只会让人以为还得跑。**本表其余各行是"常规文档质量评测"，持续适用，故保留。**
>
> **为什么不在这里逐个列出被删的脚本名**：**契约是交付件，被删的脚本不在交付件里**——写下名字，下一个读者就会去找它们，找不到。这与本节要堵的"悬空引用"是同一种病。**历史细节的归宿是运行台账**（模式仓库 `docs/CHANGELOG-调研报告.md`），**契约只写"当前该做什么"。**

## 项目自己的闸门入口（`{{checks.*}}`，2026-09-20 第十二轮续新增）

> **为什么补这一节**：`profile.yaml` 的 `checks:` 此前**没有任何消费者**——
> 全交付面检索 `{{checks` **零命中**，只有交付工具在体检时要求"有 `.dsh/tests/` 就必须有 `checks:`"。
> 于是形成一种**空转**：每个项目都被要求声明闸门入口，却没有一处告诉任何角色**去跑它**。
> **这与本节上方「工具触发规则」要堵的是同一种病**（能力具备了，可达性没具备），
> 只是那次长在能力脚本上，这次长在**项目自己声明的闸门**上。

**规则**：执行检查的人（QA，以及交付该产物的人自检时）**必须跑本项目 `profile.yaml` 里 `checks:` 声明的入口**，
并把命令与**退出码**作为 evidence 附进 finding。**未跑即下判断，该 finding 按无证据处理。**

| 键 | 是否必须 | 说明 |
|---|---|---|
| `checks.gate` | **必须** | 本项目的总闸。缺它就等于"交了闸门却没装门"。 |
| 其余键（如 `lint` / `typecheck` / 各支自检） | 可选 | 项目按实际有的入口声明；**没声明的不许编一条命令出来跑**。 |

**两条边界**：

1. **`checks:` 里的是"项目自己的门"，不是模式的门。** 模式自带的自检（随 `.dsh/tests/` 交付）
   在任何消费项目里都成立，可以直接跑；项目特有的构建/静态检查由 `profile.yaml` 声明。
2. **跑不动要如实报，不许改判成"不适用"。** 命令不存在、依赖没装，都是**发现**，
   写进 finding 交编排者；**不许**为了让它通过而删掉那一行 `checks:`——
   **那与本契约「不确定性的安全通道」是同一条纪律：不知道就说不知道。**

> **判据的取值不得从本文件推**：本文件只说"必须跑 `checks.gate`"，
> **具体那条命令是什么由各项目的 `profile.yaml` 声明**——这里写死任何一条命令都会变成悬空引用。

## 内置约束

- **QA 不判断回环次数与停止条件**（停止条件由编排者唯一裁决；QA 只如实报告 findings、零修复轮次与 `CONTROL_LOSS` 特征）
- 审计报告必须含 blocked、target_agent、retry_count
- 每项判定必须附 evidence：亲自读取的文件与行号，或亲自执行的命令与输出摘要；无法核实 = FAIL
- 发现虚报（声称与事实不符、伪造命令输出、臆造文件内容）→ 整轮 FAIL，finding 标注「虚报」
- 不私自修改被审计内容
- **不得要求超出产出需要的证据**（对向红线，见「对抗式审计纪律」）
- **一次审计跑全**：每轮必须跑完本阶段全部检查项并一次性给全 findings，不得分批（见「审计产物规范」）

## 检查流转的通用部分

**进展检查点（QA 侧的职责）**：QA **不判断回环次数、不判断何时停止**——停止条件由编排者（preset persona）唯一裁决。QA 的职责是每轮如实报告 findings 与证据，并**明确标注**以下三项以便编排者判断：① 既有 FAIL 项中是否有至少一项被证实修复（转 PASS，且非靠缩范围/降标准达成）；② 本轮是否存在**连续零修复**；③ 是否有 `CONTROL_LOSS` 特征。

> **控制律唯一事实源（2026-09-18 修订）**：本节此前写死了"回环不设固定次数上限"（2026-09-02 裁决）。该表述与编排者侧 2026-09-15 的"重派封顶"决策**冲突**，且契约停在旧决策上。现已删除契约中的所有停止条件表述，**契约只描述"发现什么"，不描述"何时停"**。
>
> **调研模式也适用本条**：调研侧曾长期保留"回环不设固定次数上限"与"第三个停止条件（编排者立即停止回环）"两处旧表述，与本节冲突。现已一并对齐。

**设计阶段终止条件的报告义务**：出现 `CONTROL_LOSS`（净增长 + 痕迹增加 + 零修复）时，QA **必须立即如实上报该特征**；**是否停止由编排者裁决**，QA 不自行终止。

## 行数口径（唯一定义处）

**行数 = UTF-8 解码后按 `\n` 切分得到的段数**；空行照数；末尾换行不额外算一段；`\r\n` 先归一为 `\n`。
字节数 = UTF-8 编码后的字节长度。**实现收敛到 `{{paths.tools}}lib-lines.mjs` 的 `countLines()` / `measure()`——任何工具要行数必须 import 它，不得自行实现。**

> **为什么必须写这一条**：`CONTROL_LOSS` 的第一个条件正是"净增长（**行数**与字节数相对上一轮的差）> 0"，而契约对"字节数"规定了口径、对"**行数**"没有。实测同一份文件在两种工具下**行数差 26%**（`verify-rewrite-555.md`：本口径 167 行 vs PowerShell `Get-Content` 默认编码 123 行）——差在**空行与末尾换行**的处理。**判据用的数没有定义，闸门就会因换工具而改变结论。**
>
> 口径自检（**随交付件走，目标项目可直接跑**）：`node {{paths.tools}}lib-lines.mjs --self-test`。它把"三种常见实现量出三个数"固化为常驻对照证据，并在口径被改动时报 FAIL。

## 最小留存台账（P3c）与周期时间采集（P2a）

**每链闭环时，编排者向 `{{paths.run_ledger}}` 追加一行**。字段定义以该文件的表头为准；
**结构校验**：`node {{paths.tools}}ledger-check.mjs`。

### 为什么不存"全部审计文件"

链级闭环会清理 `.dsh/tmp/` 与 `.dsh/reports/`，**证物随之消失**——实测后果：无基线、无趋势、无改进验证，且**至少 5 处文档把已不存在的审计 json 当证据引用**。

但留存全部审计文件也**已被否决**：那造成过 **83 文件 / 1212 KB** 的堆积。**最小可行形式是"每链一行摘要"**——足够支撑趋势与规则复审（P9），又不重演堆积。

### 采集什么

台账**共 11 列**，按五组：

| 字段组 | 字段 | 服务于 | 回答的问题（GQM 的 Question 层） |
|---|---|---|---|
| 标识 | 链 id / 起止 | 定位 | 这条链是什么、什么时候跑的？ |
| 档位 | A0 / A1 / A2简 / A2标准 / A2深 | 分层比较（**不跨档位比**） | 这个数字该和哪些链比？ |
| 流量 | 派发次数 / 重派次数 / 每环轮次 | **P2a 周期时间**：产出**分布**，不报均值 | 时间花在返工上还是花在推进上？ |
| 终局 | 结论（通过 / 升级用户 / 未闭环） | 趋势 | 这个档位的链通常能自己闭环吗？ |
| **失败分布** | **失败检查项的 id 分布**（如 `D8×2,D13×1`） | **P9 规则复审的输入** | 哪条规则在反复失守？ |
| **不确定性** | **`confidence`（high/medium/low）** | P8 安全通道的验收 | 报告者在什么情况下底气不足？ |
| **判据异议** | **`criterion_issue`（计次；有则记次数，无则 0）** | **P9 规则复审的输入** | 哪条判据被反复质疑、该改？ |

> **Question 层不是新指标，是指标与目的之间的那一环**（GQM：Goal → Question → Metric）。
> 上表最后一列就是它。**没有这一列，采集就退化成"先攒数、再想为什么要攒"**——
> 这正是 `criterion_issue` 采了却无处可去的原因：没人规定它回答哪个问题。
> **加的是 Question，不是新 Metric**——按 §0 原则 5，度量一旦成为目标即失效（Goodhart）。

> **完整的三层（Goal → Question → Metric）见 `_shared/metrics-gqm.md`。** 本节的最后一列是 **Question 层**；
> 那个文件补上**上位的 Goal 层**（为谁 / 为什么目的 / 从哪个视角 / 在哪个环境）。
> 按 GQM 的判据（理论报告 §5.1）**Goal 层必须在前**——「没有这一行的度量，从一开始就是无效度量」。
> **加列时必须同步改那张表**：`ledger-check.mjs` 会强制"台账每一列都能在表中找到"，找不到就判 FAIL。

> **为什么记分布而不是总数**：总数只能说"这轮不好"；**分布才能指出是哪条规则在反复失守**——也就是 P9 要删/合并/修订的那一条。

### 三条硬约束

1. **仅作诊断，不得作为考核指标**。派发次数、重派次数、轮次都属 Activity 类度量，最易 Goodhart 化（SPARK / §0 原则 5）。**它们只用来发现结构与趋势。**
2. **P2a 只报分布，不报均值**（§0 原则 8）。均值会把长尾藏起来，而长尾正是要看的。
3. **台账在产物之后写**——回执/台账**不得先于产物**（源头纪律：产物才是证物，台账只是索引）。写的时机是**链闭环、`.dsh/tmp/` 被删除之前**：先把数据摘出来，再删证物。

### 规则复审机制（P9，2026-09-18 新增）

**每 5 条链闭环触发一次规则复审**（N=5，按 `{{paths.run_ledger}}` 的数据行计数）。
**触发与召集的负责人是编排者**（不是 QA）——QA 只提供台账数据与 `criterion_issue` 记录，
编排者在第 5 条链闭环时把复审作为一条 A1 链派出；判据是台账数据行数，可机器核对。
产出一页清单，落 `{{paths.docs}}` 下的耐久位置（**不放 `.dsh/tmp/`——它会被闭环清空**）。

| 问句 | 目的 | 处置 |
|---|---|---|
| 哪条判据在最近 N 条链里**从未 FAIL**？ | 可能已无区分度 | 候选删除或降为抽样 |
| 哪条判据 FAIL 后**从未导致有意义的修改**？ | 可能只是噪声 | 候选修订 |
| 哪两条判据**总是同时 FAIL**？ | 可能是一件事被管两遍 | **候选合并** |
| 哪条规则**与其它规则冲突**？ | 调节器内部不一致 | 纠正 |
| 哪条判据的 **`criterion_issue` 次数最高**？ | 被反复质疑 | 优先复核该判据本身 |

**硬判据：每次复审必须至少删掉或合并一条规则。** 若一条都删不掉，**报告为复审机制失效**——这本身是有效结论，不是失败。

> **为什么必须有这条硬判据**：判据演进实测 **6 次全部来自事故驱动、全部是新增约束、无一次删除或合并**。按 Senge 的「成长上限」原型，规则增长带来质量提升的同时也带来负荷增长，**负荷最终成为限制**。没有可证伪的产出要求，复审就会退化成「再写一页清单」。（Schön 反思性实践——反思应是常规而非例外；双环学习。）
>
> **前两次复审的能力不同，要说清楚**：第 1 次（2026-09-18）**运行台账数据行 0 条**，因此**只能依据结构证据**（后三问），答不了前两问。这不是缺陷而是顺序——测量系统必须先于控制图可信（Shewhart / Deming）。满 5 条链后，前几问即可回答。

### 台账为空时怎么算

**空表是有效状态。** 首次建立时**无历史数据可补录**——那些数据已随闭环被清掉。**不得编造看起来合理的数字**：宁可表是空的。这本身是有效结论：**在建立台账之前，本模式对自己的运行状况是不可观测的**，所有"改进了多少"的说法都缺少可核对的基线（Shewhart / Deming：**测量系统必须先于控制图可信**）。
