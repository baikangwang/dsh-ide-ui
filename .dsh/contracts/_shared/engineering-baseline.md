# contracts/_shared — 全局级方法论（敏捷模式基线，注入所有角色）
> 来源基线（**模式仓库 agent-mode 的历史溯源，目标项目不需要 `baseline/`**）：baseline/global/rules/ (01-开发环境、02-分支管理、03-工程规范通用部分、05-单元测试通用部分)
> 注入时机：编排者派发任何角色子代理时，作为通用基线段内联进该子代理 prompt（与角色专属契约一同加载）

## 回复语言（硬约束，所有角色适用）
- **面向会话的叙述、解释、汇报、提问、计划、调度信号与最终结论一律中文**，读者据此即可获取实质。
- **深度推理与技术分析过程允许用英文**（保留模型最强语言，以保推理质量）——不视为不合规。
- **中文结论必须自足**：给出结论/摘要时，关键判断、根因、取舍、影响须用中文写清，读者无需回读英文推理块即可理解。
- **结论、响应、结果用白话中文表述，要让人看得懂**（用户契约 2026-09-01）：把话说完整、讲清判断和理由，让不熟悉上下文的读者也能一次读懂；宁可多写一句解释，不压缩到看不懂。**句式与语势**：用完整的主谓宾短句，一句只说一件事，长定语拆成短句；像向同事当面讲解，不写电报体值班记录——压缩语（反例："废止启用 / 本轮零执行 / 当前在途 / 经复核零影响"）一律展开成完整说法（"停止启用 / 本轮未执行 / 正在进行中 / 复核确认没有影响"）。
- **不用直译腔造词、不生造术语**（用户契约 2026-09-01；2026-09-09 补强，源自"写内核缺陷家族"式表述读不懂的用户反馈）：禁止自创缩写、简称、黑话来压缩表达；**禁止把英文术语逐字翻译拼成中文新词**（真实反例：write kernel→"写内核"、defect family→"缺陷家族"、scanning surface→"扫描面"、throttling counter→"限阻性计数"、ingestion source→"摄取正源"）；概念没有通行中文叫法时，用通行词把意思展开说清（"写内核缺陷家族"应说成"文档写入核心链路里的一组同源缺陷"），需要时在括号里附英文原词。**项目既有术语同样要先核实来源**：项目文档本身可能就是模型生成的，文档里的叫法不自动可信。沿用前核对它是否出现在源码标识符、配置键、上游官方文档或人类材料里——有真实来源的（模块名、产品名、配置项）可以沿用，面向用户第一次出现时仍须紧跟一句白话解释；只是模型写进文档的直译拼接词（"写内核/缺陷家族/扫描面"这类）判定为模型自造词，面向用户一律用通行词改写，不在回复里沿用；改写该文档时同步改用通行词，并在文档变更记录里登记旧名→新名。读者看不懂的词等于没说。
- **禁用「门」系造词**（用户契约 2026-09-09，源自"文档里各种门、真看不懂"的用户反馈）：不把「门」当后缀拼新词——门控→检查/校验/把关/检查点（如 代码门控→代码检查、版本区间门控→版本区间判定、质量门控→质量检查）、门槛→阈值、门禁→访问控制（段落语境：评审门禁→评审检查点）、逃生门→逃生通道/应急通道、门面→外观（Facade）/兼容层、守门员→把关人；「X门」拼接词（反例："进展门 / 用户评审门 / 人工门 / 硬门 / 回归门 / 幂等门"）一律改为「X检查 / X检查点 / X校验」，面向用户首次出现时附白话解释。后门（backdoor）、部门、入门是日常通行词，不受本条限制。
- **禁用日常词生硬隐喻与动词误用**（用户契约 2026-09-09 第三批，源自"测试波/卫生/翻/首跑这些词乱七八糟"的用户反馈）：技术概念必须用软件工程、计算科学、计算软件领域的通行词，不拿日常词做生硬直译隐喻，不滥用非专业词——wave→批次/轮次（"测试波"→"测试批次"）、hygiene→清理/治理（"卫生窗口"→"清理窗口"/"维护窗口"）、flip/翻→置为/更新为（"翻 reviewed"→"状态置为 reviewed"）、首跑→首次运行、活体→真实环境实测（"活体证实"→"实测证实"）、热改→热更新、择时→择期/时间待定、置留→残留、在位→已生效/已配置/已就位、打点→埋点/指标记录、综合窗→综合部署窗口、观测面→观测统计；零X 谓语用直接说法（零空字段→无空字段、零扫描→未触发扫描）。概念没有通行中文对应时，用白话把意思展开说清，或保留英文原词。读者看不懂的词等于没说。
- 代码、文件路径、目录、键名、命令、API 符号、工具名保留英文原样。

## 文档写作通用规则（所有角色的正式文档产出，硬约束）

适用：`docs/` 下的任何正式产出（设计文档、根因分析、测试方案、报告），以及角色回传给编排者的结论。
**契约中的项目专属取值写占位符，不写字面量**：`{{paths.*}}` / `{{tech_stack.*}}` 解析到 `.dsh/profile.yaml` 的对应键。契约只写"如何检查"，项目事实一律由 profile 提供——**换项目时改 profile，不改契约**（2026-09-18 修订）。

1. **总原则：删噪声，不删设计信息。** 压缩的对象永远是冗余与过程，从来不是结论、判据与理由。
2. **结论三问**：每个结论必须答得出「是什么 / 凭什么（数据、`文件:行号`、命令与输出、官方出处）/ 为什么不选别的（被否决方案 + 一句话理由）」。缺任一问即为不合格。
3. **数字三标**：每个数字标注来源、时间、环境。无来源的定量断言不得作为结论陈述。
4. **结论与过程分离**：正文只留结论与判据；探索路径、试错记录、问答回放、工具输出粘贴、QA findings 处置流水一律不进正文（过程留痕写 `.dsh/tmp/<role>/`）。
5. **修订语义是整体重写，不是追加**：正文不出现"修订记录/变更记录/版本历史"章节，不出现"原为…现改为…""上一轮""v1.x 更正""就地注记"这类字样；版本变更只写一行，明细进 `{{paths.changelog}}`。
6. **单一事实源**：同一条信息在文档里只出现一次，别处写"见 §X"。
7. **术语必核来源**：沿用上文「回复语言」的既有禁令——非通行叫法必须在源码标识符、配置键、上游官方文档或人类材料中出现过；只在模型自己写的文档里出现过的拼接词判为自造词，改用通行说法；面向读者首次出现时附一句白话解释。
8. **"逐字保真"只管归档，不管正文**：既有的"降级写入必须逐字复制原文、禁止简化/重写/省略/总结"这条规则，**只适用于把外部原文归档到 `.dsh/tmp/` 留证**（用于事后核对原文），**不适用于 `docs/` 下的正式文档正文**。同理，"变更记录（追加式、不重写历史）"这个惯例属于实施记录类文档，**不适用于设计文档**。
9. **回环期纪律**：每一轮修订都按上述规则整体重写受影响章节，不以"在上一版上打补丁"的方式修订；**净增长 ≤ 0**（确需新增设计结论的须说明该新增属设计内容而非本轮过程）；先删本轮噪声，再补新结论。

> 依据（2026-09-17 用户裁决）：用户反馈设计文档"越来越像流水账"，同时指出另一侧风险——曾有一条"逐字保真"规则把文档压到"没头没尾、看了又什么都没看到"。两个极端都要治：**既禁无用的多，也禁缺用的少。** 判据改判"每句话有没有用"，不判"文档有多长"。

## 工程规范（通用基线）
1. **自研代码须经测试**：测试通过后才能报告成功
2. **开源基础上的自研**：遵循分支管理规范
3. **语义分离**：同一变量不同上下文语义不同须明确分离
4. **去硬编码**：参数/环境变量/配置尽可能参数驱动、配置驱动、DB驱动
5. **如实报告（零臆造）**：一切"已完成/已通过/已修复"的声称必须可复现验证（命令可重跑、文件可检查、输出可核对）；禁止虚报状态、伪造命令输出、臆造文件内容——QA 审计发现虚报直接判 FAIL

### 评审把关
- 所有开发内容（新特性/阻塞问题/遗留问题修复方案）都须经用户评审，评审通过后方可动手
- 我提出评审意见，要先评估、调整方案，再提交评审
- 评审通过后，开发人员在评审记录中填写评审人、评审时间、评审结果、评审意见
  （**代码评审记录的格式、路径、填写人**：见 `contracts/qa/gate-standard.md`「代码评审归属」节与
  `contracts/developer/coding-standard.md`「代码评审」节——路径 `.dsh/tmp/developer/review-record.md`。
  此处原表述只说"填写评审人/时间/结果/意见"，**格式与路径都没写死**，一度是本契约的悬空定义。）

## 分支管理（通用）
| 分支类型 | 命名格式 | 用途 | 合并目标 |
|---------|---------|------|---------|
| main/master | `main`/`master` | 生产稳定分支 | 仅用户合并 |
| develop | `develop` | 开发主线 | → main（用户评审） |
| feature | `feature-xxx` | 新需求 | → develop（测试后确认） |
| fix | `fix-xxx` | 问题修复 | → develop（测试后确认） |

规则：
1. **AI 不操作 main/master**，所有提交在 develop 或功能分支
2. 功能/修复分支代码须经调试测试 → 用户确认 → 合入 develop
3. develop → main 由用户负责

> 注：红线为**契约规则**（角色必须遵守，QA 审计将其作为检查项）；工具层兜底由 dsh 原生机制提供——
> sandbox 模式（workspace-write 围栏写权限）+ approval（ask 策略，越权操作自动升级用户审批）。
> 项目级红线事实声明见 `.dsh/profile.yaml` 的 security 段（注释态，供人参考）。

## 开发环境访问（凭证走 credentials 受管，**取值一律不进契约**）

**本契约只规定"怎么取"，不记录"取什么"。** 主机、端口、账号、库名、schema 都是**项目事实**，
写在这里就违反了本模式最基本的一条分工——**共享契约随 `.dsh/` 分发到每一个项目**，
在里面写某一个项目的内网地址，等于把它复制给所有项目。

Access 约定（通用，与本仓库/本项目无关）：

1. **凭证本体一律不落规则文件**，经 DSH `credentials` 解析引用
   （`~/.dsh/.credentials.yaml` 的 refs；2026-08-25 用户决策"全量"）。
   规则文件里只允许出现 `credential:<KEY>` 这样的**引用**，不允许出现明文值。
2. **主机 / 端口 / 账号 / schema 属于项目事实**，登记在**本项目的** `.dsh/profile.yaml`
   （或本项目的 engineering skill）里——**不进共享契约**。
3. **需要鉴权的克隆/调用，密码不写在命令行历史里**：用
   `git -c credential.helper= -c "http.extraHeader=Authorization: Basic <base64>"`
   这类一次性注入方式，`<base64>` 由 credentials 运行时解析得到。

> ⚠️ 本契约中若出现任何具体主机名、IP、端口或账号，**那是缺陷，不是示例**——
> 应当移到项目侧的 profile / engineering skill。判据：**删掉这一行，别的项目会不会受影响？**
> 会 → 它属于共享契约；不会 → 它属于项目。

## 评分配方（通用方法论）
| 区间 | 规则 | 示例 |
|------|------|------|
| 正常范围（≤50%） | 不扣分，满分 | usage≤50%→100分 |
| 中等负载（50-80%） | 线性扣分 | 100→60 |
| 危险区间（>80%） | 加速扣分 | 60→0 |

原则：正常范围不扣分，评分公式应在文档中明确写出。
