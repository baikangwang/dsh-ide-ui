# contracts/_shared — workspace 契约结构通用约定（两模式共用唯一正本）

> 属性：**随 `.dsh/` 交付**。本文件写**两种模式完全相同**的 workspace 约定。
> 各模式的 `contracts/README.md` 只保留自己的**目录树**与本模式的角色名，其余指向本文件。
>
> **为什么单独一份**：这些约定原先在敏捷与调研两份 `README.md` 里各写一遍，
> 实测调研侧**整节缺失**——两态划分、交付单位、能力脚本位置、角色切分依据、所有权表、
> 回环控制律的唯一事实源，六节全无（当时测得两份 README 的四个同名节**零节逐字节相同**）。
>
> **角色名怎么处理**：本文件按**职责**表述，并在括号里给出两模式的角色名。
> 这样同一张表对两种模式都成立，不必各写一份。

## 目录契约：闭环白名单是**两态划分**（2026-09-18 修订，同日由三态改回两态）

> **第一次修订原因**：原白名单只有"清理"与"不清理"两栏，导致三个同源缺陷——能力脚本目录在哪一栏都不在、`.dsh/archive/` 无处声明、根目录出现 13 个 `.dsh-tmp-*` 逃逸件。根因是**目录归属没有单一事实源**。故改为三态，并要求**完整性**。
>
> **第二次修订原因（2026-09-18 用户裁决）**：三态里的第三态 `.dsh/archive/` 被论证为**有害**。它的规则是"闭环只移动不删除"，理由是"本仓库不是 git 仓库"。实测该规则被执行成垃圾堆积，**且堆在交付件内部**：`.dsh/archive/` 长到 **1341 文件 / 23.9 MB，占整个 `.dsh/` 的 97%**。交付单位既然是 `.dsh/`，**每个接入的项目都会收到这 23.9 MB**。现删除该态：**闭环直接删除临时产物**，需要留的证据在删除**之前**摘进正式产出。详见 `.dsh/README.md`「两态划分」。

| 态 | 路径 | 闭环动作 |
|---|---|---|
| **正式产出**（长存，参与编排） | `{{paths.source}}`、`{{paths.docs}}`、`.dsh/{profile.yaml, contracts, skills, tools}` | **绝不清理** |
| **临时产物**（删除） | `.dsh/tmp/**`、`.dsh/reports/**` | **链级闭环直接删除** |

**两条硬要求**：

1. **完整性**：`.dsh/` 下的每一个路径必须**恰好落进上述两态之一**。新增目录时同步更新本表——**未声明的目录是缺陷，不是自由**。
2. **先摘录，后删除**：闭环删除临时产物之前，把需要留的证据（运行台账行、审计结论、数值）**写进正式产出**。顺序不能反——**先删后摘等于把证据弄丢**。

> **为什么推翻"只移动不删除"**：它把"不可恢复"当成了保留的理由。但临时产物**按定义就是过程证物**——结论已经进了正式产出与运行台账，留着的是**副本**不是证据；而且**没有任何消费者**：没有角色读它、没有契约引用它的内容、没人会去看它。"不可恢复"只说明**删除要谨慎**，不说明**必须永久搬运**。

**临时产物一律写入 `.dsh/tmp/<role>/` 或 `.dsh/reports/`**，按目录收敛清理，**禁止硬编码文件名**，**禁止写到仓库根**。

## 交付单位是 `.dsh/` + `.env`（2026-09-18 修订）

**模式交付给实际项目的东西，只有 `.dsh/` 与 `.env` 两样。** 仓库根的 `docs/` 与 `tools/` **不是交付件**——它们是模式自身的开发工作区。

由此推出两条硬规则：

1. **凡"运行模式所需要的资产"都必须在 `.dsh/` 内**（契约 / skill / 工具三类之一）。落在 `docs/` 或 `tools/` 就等于**其他项目拿不到**，只能跨工作区读取——那是不可能的。
2. **`.dsh/` 必须自包含**：把本仓库的 `.dsh/` 整体拷到目标项目，就应当得到一个可运行的模式。

> **此前违反这两条的实例**：能力脚本正本原先放在仓库根 `tools/`，于是"拷 `.dsh/`"得到的交付件里**没有工具**，只能靠模式仓库的分发器另行推送；`docs/06`（写法指南样例）、`docs/07`（B 类清洗方法）、`docs/08`（A 类重写派发模板）都是运行时要用的资产却躺在 `docs/` 下。**均已迁入 `.dsh/`。**

## 能力脚本位置（2026-09-18 修订）

**正本在 `.dsh/tools/`，随 `.dsh/` 整体交付。**

> **为什么这里不给分发器的文件名**：它是**模式仓库的运维脚本，不随 `.dsh/` 交付**。契约（交付件）里写一个拿不到的文件名，读者会去找它而找不到——那正是本节要堵的"悬空引用"。**凡是"只在模式仓库存在"的东西，契约里一律只描述职责，不写路径。** 其他项目的 `.dsh/tools/` 是由**模式仓库的分发器**生成的**副本**（带两行副本头）。

| 角色 | 路径 | 内容 |
|---|---|---|
| 本仓库 `.dsh/tools/` | **正本** | 无副本头 |
| 其他项目 `.dsh/tools/` | 副本 | 带副本头（`正本：agent-mode 仓库 .dsh/tools/<名>`） |

分发器 **显式排除正本所在仓库自己的 `.dsh/tools/`**（那是正本，不是副本）。

> **此前三处引用悬空的真正成因**：契约与预设写死 `.dsh/tools/`，而正本当时在 `tools/`，源仓库**没有**该目录；分发器里"排除正本所在仓库"这条例外**未被记录**。**把正本搬进 `.dsh/tools/` 后，此特例自然消失，`paths.tools` 对所有项目取值一致。**

## 层内三种形态的分工（骨架 / 契约 / skill）

| 形态 | 载体 | 性质 | 加载方式 | 何时用 |
|------|------|------|---------|--------|
| **骨架** | `.dsh/profile.yaml` | 声明式**数据** | 编排者会话开始读取 tech_stack/deploy 骨架作为项目事实 | 可结构化的技术事实：语言/构建/包结构/端口/部署骨架/安全红线 |
| **契约** | `.dsh/contracts/<role>/*.md` | 结构化**文本** | 派发时把契约清单写进派发提示词，子代理开工前自读（硬性开工指令） | 可叙事、需模型理解的契约：设计模板、编码约束、检查标准、语义约定 |
| **skill** | `.dsh/skills/{project}-*.md` | 项目级 **skill** | 按需 skill() 拉取（官方发现根 `.dsh/skills`） | 大体积低频参考知识：工程规范全文、部署 SOP、测试方法论、**模式能力脚本的用法** |

> **这三种形态都在 C 层（`.dsh/`）内部。** A/B/C 三个字母已专指三层部署架构（A 通用引擎 / B 入口预设 / C workspace = `.dsh/` + `.env`），见 `.dsh/README.md`「三层架构，以及 A/B/C 是*哪*三层」一节。层内三样不再用字母，以免与层级混淆（2026-09-20）。

**能力脚本（`{{paths.tools}}`）的三分法**（2026-09-18 确立）：**触发规则 → 契约**；**用法说明 → skill**；**脚本本体 → 留在 `{{paths.tools}}`，不搬进 skill**。搬进 skill 会与分发器形成**第二套副本**，即该脚本自己警告的"副本漂移"事故。

## 按角色 × 按 workspace 加载

- **按项目**：编排者读取 `.dsh/profile.yaml` → 项目骨架/红线事实（tech_stack/deploy/security）。
- **按角色**：编排者调度到某角色时，把该角色 `.dsh/contracts/<role>/` + `_shared` 基线的文件清单写进派发提示词并附硬性开工指令，由 subagent 开工前自读；未调度角色不加载 → 上下文受控、token 不浪费（2026-09-09 用户决策：子代理自读替代编排者读+内联）。
- **`_shared` 基线与 QA 通用契约**：`.dsh/contracts/_shared/` 下的文件是**两模式共用的唯一正本**；其中 `qa-common.md` 只在派发 QA 时加入清单，其余（`engineering-rules.md` 等）**所有角色必读**。

## 回环控制律的唯一事实源

**回环的停止条件只由编排者（preset persona）定义。** 契约只描述"发现什么"，**不描述"何时停"**——契约中不得出现任何重派次数、重试上限或停止条件表述。

> **此前同一控制律在三处各说各话**：QA 契约"回环不设固定次数上限"、编排者"最多重派 2 次"、测试契约"retry≤2"。**调节器需要单一控制律；两套互斥控制律同时存在，等于没有确定策略。**
>
> **调研侧曾长期未对齐**：调研 `qa/gate-standard.md` 直到 2026-09-20 仍写着"回环不设固定次数上限"与"第三个停止条件（编排者立即停止回环）"，与本节冲突。**已一并对齐。**

## 运行台账与度量（GQM）——**编排者的职责，不是 QA 的**

**每链闭环时，编排者向 `{{paths.run_ledger}}` 追加一行**（字段定义见 `_shared/qa-common.md`「最小留存台账」节；
结构校验：`node {{paths.tools}}ledger-check.mjs`）。**时机在 `.dsh/tmp/` 被删除之前**——先摘录，后删除。

> **为什么必须写在这里（2026-09-20 补）**：台账的写入职责原先**只写在 `_shared/qa-common.md` 里**，
> 而该文件按上面的加载规则**只在派发 QA 时加入清单**——于是**编排者从自己的契约里读不到"有台账这回事"**。
> 一份被指派了职责、却读不到职责说明的角色，不会去履行它。**职责说明必须落在承担者的必读面内。**

**度量与目标的连接（GQM）见 `_shared/metrics-gqm.md`**（Goal → Question → Metric 三层）。
台账的**每一列**都必须在其中找到它回答的 Question；`ledger-check.mjs` 会强制这一点，找不到即 FAIL。
**新增或修改台账列之前先读它**——按 GQM 的判据，无 Goal 层的度量从一开始就是无效度量。

- **读台账按 Question 组织，不按列顺序读**（列顺序是存储格式，不是思考顺序）。
- **G1-Q1（连续两轮零修复 → 停止回环）** 是已有控制律的度量表述；回环停点的唯一事实源见上一节。

## 角色切分依据（2026-09-18 补写）

**切分依据 = 产出物所有权互斥 + 活动阶段。**

- **所有权互斥**：两个角色不同时拥有同一类产出物的写权。
- **活动阶段**：设计 / 实现 / 验证 / 交付 / 把关 五个阶段各设一个角色。

**它不是认知负荷切分。** 认知负荷理论用于设计团队边界**未找到对照实验**，属外推，不作为依据。可用口径仅是操作性的：*若一次注入的规则无法在单次判断中全部用完，即属外在负荷，应继续切分*。

**角色数量上限未声明**。两模式的当前编制：

| 模式 | 常驻编排者 | 专业角色 |
|---|---|---|
| 敏捷 | 1 | 架构师 / 开发专家 / 测试专家 / 部署专家 / QA |
| 调研 | 1 | 首席分析师 / 调研专家 / 环境运维专家 / 验证专家 / QA（+ A1 链的实施角色） |

**任何新增角色的提议须先回答：为什么此前被主动削减的角色不该回来。**

## 新项目接入步骤（零代码）

1. 在 workspace 的 `.dsh/` 下新建 `profile.yaml`（声明语言/构建/包结构/部署骨架/安全红线）。
2. 可选的：`.dsh/contracts/<role>/` 放该项目特有的角色契约；没有就不建（用通用契约）。
3. 可选的：`.dsh/skills/` 放该项目大知识库（需 frontmatter：`name`/`description`）；没有就不建。
4. 跑**就绪检查**（引用完整性 + 环境 + persona + preset 健康），任一不过即阻断。
5. 完成——会话选择对应模式即自动生效。无需改引擎、无需写代码。

> **契约中不得出现本仓库专属路径字面量。** 项目相关的取值一律由 `profile.yaml` 提供；**填不上就删掉整句，不留指向空处的路径**——悬空引用正是"填不上却留着"的产物。

> 每个契约文件顶部保留 `来源基线` 注释，指向**模式仓库**的 `baseline/` 备份，保证可追溯与审计。
> **该路径只存在于模式仓库 agent-mode，不是交付件**——注释现已自带这一作用域，免得消费项目去找一个不存在的 `baseline/`。
