# contracts/_shared — workspace 契约结构通用约定（两模式共用唯一正本）

> 属性：**随 `.dsh/` 交付**。本文件写**两种模式完全相同**的 workspace 约定。
> 各模式的 `contracts/README.md` 只保留自己的**目录树**与本模式的角色名，其余指向本文件。
>
> **角色名读法**：本文件按**职责**表述，括号内给出两模式的角色名——同一张表对两种模式都成立。

## 目录契约：闭环白名单是**两态划分**

| 态 | 路径 | 闭环动作 |
|---|---|---|
| **正式产出**（长存，参与编排） | `{{paths.source}}`、`{{paths.docs}}`、`.dsh/{profile.yaml, contracts, skills, tools}` | **绝不清理** |
| **临时产物**（删除） | `.dsh/tmp/**`、`.dsh/reports/**` | **链级闭环直接删除** |

**两条硬要求**：

1. **完整性**：`.dsh/` 下的每一个路径必须**恰好落进上述两态之一**。新增目录时同步更新本表——**未声明的目录是缺陷，不是自由**。
2. **先摘录，后删除**：闭环删除临时产物之前，把需要留的证据（运行台账行、审计结论、数值）**写进正式产出**。顺序不能反——**先删后摘等于把证据弄丢**。

**临时产物一律写入 `.dsh/tmp/<role>/` 或 `.dsh/reports/`**，按目录收敛清理，**禁止硬编码文件名**，**禁止写到仓库根**。

## 交付单位是 `.dsh/` + `.env`

**模式交付给实际项目的东西，只有 `.dsh/` 与 `.env` 两样。**

由此推出两条硬规则：

1. **凡"运行模式所需要的资产"都必须在 `.dsh/` 内**（契约 / skill / 工具三类之一）——落在别处就等于**其他项目拿不到**。
2. **`.dsh/` 必须自包含**：把模式仓库的 `.dsh/` 整体拷到目标项目，就应当得到一个可运行的模式。

### 三条配套硬约束

1. **官方发现根只有一个，不能改。** 模式预设对 `.dsh/` 的发现走 DSH 官方的 workspace 约定（见 `.dsh/contracts/README.md` 的目录约定与预设的加载段）。
   **`.dsh/contracts/`、`.dsh/skills/`、`.dsh/tools/` 三个子目录是官方发现根**——往里加文件会被自动发现；**另立一个平级目录不会被发现**。
2. **新增或改名 `profile.yaml` / `contracts/` / `reports/` 时，必须同时改预设**——这三个路径由**预设 persona 写死**，DSH 引擎不读它们。
   新增任何"约定式文件/目录"前，先答一句「**除了我，还有谁按这个路径去读它？**」——答不出来就不要建。
3. **`.env` 必须留在项目根**，不得挪进 `.dsh/`——DSH 引擎按**工作区根**查找它。

## 能力脚本位置

**正本在 `.dsh/tools/`，随 `.dsh/` 整体交付。**

> **凡是"只在模式仓库存在"的东西，契约里一律只描述职责，不写路径**——写一个拿不到的文件名，读者会去找它而找不到，那正是本节要堵的"悬空引用"。分发器本身是模式仓库的运维脚本，不随 `.dsh/` 交付。 其他项目的 `.dsh/tools/` 是由**模式仓库的分发器**生成的**副本**（带两行副本头）。

| 角色 | 路径 | 内容 |
|---|---|---|
| 模式仓库 `.dsh/tools/` | **正本** | 无副本头 |
| 其他项目 `.dsh/tools/` | 副本 | 带副本头（`正本：agent-mode 仓库 .dsh/tools/<名>`） |

分发器 **显式排除正本所在仓库自己的 `.dsh/tools/`**（那是正本，不是副本）。

## 层内三种形态的分工（骨架 / 契约 / skill）

| 形态 | 载体 | 性质 | 加载方式 | 何时用 |
|------|------|------|---------|--------|
| **骨架** | `.dsh/profile.yaml` | 声明式**数据** | 编排者会话开始读取 tech_stack/deploy 骨架作为项目事实 | 可结构化的技术事实：语言/构建/包结构/端口/部署骨架/安全红线 |
| **契约** | `.dsh/contracts/<role>/*.md` | 结构化**文本** | 派发时把契约清单写进派发提示词，子代理开工前自读（硬性开工指令） | 可叙事、需模型理解的契约：设计模板、编码约束、检查标准、语义约定 |
| **skill** | `.dsh/skills/{project}-*.md` | 项目级 **skill** | 按需 skill() 拉取（官方发现根 `.dsh/skills`） | 大体积低频参考知识：工程规范全文、部署 SOP、测试方法论、**模式能力脚本的用法** |


**能力脚本（`{{paths.tools}}`）的三分法**：**触发规则 → 契约**；**用法说明 → skill**；**脚本本体 → 留在 `{{paths.tools}}`，不搬进 skill**。搬进 skill 会与分发器形成**第二套副本**，即该脚本自己警告的"副本漂移"事故。

## 按角色 × 按 workspace 加载

- **按项目**：编排者读取 `.dsh/profile.yaml` → 项目骨架/红线事实（tech_stack/deploy/security）。
- **按角色**：编排者调度到某角色时，把该角色 `.dsh/contracts/<role>/` + `_shared` 基线的文件清单写进派发提示词并附硬性开工指令，由 subagent 开工前自读；未调度角色不加载 → 上下文受控、token 不浪费（用户决策：子代理自读替代编排者读+内联）。
- **`_shared` 基线的必读面按文件定，不按目录定**：`.dsh/contracts/_shared/` 下的文件是**两模式共用的唯一正本**，但**不是每份都全员必读**——必读面就是"**这个角色在链里用得到的那几份**"。

| 文件 | 谁必读 | 承担者与场合 |
|---|---|---|
| `contract-conventions.md` | **所有角色** | 两态划分 / 交付单位 / 所有权表 / 回环控制律——每个角色都要知道自己产出落在哪一态、谁能写什么 |
| `engineering-rules.md` | **所有角色** | 回复语言 / 文档写作通用规则 / 工程规范 / 评审把关 / 分支管理 / 开发环境访问 / 评分配方 |
| `evidence-rules.md` | **写作角色 + QA**（敏捷=架构师；调研=首席分析师/调研专家/验证专家） | 引用外部结论的纪律（档位 / 外推声明 / 边界表 / 逐条禁令）与改进提案的纪律。**条件性必读**：任何角色要提效率或过程改进提案时先读它 |
| `qa-common.md` | **仅 QA** | QA 自己的检查项正本 |
| `research-rules.md`（仅调研模式） | **调研侧所有角色** | 只写调研相对敏捷的差异，与 `engineering-rules.md` 同读 |
| `metrics-gqm.md` | **编排者** | 台账 12 列与 GQM 的对应（`ledger-check.mjs` 按它强制） |

- **这张表是声明，预设的派发清单是实现。** 真正决定"谁读什么"的是两份预设里那段「按角色契约加载」——**改一处就必须改另一处**。
  **判据**：给某角色加一份必读文件前，先答「**它里面哪一条会改变这个角色本轮的行为？**」
  答不出就是往他的 context 里塞噪声——**这与「职责说明必须落在承担者的必读面内」是同一枚硬币的两面**：
  前者防"该读的没读到"，后者防"不该读的占了他的预算"。
- ⚠️ **已知落差（待办）**：`metrics-gqm.md` **不在任何派发清单里**，只能靠本文档的指针可达；
  而两份预设描述 `contract-conventions.md` 时都写着它含「运行台账与度量（GQM）」——**那句话与实际不符**（GQM 在独立文件里）。

## 回环控制律的唯一事实源

**回环的停止条件只由编排者（preset persona）定义。** 契约只描述"发现什么"，**不描述"何时停"**——契约中不得出现任何重派次数、重试上限或停止条件表述。

> 调节器需要**单一控制律**；两套互斥控制律同时存在，等于没有确定策略。

## 运行台账与度量（GQM）——**编排者的职责，不是 QA 的**

**每链闭环时，编排者向 `{{paths.run_ledger}}` 追加一行**（字段定义见 `_shared/qa-common.md`「最小留存台账」节；
结构校验：`node {{paths.tools}}ledger-check.mjs`）。**时机在 `.dsh/tmp/` 被删除之前**——先摘录，后删除。

> **职责说明必须落在承担者的必读面内**——一份被指派了职责、却读不到职责说明的角色，不会去履行它。

**度量与目标的连接（GQM）见 `_shared/metrics-gqm.md`**（Goal → Question → Metric 三层）。
台账的**每一列**都必须在其中找到它回答的 Question；`ledger-check.mjs` 会强制这一点，找不到即 FAIL。
**新增或修改台账列之前先读它**——按 GQM 的判据，无 Goal 层的度量从一开始就是无效度量。

- **读台账按 Question 组织，不按列顺序读**（列顺序是存储格式，不是思考顺序）。
- **G1-Q1（连续两轮零修复 → 停止回环）** 是已有控制律的度量表述；回环停点的唯一事实源见上一节。

## 行数口径（唯一定义处）

**行数 = UTF-8 解码后按 `\n` 切分得到的段数**；空行照数；末尾换行不额外算一段；`\r\n` 先归一为 `\n`。
字节数 = UTF-8 编码后的字节长度。**实现收敛到 `{{paths.tools}}lib-lines.mjs` 的 `countLines()` / `measure()`——任何工具要行数必须 import 它，不得自行实现。**

> **判据用的数没有定义，闸门就会因换工具而改变结论**——同一份文件在 Python `splitlines()` /
> Node `split('\n')` / PowerShell `Measure-Object -Line` 下会量出**三个不同的行数**，
> 于是「净增长 ≤ 0」与 `CONTROL_LOSS` 都会**因为换了工具而改变结论**。这是判据结构缺陷，不是实现 bug。
>
> 口径自检（**随交付件走，目标项目可直接跑**）：`node {{paths.tools}}lib-lines.mjs --self-test`
> 与 `node .dsh/tests/lib-lines-check.mjs`。前者把"三种常见实现量出三个数"固化为常驻对照证据，
> 后者把本模式的取值固化在测试里；口径被改动即报 FAIL。

**谁用**：架构师与分析师（改文档时要控 `净增长 ≤ 0`）、QA（要数行数与痕迹命中数）。**三方读同一份，不得各自留一份。**

## 正式产出的回环纪律（正本）

> **承担者**：`docs/**` 正式文档的所有者是**写作角色**（敏捷=架构师 / 调研=首席分析师，见「所有权表」）；
> QA 按本节数数并判 FAIL。**其余角色的产物不在本节管辖内。**
> 角色契约**只写"见本节"，不重复抄写**——两处各存一份就会漂（本模式实测漂过）。

**文档/报告永久代表「当前正确的那一版」。** 每一轮修订按此执行：

1. 读一遍现有文档全文，确认当前正确状态
2. **整体重写受影响的章节**：把新结论直接写进对应章节的最终形态，不保留旧结论、不留订正注记
3. 同步订正连带影响的章节（改了接口/结论就改实施清单、摘要、反证清单与后续行动），不留"待同步"
4. **全篇自洽复检**：以"没读过旧版的人"的视角通读，确认无旧版残留、无前后矛盾
5. 在 `{{paths.changelog}}` 加一行（版本 / 日期 / 结论变化摘要 ≤1 行）
6. 旧版本对照物放 `.dsh/tmp/<本角色>/`（供 QA 核对"是否真的改对了"），随闭环清理

**正文中不允许出现**（QA 会逐条检索并判 FAIL）：

- 记录本文档自身修订史的章节（无论标题怎么写）
- 新旧对照、引述往轮 QA 判定、就地补写的注记、以版本号标注的订正——这类字样
- 被改掉的旧结论、旧命令、旧判据

**回环期纪律（每轮重新施加，防止随轮次失控）**
回环里**规则不会自动保持**：第 3 轮时首轮的准则已经滑出注意力，而"打补丁"是最省事的动作。所以每一轮重派都要重新施加：

- **净增长 ≤ 0**：本轮修订后的行数与字节数不得超过上一轮。确需新增**本轮结论**的（首轮遗漏、用户扩范围），必须在正文说明该新增属**结论**而非本轮过程；**先删本轮噪声，再补新结论**
- **全篇自洽复检**：改完通读一遍，确认没有前后矛盾——"只改点名的几处、不做全篇复查"正是上一轮修订引入新矛盾的来源
- **QA 每轮记录三个数**（行数 / 字节数 / 修订痕迹命中数；口径见上一节）并与上一轮对比；出现"净增长 + 新增修订痕迹 + 未修复任何上一轮 FAIL"三者同时成立 → 编排者停止回环并升级用户裁决，不继续修订

> 边界：**"不许变长"拦的是过程沉积，不是结论生长。** 首轮漏了一个证据源或一个子问题时报告当然该变长，要的是说清新增长的是结论，而不是这轮的经过。

## 角色切分依据

**切分依据 = 产出物所有权互斥 + 活动阶段**：两个角色不同时拥有同一类产出物的写权；设计 / 实现 / 验证 / 交付 / 把关 五个阶段各设一个角色。

**认知负荷理论不作为切分依据**（它用于团队边界**未找到对照实验**）。可用口径仅是操作性的：*若一次注入的规则无法在单次判断中全部用完，即属外在负荷，应继续切分*。

### 改动角色划分或检查项时的四条硬要求

1. **举证材料是「缺陷类型覆盖率 N vs M」**——N = 该角色需识别的缺陷类型数，M = 现行判定规则实际覆盖的类型数。**报数，不报理论名字**；该覆盖率写进 QA 审计的 `coverage` 字段（见 `_shared/qa-common.md`）。
2. **改角色划分按架构决策评审**，不得当成"调一下流程配置"顺手改。
3. **新增角色必须同时回答两问**，任一答不出则**不予设立**：
   - 它靠什么**感知外部变化**（契约变化、下游消费者）？
   - 它**什么时候升级为人工裁决**？
4. **新增判据同样补出它的升级条件**（既有实例：`qa/gate-standard.md` 的 `CONTROL_LOSS`）。

### 「通信结构」的抓手就三条——改这三条就是改架构

| 抓手 | 问句 |
|---|---|
| **谁能读谁的产物** | 角色 A 的产出，角色 B 有没有读取权限/加载路径？ |
| **谁能触发谁的派发** | 角色 A 能不能直接让角色 B 开工，还是必须经过编排者？ |
| **谁的结论能阻断谁** | 角色 A 的判定能不能拦住角色 B 的交付？ |

**本模式是星形拓扑**：sibling 角色之间不互发消息，**编排者是唯一枢纽**——结果一律回报编排者，不得直接找其他角色。

## 所有权表（每个路径**恰好一个**所有者）

> **按职责表述**，括号内给出两模式的角色名。标「—」表示该产出物在该模式下不存在。

| 产出物 | 所有者 | 说明 |
|---|---|---|
| `docs/**` 正式文档 | **写作角色**（敏捷=架构师 / 调研=首席分析师） | 既有 |
| `.dsh/contracts/**` | **写作角色** | 判据与契约的**修改/维护**归属 |
| `.dsh/profile.yaml` | **写作角色** | 项目事实声明 |
| `.dsh/skills/**` | **写作角色** | 项目级知识资产 |
| `.dsh/tools/**` | **写作角色** | 与引用它们的契约同主，避免"引用者与被引用者不同主" |
| 生产代码目录（`paths.source`） | **实施角色**（敏捷=开发专家 / 调研=实施角色） | 目录名由 `profile.yaml` 声明 |
| 构建配置（如 `build.gradle` / `package.json` / `Makefile`） | **实施角色** | 构建命令被多份契约引用；调研模式多数链不改代码，标「—」 |
| 测试目录（`paths.tests`） | **测试角色**（敏捷=测试专家 / 调研=验证专家） | 目录名由 `profile.yaml` 声明 |
| `.gitignore` | **实施角色** | 根目录逃逸件的堵口 |
| `{{paths.changelog}}` | **写作角色** | — |
| 部署编排定义 | **部署角色**（敏捷=部署专家 / 调研=环境运维专家） | 写定义属该角色；**执行部署属 Jenkins（排他）**；只读验证属该角色 |
| **提交动作（`git commit`）** | **编排者** | 跨角色的**链级**动作；不由产出该变更的角色自行提交 |
| `.dsh/tmp/<role>/`、`.dsh/reports/` | 各角色自己 | 临时 |

> **提交动作的位次与红线**：
> - **位次：链级闭环、全部 QA 与测试通过之后**，与"清理临时产物"同一时机——顺序是**先摘录 → 再提交 → 后删除**，不能反（与上文两条硬要求一致）。

> - **执行者：编排者**，不是产出该变更的角色——编排者是唯一看得到全链的角色，**一次链 = 一个可回滚的提交点**。
> - **红线不变**（正本见 `_shared/engineering-rules.md` 的 `security` 节）：AI **不碰 `main`/`master`**；提交一律落在 `develop` 或功能分支；`develop → main` 由用户负责。
> - **与"两态划分"的关系**：`.dsh/tmp/**`、`.dsh/reports/**` 属临时产物，**不应进提交**——**带着临时产物提交 = 把本该删掉的东西写进历史**。
> - **提交范围纪律**：只提交本轮链**实际改动的正式产出**；**禁止 `git add -A`**（它会把临时产物与无关文件一并提交）。提交后**核对提交里的非 `.dsh/`/非 `paths.source` 文件数为 0**，再收口。
