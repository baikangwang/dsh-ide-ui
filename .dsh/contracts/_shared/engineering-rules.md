## 回复语言（硬约束，所有角色适用）
- **面向会话的叙述、解释、汇报、提问、计划、调度信号与最终结论一律中文**，读者据此即可获取实质。
- **深度推理与技术分析过程允许用英文**（保留模型最强语言，以保推理质量）——不视为不合规。
- **中文结论必须自足**：给出结论/摘要时，关键判断、根因、取舍、影响须用中文写清，读者无需回读英文推理块即可理解。
- **结论、响应、结果用白话中文表述，要让人看得懂**（用户契约 2026-09-01）：把话说完整、讲清判断和理由，让不熟悉上下文的读者也能一次读懂；宁可多写一句解释，不压缩到看不懂。**句式与语势**：用完整的主谓宾短句，一句只说一件事，长定语拆成短句；像向同事当面讲解，不写电报体值班记录——压缩语（反例："废止启用 / 本轮零执行 / 当前在途 / 经复核零影响"）一律展开成完整说法（"停止启用 / 本轮未执行 / 正在进行中 / 复核确认没有影响"）。
- **不用直译腔造词、不生造术语**（用户契约 2026-09-01；2026-09-09 补强，源自"写内核缺陷家族"式表述读不懂的用户反馈）：禁止自创缩写、简称、黑话来压缩表达；**禁止把英文术语逐字翻译拼成中文新词**（真实反例：write kernel→"写内核"、defect family→"缺陷家族"、scanning surface→"扫描面"、throttling counter→"限阻性计数"、ingestion source→"摄取正源"）；概念没有通行中文叫法时，用通行词把意思展开说清（"写内核缺陷家族"应说成"文档写入核心链路里的一组同源缺陷"），需要时在括号里附英文原词。**项目既有术语同样要先核实来源**：项目文档本身可能就是模型生成的，文档里的叫法不自动可信。沿用前核对它是否出现在源码标识符、配置键、上游官方文档或人类材料里——有真实来源的（模块名、产品名、配置项）可以沿用，面向用户第一次出现时仍须紧跟一句白话解释；只是模型写进文档的直译拼接词（"写内核/缺陷家族/扫描面"这类）判定为模型自造词，面向用户一律用通行词改写，不在回复里沿用；改写该文档时同步改用通行词，并在文档变更记录里登记旧名→新名。读者看不懂的词等于没说。
- **禁用「门」系造词**（用户契约 2026-09-09，源自"文档里各种门、真看不懂"的用户反馈）：不把「门」当后缀拼新词——门控→检查/校验/把关/检查点（如 代码门控→代码检查、版本区间门控→版本区间判定、质量门控→质量检查）、门槛→阈值、门禁→访问控制（段落语境：评审门禁→评审检查点）、逃生门→逃生通道/应急通道、门面→外观（Facade）/兼容层、守门员→把关人；「X门」拼接词（反例："进展门 / 用户评审门 / 人工门 / 硬门 / 回归门 / 幂等门"）一律改为「X检查 / X检查点 / X校验」，面向用户首次出现时附白话解释。后门（backdoor）、部门、入门是日常通行词，不受本条限制。
  - **`闸门` 不在本条禁令内（2026-09-21 裁决，落纸以防反复重提）**。理由有二：① 本条禁的是**「修饰语 + 门」的拼接造词**（反例全部是该形态：「进展门」「人工门」「硬门」「回归门」），而 `闸门` 是汉语固有复合名词（sluice gate），`闸` 不是修饰语；② 本条自己已把"日常通行词"（后门/部门/入门）明确豁免，`闸门` 属同一类。
  - 但**`门禁` 在禁令内**（本行映射表已列：`门禁→访问控制`，评审语境作"评审检查点"）。**实测本仓库交付面曾有 8 处 `门禁` 残留**（含 `qa-common`/`agile-toolkit` 的节标题与生成物 `REGISTRY.md`）——**禁令写了不等于执行了**，故此处点名：`门禁` 与 `门控` 同等对待，出现即判术语违规。
- **禁用日常词生硬隐喻与动词误用**（用户契约 2026-09-09 第三批，源自"测试波/卫生/翻/首跑这些词乱七八糟"的用户反馈）：技术概念必须用软件工程、计算科学、计算软件领域的通行词，不拿日常词做生硬直译隐喻，不滥用非专业词——wave→批次/轮次（"测试波"→"测试批次"）、hygiene→清理/治理（"卫生窗口"→"清理窗口"/"维护窗口"）、flip/翻→置为/更新为（"翻 reviewed"→"状态置为 reviewed"）、首跑→首次运行、活体→真实环境实测（"活体证实"→"实测证实"）、热改→热更新、择时→择期/时间待定、置留→残留、在位→已生效/已配置/已就位、打点→埋点/指标记录、综合窗→综合部署窗口、观测面→观测统计；零X 谓语用直接说法（零空字段→无空字段、零扫描→未触发扫描）。概念没有通行中文对应时，用白话把意思展开说清，或保留英文原词。读者看不懂的词等于没说。
- 代码、文件路径、目录、键名、命令、API 符号、工具名保留英文原样。

## 文档写作通用规则（所有角色的正式文档产出，硬约束）

适用：`docs/` 下的任何正式产出（设计文档、根因分析、测试方案、报告），以及角色回传给编排者的结论。
**契约中的项目专属取值写占位符，不写字面量**：`{{paths.*}}` / `{{tech_stack.*}}` 解析到 `.dsh/profile.yaml` 的对应键。契约只写"如何检查"，项目事实一律由 profile 提供——**换项目时改 profile，不改契约**（2026-09-18 修订）。

1. **总原则：删噪声，不删设计信息。** 压缩的对象永远是冗余与过程，从来不是结论、判据与理由。
2. **结论四问**：每个结论必须答得出「是什么 / 凭什么（数据、`文件:行号`、命令与输出、官方出处）/ 这份依据**属于哪一档证据**（一手 / 二手 / 未找到一手来源）/ 为什么不选别的（被否决方案 + 一句话理由）」。缺任一问即为不合格。
   **引用外部结论必须标注证据档位**（理论报告 §5.12 第 2 条）：`[已核验-一手]` / `[已核验-二手]` / `[未核验]`；**二手与未核验的结论不得作为设计决策的唯一依据**。实测依据：2026-09-18 理论核验发现一份 13 行的「机制 → 理论」映射表里**至少 12 行**依据的是后来被降档或撤回的二手转述——**不标档位，就分不出哪一行是硬的那一行。**
3. **数字三标**：每个数字标注来源、时间、环境。无来源的定量断言不得作为结论陈述。
4. **结论与过程分离**：正文只留结论与判据；探索路径、试错记录、问答回放、工具输出粘贴、QA findings 处置流水一律不进正文（过程留痕写 `.dsh/tmp/<role>/`）。
5. **修订语义是整体重写，不是追加**：正文不出现"修订记录/变更记录/版本历史"章节，不出现"原为…现改为…""上一轮""v1.x 更正""就地注记"这类字样；版本变更只写一行，明细进 `{{paths.changelog}}`。
6. **单一事实源**：同一条信息在文档里只出现一次，别处写"见 §X"。
7. **术语必核来源**：沿用上文「回复语言」的既有禁令——非通行叫法必须在源码标识符、配置键、上游官方文档或人类材料中出现过；只在模型自己写的文档里出现过的拼接词判为自造词，改用通行说法；面向读者首次出现时附一句白话解释。
   - **`Δ判定式` 这个名字不进交付面（2026-09-21 裁决，落纸以防反复重提）**：模式仓库的设计文档用「Δ判定式」指称上一条规则里的**净增长 ≤ 0**（`Δ` 取"变化量"义）——**但它是个只在模型自己写的文档里出现过的拼接词**，按本条正属自造词；实测交付面 **0 命中**，全仓库仅 2 行提到它，且都是同一句出处声明。
   - **处置：机制保留，名字不用。** 交付面一律写**「净增长 ≤ 0」**（描述性表述，读者无需查表即懂）；**不引入「Δ判定式」这个叫法**。
   - **为什么写成裁决而不是默默不管**：那个名字出现在模式仓库文档的**落地声明**里（"落地清单之一：Δ判定式"），读者拿这句话来交付面核对时会**找不到任何落点**，从而误判为未落地——**一次命名不一致会持续制造假缺口**。记下"名字不用、机制已落"这一条，是让核对者能一次判定完。
8. **"逐字保真"只管归档，不管正文**：既有的"降级写入必须逐字复制原文、禁止简化/重写/省略/总结"这条规则，**只适用于把外部原文归档到 `.dsh/tmp/` 留证**（用于事后核对原文），**不适用于 `docs/` 下的正式文档正文**。同理，"变更记录（追加式、不重写历史）"这个惯例属于实施记录类文档，**不适用于设计文档**。
9. **回环期纪律**：每一轮修订都按上述规则整体重写受影响章节，不以"在上一版上打补丁"的方式修订；**净增长 ≤ 0**（确需新增设计结论的须说明该新增属设计内容而非本轮过程）；先删本轮噪声，再补新结论。
10. **原则必须可证伪**：写进契约、方案或设计文档的**设计原则**，必须答得出「**什么样的观测会推翻它**」（理论报告 §5.12 第 3 条）。答不上来的原则，失败模式必然是"永远通过"或"凭评审者心情"。**不可证伪的原则不得写入契约。**
    > 本仓库的实测依据：判据演进**6 次全部来自事故驱动、全部是新增约束、无一次删除或合并**（见 `qa-common.md` 规则复审节）。**只增不减，正是因为没先问"它怎样才算失败"。**

> 依据（2026-09-17 用户裁决）：用户反馈设计文档"越来越像流水账"，同时指出另一侧风险——曾有一条"逐字保真"规则把文档压到"没头没尾、看了又什么都没看到"。两个极端都要治：**既禁无用的多，也禁缺用的少。** 判据改判"每句话有没有用"，不判"文档有多长"。

## 外部理论与改进提案的准入（硬约束）

> 2026-09-20 新增。来源：理论报告 **第 1 章（哲学层）§一.2 / §三 / §四.3 / §九 / §十**、§2.2 / §2.5 / §2.10 / §3.6.2 / §5.12 第 5 条 / 第 6 章 §2.1–§2.4、§5.2、§5.4，以及第 0 章 §7.4 的裁决。
> **这一节管的是"提案该不该被采纳"，不是"提案写得好不好"。** 它填补此前只有"标注档位"、没有"**怎么定档、什么档位能支撑什么结论**"的空档。
> **2026-09-21 注**：上面那串节号是**溯源指针**（本节每条规则从哪来），本节正文已把规则内容就地写清——**读者不需要去翻那份报告就能用本节**。
> 「理论报告」= **模式仓库** `docs/` 下的 `敏捷管理理论基础调研报告-v2.0-2026-09-18.md`（**不是交付件**）。此处只留节号作可追溯性来源，不构成需要读者打开的引用。

### 1. 改进提案的反馈回路准入

**任何效率或过程改进提案，必须先说明三件事**：它作用在**哪条反馈回路**上、**延迟多久**显现、**有没有副作用回路**。做不到这一点的**不予采纳**（理论报告 §2.2：这是系统论的唯一硬性要求——先画出反馈回路，再谈优化）。

**"改进"不等于"加检查"。** 未做变异分析（普通原因 vs 特殊原因）的改进建议**默认不采信**——见 `qa-common.md`「新增判据的准入纪律」。

### 2. 禁用"多样性不足"式论证；改用可检验的覆盖率

**不要用「Ashby 定律要求更多多样性」「信息论说信道容量不足」来论证加角色或加检查项**——那是**用理论名字代替机制论证**（理论报告 §2.5）。可检验的替代判据是**缺陷类型覆盖率 N vs M**：QA 需要识别的缺陷类型有 N 类、现行判定规则只覆盖 M 类，则 N−M 类必然穿透到下游。**报数，不报名字。**

新增角色的举证门槛另见 `contract-conventions.md`「角色切分依据」节。

### 3. 引用外部结论必须自我声明为外推

把工业侧或人因侧的研究结论迁移到本仓库场景时，**必须显式写"这是外推"**，并给出原研究的情境。**禁止**用「研究表明」「业界已证明」「公认」这类措辞把外推写成定论（理论报告第 0 章）。

**引用密度 ≠ 证据密度**：一段话被引用得多，不说明它证据强（Tuckman 是典型：培训材料引用极多、学术证据薄弱）。**按证据定档，不按引用次数定档。**

**外推要标出原结论的严格性等级**（第 1 章 §十三 M8）：同为"系统思维"，**系统动力学有方程、可算**，而 Senge 的「系统原型」是**模式库、只能类比**——把后者当前者用，是把类比当迁移。凡涉及这类同源不同严格性的理论，**必须写明引的是哪一支**。

**不得用"符合某个哲学流派"为机制背书**（第 1 章 §九）：实用主义与敏捷宣言的关系经核验属**后人哲学追溯，非宣言直接依据**，因此"符合实用主义"不构成任何证据。要表达同一意思请用可检验的弱表述——**「本机制的效果以实际交付结果判定，不以流程合规判定」**。

### 4. 结论档位与来源档位是两件事

上文规则 2 的 `[已核验-一手/二手/未核验]` 是**来源档位**（这个说法从哪来）。**结论还要另定一次档**（这个说法现在站得住吗）——**"一手但已被推翻"是最危险的组合，只看来源档位完全管不住。**

#### 4.1 三档的定义（2026-09-21 新增，第 6 章 §1.1）

> **为什么补**：交付面此前**只有档位名、没有定义**（`[已核验-一手]` 到处在用，但"什么算一手"从未成文）。
> 后果是**同一条来源可以被两个人标成不同档位，且都自认为合规**——档位虚高的判据（D11）也就无从落地。

| 档位 | **算**这一档的条件 | **不算**（常见误标） |
|---|---|---|
| `[已核验-一手]` | 读到了**原文本身**或其**官方元数据**（论文全文 / 官方文档页 / 标准正文） | 只读到摘要 · 只读到二手转述里引的原句 · 只"确认它存在"但没读内容 |
| `[已核验-二手]` | 只读到**权威转述**，或**只确认了来源存在**而未读原文 | 把二手转述当原文内容引用 · 用百科/博客当转述来源（那不是权威转述） |
| `[未核验]` | **未找到**来源，或找到但未能读取 | —— |

**三条判读纪律**：
1. **读到摘要 = 二手，不是一手。** 实测发生过：`Baham & Hirschheim 2021` 只有摘要可读，却按一手处理。
2. **来源档位 ≠ 结论档位**（本条正文）：`[已核验-一手]` 只说明"这句引文我读过原文"，**不说明"这个结论现在站得住"**。两者必须分别标注。
3. **档位虚高 = D11 FAIL**（敏捷侧见 `qa/gate-standard.md`；调研侧同判）。

#### 4.2 定档流程：三查（2026-09-21 新增，第 6 章 §2.1）

> **为什么补**：`research-rules.md` 早有这套流程，**敏捷侧没有**——于是同一份证据在调研链里按流程定档、在敏捷链里凭印象定档。
> 注意：下面这套流程**不是新判据**，它是 §4.1 定义与 C1–C4 判据的**执行步骤**。

**限时 30 分钟 / 最多 3 轮检索，查三件事；三查都无结果即定 `[未核验]`，并接受它：**

| 轮 | 查什么 | 查到了 → | 查不到 → |
|---|---|---|---|
| 1 | **原创出处**（最早那一篇） | 读到原文 ⇒ 一手 | 继续 |
| 2 | **独立复现**（同行评审的重复验证） | 有 ⇒ C2 成立，可支撑结论 | 继续 |
| 3 | **反证**（推翻或限制它的研究） | 有 ⇒ 按 §4 措辞表写「已被证伪」或「多数不支持」，并附该证据 | 定 `[未核验]` |

**红线**：**30 分钟到了就停，写 `[未核验]`，不得为了"看起来更可靠"而升级档位**——把未核验写成已核验是本仓库的**已知失效形态**，比写 `[未核验]` 危害大得多。

#### 4.3 留白必须成清单，不得用推测填补（2026-09-21 新增，第 5 章 §5.10.3 / §5.13、第 6 章 §七、第 1 章 §十五）

> **为什么补**：这条纪律此前**只落在 `contracts-research/_shared/research-rules.md`（调研模式专用）**，敏捷侧没有对应条款。
> 但"未核验的空白"在两种模式里都会出现——**敏捷侧一样要引外部理论**（准入硬约束就在本节开头），一样会遇到"查不到"。
> **两模式不对称的后果**：同一条纪律，调研链会执行、敏捷链不会，而判据本身对两者是同一件事。

**本次取证/论证中「刻意不查」或「查不到」的位置，必须单独成清单登记，不得用推测填补。** 清单每行写三样：

| 写什么 | 例 |
|---|---|
| **查了什么 / 没查什么** | 「未查 Ringelmann 效应的原始 1913 年法文文献」 |
| **为什么** | 「该文献无数字化版本，**而未核验**不影响本结论」 |
| **影响哪个结论** | 「影响 §3 的团队规模论证；**已在文中标 `[未核验]` 并降档**」 |

**三条硬判据**：
1. **「查不到」是合法结论**，写进清单即可——**但不得降级成"大概不成立"**（同 §4 措辞表）。
2. **空白是刻意的时候就写"刻意"**：「本次刻意不查 X，因为 Y」比留一个洞更可信。
3. **清单本身是可信度的组成部分，不是噪声**——审计时**不得**把留白清单当"过程留痕"要求删除（与 `qa-common.md` 的 R8/D9 必要性判据的例外条款同源）。
4. **不得跨章节/跨文档"借"内容**：某处标注为待核验/留白的内容，**别处不得直接引用其结论**——要引必须先补核验。**一次"借"就等于把一处留白复制成两处未核验的引用。**

**入选判据**（理论报告第 6 章 C1–C4，四者不必齐全，缺哪条就在档位上写明）：

| 判据 | 问什么 |
|---|---|
| **C1 源头可考** | 找得到最早那一篇吗？（不是二手转述的转述） |
| **C2 学术沉淀** | 有同行评审的独立复现吗？ |
| **C3 框架采用** | 被权威框架**明文**采用了吗？ |
| **C4 工业验证** | 有可考的工业侧实测吗？ |

**C5 可证伪性只作筛查，不作裁决。** 它只问一句「什么样的观测结果能反驳这个说法？」：
- 答不上来 → **不进入分档流程**，不得写入契约（与上文规则 10 同源）；
- 答得上但反驳条件极苛刻 → **降档**；
- **C5 不得用于宣称「某说法已被证伪」**——那需要独立的反驳证据，属 C1–C4。本仓库实测已出现过用"证伪"一词下论断的脚本，属越界。

**否定性结论的措辞强度必须与证据强度一致**（理论报告第 6 章 §5.4，本仓库的系统性偏差是"否定性结论一律比证据更硬"）：

| 证据状态 | 只能这样写 |
|---|---|
| 没找到一手来源 | 「**未找到**一手来源」 |
| 多数研究不支持 | 「**多数不支持**」（写明是哪些） |
| 原始结论被直接推翻 | 「**已被证伪**」（须附推翻它的那份证据） |

**"未找到"是合法的结论**，不是失败；但**不得**降级成"大概不成立"或直接当作"已被证伪"。

### 5. 红旗清单（出现即降档，逐条写明降到了哪一档）

1. 引用链找不到最早那一篇（全是转述的转述）
2. 用「研究表明」「业界已证明」代替出处
3. 只有单一成功案例，却当作一般规律
4. 把相关性直接当因果
5. 把类比当同构（情境不同却当同一回事）
6. 诉诸权威（"某某权威说过"而不给判据）
7. 利益相关方自证（由受益方自己出具的证据）

### 6. 常见论证陷阱（写"外推"前先自查，命中即须修正措辞）

把从业者框架当科学理论 / 把相关性当因果 / 把类比当迁移 / 把单一成功案例当验证 / 幸存者偏差 / 度量成为目标即失效（**归属：Strathern 1997 对 Goodhart 定律的改写，不是 Goodhart 原话**，理论报告 §4.15）/ 利益相关方自证。

### 7. 两条数值禁令

- **「利用率 80%」不得作为并发度设计依据**——它必须由本仓库实测决定（理论报告 §3.6.2）。本文件中出现的 80% 是**评分配方**的阈值，与此无关，不要互相援引。
- **在制品上限的具体数值不得预设**：它由实测决定，不由类比决定。

### 8. 规范性命题与实证命题必须分开判（2026-09-20 新增，第 1 章 §三）

> **本节修的是第 4 节 C5 的一个误伤**：按 C5 的字面执行，「敏捷宣言的四条价值」答不出"什么观测能推翻它"，会被直接判为不达标。**那是范畴错误**——那份文件是**规范性文件（axiology）**，不是科学理论。

| 命题类型 | 例子 | 评判标准 | 能否做证据分档 |
|---|---|---|---|
| **规范性** | 宣言四句价值、Scrum 五价值观 | **自洽性**（内部有无矛盾）+ **解释力**（能否一致地解释本仓库的做法） | **否**——做分档即范畴错误 |
| **现象学描述** | Schön 反思性实践 | 同上；辅以"是否可操作" | **否** |
| **定义性论断** | Polanyi「我们知道的比能说出来的多」 | 只看**是否明标不可证伪** | **否** |
| **经验性主张** | 「返工率与周期时间相关」 | C1–C5 全套 | **是** |

**三条硬判据**：
1. **契约里允许出现规范性条款，但必须标明它是规范性条款**，且不得为它编造实证引用（"研究表明应当自组织"这类，见第 3 节）。
2. **哲学层的结论不得被当作实证依据使用**——它只能提供**解释**与**立场合法性**，不能提供强度。
3. **「不可证伪」是标注，不是罪名。** 明标了不可证伪的命题是合法的规范性主张；**没标却被当实证用的**才是缺陷。

**已知最严重的滥用形态**：把 Polanyi 的隐性知识命题当作**「所以不必写文档」的辩护**。该命题的正确推论是**相反方向**的——正因为契约传达不了情境取舍，契约才**更**需要写明「什么时候必须升级为人工裁决」（见 `contract-conventions.md`），而不是更少。

### 9. 判据冲突必须写明冲突的双方与优先级（2026-09-20 新增，第 1 章 §十）

本仓库**确实存在判据冲突**（如「删噪声」与「不删设计信息」；D8 与 D9 互为刹车）。冲突出现时：

1. **必须写明冲突的具体双方是哪两条**——只写"按敏捷价值观"是**无法执行的空话**，判为不合格表述。
2. **优先级顺序**：宣言四句价值（`[已核验-一手]`）> 本仓库既有裁决记录 > 契约条文 > 评审者判断。
3. **宣言只在冲突时生效**——原文是「while there is value in the items on the right, we value the items on the left more」。**没有冲突时不要援引它**，那只是口号。
4. 本仓库的**判决惯例**是"以实际交付结果判定，不以流程合规判定"——**这条不需要引用任何哲学出处**（不得用"符合实用主义"为机制背书，第 1 章 §九）。

### 10. 分权必须同时保证对外部耦合的感知能力（2026-09-20 新增，第 1 章 §四.3）

**自组织不是无条件成立的**：它的有效性依赖于与外部系统的耦合质量。把决策权下放给角色子代理时，**必须同时保证它对下游（契约变化、下游消费者）的感知能力**——否则**分权只是把失败点挪个位置**，不是消除它。落到 `contract-conventions.md`「角色切分依据」节。

### 11. 契约必须可演化，但不得放弃

本仓库的需求属**不良结构问题**（判据会随实现而变），因此契约**必须留有低成本修订通道**（见 `qa-common.md`「规则复审机制」），但**不得**因此得出"契约不重要、按需来就行"——不良结构问题需要的是**更重**的过程设计，不是更轻的。

### 12. 理论外推的边界：能引什么、不能引什么（2026-09-20 新增）

> 来源：理论报告 **第 2 章 §2.6 / §2.7 / §2.9**、**第 5 章 §5.4 / §5.6 / §5.7 / §5.8 / §5.9**。
> 本节补的是第 3 节的**下位执行细则**：第 3 节说"外推必须自声明"，本节说**具体到哪几个理论，声明成什么样才算合格**。
> 前 11 节管"提案该不该采纳"，本节管"引用这批理论时，哪一半能用、哪一半不能用"。

**总规则：理论提供的是「待检验命题」，不是「现成度量」。** 把一个理论的名字或指标直接搬进本仓库，
如果不同时说明**它在原情境里定义在哪个事件上**、**本仓库有没有那个事件**，即为误用。

| 理论 | 本仓库有没有它依附的事件/对象 | 能引什么 | **不能引什么** |
|---|---|---|---|
| **DORA 五项指标** | ❌ **没有「部署」事件** | 那条结论本身：「**速度与稳定性不是权衡关系**」——但它在本仓库是**待检验命题**，不是既有结论 | 五项指标本身（Deployment frequency 直接不适用，其余四项只能类比）；**禁止「本仓库达到 DORA 精英级」这类表述——那是范畴错误** |
| **DevEx「心流」维度** | ❌ agent 无「心流」 | 反馈环维度（**同构**：派发到首次有效判定的回合数与耗时） | 心流状态——**不符构，不得强行套用** |
| **认知负荷（Sweller）** | ⚠️ 部分同构 | **操作性判据**：*单次注入的规则若无法在一次判断中全部用完，即属外在负荷，应继续切分* | 「4±1 组块」「工作记忆容量」式论证——**LLM 没有人类意义上的工作记忆瓶颈**。用理论名当依据即为外推（见 `contract-conventions.md`「角色切分依据」节） |
| **OODA** | ❌ 无「观察-定向」循环对象 | 唯一可迁移项：**在派发链中加入显式的「重新判断」环节**（比单纯提高派发速度更有价值） | 用 OODA 为机制命名 |
| **Cynefin** | ⚠️ 取决于任务类型 | 引入机制前**先问"这是哪个域的问题"**；**必须保留"尚未知道属哪类"的位置**，不得强迫分类 | 用 Cynefin 给机制命名代替论证 |
| **Stacey 矩阵** | ❌ 不适用 | —— | **本仓库不使用 Stacey 矩阵作为理论依据**（改用 Cynefin）；其两轴被判据 C1–C4 逐项检验均不成立 |
| **Brooks 本质/偶然复杂度** | ⚠️ 只可作预期管理 | 改进预期设上限：切片/并发/后端优化**都在偶然侧**，不会有数量级提升 | 把 Brooks 读作**「反对迭代」**——原文明确支持增量开发 |
| **SPACE** | ⚠️ 只可作维度清单 | 「不要用 token 消耗量或派发次数评价效率」——Activity 类只占五分之一，最易 Goodhart 化 | 把任何一项 Activity 当生产力指标 |
| **敏捷有效性的实证研究** | ❌ 情境不可比 | 最强可引用表述：「**某些机制在软件行业有较一致的实证观察**」 | 「敏捷被证明有效」；**按品牌引用**（应引用「缩短反馈周期」这类机制，而非「因为我们用了敏捷」） |

**两条独立硬判据**：

1. **承认情境依赖**（第 5 章 §5.9）：本仓库的情境——LLM 多代理、无人类社会化通道、吞吐率硬约束——**与任何已有研究的情境都不同**，因此**它的有效性在证据上是空白，只能靠自己积累**。这不是弱点，是**必须显式承认的前提**；不承认它，度量与命题就会照着别人的情境设计。凡声称"按业界最佳实践"而不说明情境差异的提案，判为未完成。
2. **预防性禁令同样要落纸**（第 5 章 §5.6/§5.8）：上表中"不能引什么"的数条，在本仓库**当前并没有对应的引用对象**（没人引过 DORA 指标、Brooks、心流）。**它们是防未来误用的防线，不是对现状的指控**——但要写下来，否则第一次误用发生时没有任何东西会拦住它。

### 12.1 「理论成立」≠「该理论在软件组织中被验证」（2026-09-20 新增，第 4 章 §4.16.3）

分档时要**分开问两个问题**：① 这个论断在**它的原学科**里成立吗（来源档位）？② 它在**软件组织的实践情境**里被验证过吗（结论档位）？
**两者互不推出**。大量管理学论断在①上是 A 档、在②上是空白（Tuckman 阶段模型即为典型：引用密度极高、原始证据极薄）。
**只答了①就当作②已答，判为降档不足**——这正是第 3 节要求"标出原结论严格性等级"的原因。

### 12.2 契约松紧按「任务确定性」调，不按「改动大小」调（2026-09-20 新增，第 4 章 §4.4）

**确定性任务收紧契约，开放性任务放开**——机械式重构（改法唯一、对错可判）应当把判据写死、不留解释空间；
架构决策（存在多个可辩护方案）应当留出判断余地、并把**取舍理由**作为必填产出。
**不要把它与现有档位混为一谈**：`A0/A1/A2简/A2标准/A2深` 分的是**改动范围与是否要求实施**，与任务确定性是两个轴。
> 引用纪律：写「**借用 Shu-Ha-Ri 这一实践比喻**」，**不得**写「Shu-Ha-Ri 理论表明」——那是从业者框架，不是科学理论（第 5 节红旗 1）。

#### 12.2.1 分档用两问代理，不用三维（2026-09-21 明确，第 0 章 §7.1）

第 0 章 §7.1 的裁决是「**按三维分档：理论成熟度 / 工业侧证据 / 软件侧证据**」。本仓库交付面**把它收敛成了两问代理**：
① 该论断在**原学科**成立吗？② 它在**软件组织情境**里被验证过吗？（即 §12.1）。**这是有意的简化，不是漏做**，理由：

- 第 0 章那张三维表的**第三维（软件侧）与第二维（工业侧）在本仓库的可判定性不同**：工业侧证据**能查到**（有可考的工厂/服务业绩效数据），软件侧证据**在本仓库的情境下是空白**（§12 硬判据 1：LLM 多代理、无人类社会化通道）——**一个恒为"空白"的维度不构成分档依据**，它是一条**结论**（"这里没证据"），不是一把尺子。
- 两问代理**保留了三维的判别力**：三维要抓的错误是"拿工厂证据给软件组织背书"，而两问代理的第二问**正是抓这个**（`engineering-rules.md` 上文：「工厂证据不得给软件背书」）。
- **第三维的内容没有丢**，它以**硬判据**形态存在（§12 硬判据 1「承认情境依赖」），强度比"一个档位列"更高——档位可以被写高，硬判据不能。

### 12.3 机制改动必须按「诊断 → 干预 → 观察」三段记录（2026-09-20 新增，第 4 章 §4.8）

**本条管的是本仓库自己的改进动作**（不只是外部提案）：任何对契约、判据、角色、流程**本身**的改动，都必须留下三段痕迹：
**诊断**（哪个观测值不对、证据是什么）→ **干预**（改了哪条规则、预期动哪个变量）→ **观察**（改动后该变量怎么变）。
台账记的是**链参数**（12 列），不是这三段——三段式记在改动所属的评审记录或 `.dsh/tmp/` 过程留痕里。
**缺了"观察"一段的改动，视为未完成**——它无法被后续复审判定为有效或无效（这也是 P9 规则复审的输入前提）。
> **力场分析等命题层工具不推荐用于论证技术设计**（同章 §4.8）。

### 12.4 「高标准」必须与「高安全感」成对，否则退化为隐瞒（2026-09-20 新增，第 4 章 §4.6）

**QA 检查点的设计目标是「让问题被说出」，不是「让问题不被产出」。**
若暴露问题会让角色被追责、或触发连锁返工，系统会退化成**不报错**而不是**不犯错**——这与本仓库已实测的"88% 的派发是重复派发"在机制上同源（返工惩罚高 → 上游倾向保守与重复确认）。
因此**提高标准时必须同时给出"暴露问题不引发连锁返工"的机制**，只提标准=放水，只提安全感=放水；**只落一半就会变成免责口子**（`qa_common.md` P8 已按此写死三条边界）。
**判据**：新增任何对抗性检查时，必须同时回答"角色报出这个问题后，会承担什么后果"；答不出或答成"会被重派到底"的，该检查**不予设立**。

### 12.5 判据冲突：「报数不报名字」 vs 「引用沟通路径模型」

**这是一组真实冲突，按规定写明双方与优先级**（见第 9 节）：

| | 甲方 | 乙方 |
|---|---|---|
| **条文** | 第 2 节：不要用「Ashby 定律要求更多多样性」这类**理论名字代替机制论证**；**报数，不报名字** | 第 4 章 §4.11：**建议引用沟通路径模型**（而非布鲁克斯定律）来解释星形拓扑 |
| **各自管什么** | 管**「要不要加」**——加角色 / 加检查项的**准入举证** | 管**「为什么这样设计」**——对**既有拓扑**的解释 |

**优先级与适用边界**：`报数不报名字` **只管准入举证**（提案要加东西时，必须给出可检验的 N vs M 覆盖率，不得用理论名代替）；
**解释既有设计**时允许具名引用模型（沟通路径模型、康威定律），因为那里要说明的是**结构的来源**，不是**增量的必要性**。
**误用形态**：用"沟通路径模型说要星形"来论证**新增某个角色**——那是把解释工具当准入证据，仍按第 2 节拒绝。

### 13. 过程改进的三种定位：诊断 / 排程 / 试验（2026-09-20 新增，第 3 章 §3.5.9 / §3.13.5 / §3.14.5）

**本节补的是「改进提案」这一侧**——第 1、2 节管提案的举证，本节管**提案的定位写错时会出什么错**。

**13.1 约束理论（TOC）只能作诊断工具，不作排程工具。** 引用 TOC 时必须**先识别当前约束是哪一类**：

| 约束类型 | 表现 | 处置 |
|---|---|---|
| **规则约束** | 瓶颈是判据/契约本身（如某条规则导致大量返工） | 改规则（走 P9 规则复审） |
| **产能约束** | 瓶颈是派发/并发/上下文容量 | 调派发参数（限流、切片） |

**"先识别约束再谈改进"是强制动作**——未识别就提"提高效率"的提案，判为未完成。
**不得把 TOC 当作排程算法用**（不得用它推导优先级公式，见 13.4）。

**13.2 精益的「浪费」在本仓库有四个可观测形态，全都要看，不能只看一个**：

| 浪费形态 | 本仓库的可观测对应 |
|---|---|
| 重复派发 | 台账「派发」「重派」计数 |
| 返工回环 | 台账「轮次」「FAIL 分布」 |
| **无人消费的产物** | 产出了但下游没有任何角色引用它（文档过剩即库存） |
| 超时等待 | 台账「等待启动」（链在开始跑之前排队的时间） |

> 此前只落了第三种（且只在调研侧）。**四种必须同等对待**——只盯"产物过剩"会漏掉"等待"和"重复派发"这两类更大的浪费。

**13.3 按能力驱动，不按积压驱动。** 派发的节拍由**当前可用的派发能力**决定，不由**待办清单的长度**决定。
积压长不是加派发的理由——那只会把瓶颈从一处挪到另一处（约束仍在，只是在制品变多）。

**13.4 三条禁令（成文，使禁令可机器检索）**：

- **不引入 WSJF / Cost of Delay 公式**、**不引入 175 条 / Reinertsen / SAFe 的度量体系**——**理论来源未核实**。
  它们的"延迟成本"概念在本仓库**没有对应的可测对象**（本仓库没有"延迟上市损失"这一事件）。
  > 这与「测量前先查定义变更史」（见 `metrics-gqm.md`）是同一条纪律的两个面：查不到定义变更史的度量只作诊断量。
- **不引入"实物期权"式论证**：把"早停"说成期权价值，不给出可测对象即为理论装饰。
  **反向禁令同样成立**：以上概念即使将来被引入，也必须先给出**本仓库的那个可测对象**是什么。
- 引用 TOC 时**不得省略约束类型的识别**（见 13.1）。

**13.5 试验类改动必须写「学习目标」与「停止条件」。** 若一项改动是**试出来的**（不确定它有没有用），必须同时写明：

1. **学习目标**：这次试验要回答**哪一个**问题（一句话，且答案会改变下一步决策）；
2. **停止条件**：什么观测出现时**判定无效并回退**（不是"看情况"，必须是可观测的量与阈值方向）。

**缺任一项的试验性改动不予采纳**——因为它结束后无法判定"该留还是该撤"，只会沉淀成没人敢删的历史负担。
> 注意与**回环停点**区分：回环停点（连续两轮零修复 / 重派满 2 次）管的是**一条链要不要继续跑**；
> 学习目标与停止条件管的是**一条规则该不该留下**。两者不可互相援引。

## 工程规范（通用基线）
1. **自研代码须经测试**：测试通过后才能报告成功
2. **开源基础上的自研**：遵循分支管理规范
3. **语义分离**：同一变量不同上下文语义不同须明确分离
4. **去硬编码**：参数/环境变量/配置尽可能参数驱动、配置驱动、DB驱动
5. **如实报告（零臆造）**：一切"已完成/已通过/已修复"的声称必须可复现验证（命令可重跑、文件可检查、输出可核对）；禁止虚报状态、伪造命令输出、臆造文件内容——QA 审计发现虚报直接判 FAIL

- 所有开发内容（新特性/阻塞问题/遗留问题修复方案）都须经用户评审，评审通过后方可动手
- 我提出评审意见，要先评估、调整方案，再提交评审

  **这里只写"要记"，不写死路径**——写死路径就会在另一种模式下落空。）

## 分支管理（通用）
| 分支类型 | 命名格式 | 用途 | 合并目标 |
|---------|---------|------|---------|
| main/master | `main`/`master` | 生产稳定分支 | 仅用户合并 |
| develop | `develop` | 开发主线 | → main（用户评审） |
| feature | `feature-xxx` | 新需求 | → develop（测试后确认） |
| fix | `fix-xxx` | 问题修复 | → develop（测试后确认） |

规则：
1. **AI 不操作 main/master**，所有提交在 develop 或功能分支
2. 功能/修复分支代码须经调试测试 → 用户确认 → 合入 develop
3. develop → main 由用户负责

> 注：红线为**契约规则**（角色必须遵守，QA 审计将其作为检查项）；工具层兜底由 dsh 原生机制提供——
> sandbox 模式（workspace-write 围栏写权限）+ approval（ask 策略，越权操作自动升级用户审批）。
> 项目级红线事实声明见 `.dsh/profile.yaml` 的 security 段。
> **2026-09-21 订正**：原文写「（**注释态**，供人参考）」，而实测本仓库 `.dsh/profile.yaml` 的 `security.branch_policy` **已启用**（`default_branch` / `ai_forbidden_branches` / `ai_allowed` 三项均为生效键，不再是注释）。
> 这是**反向漂移**：评审期确实曾是注释态，后来启用了，但契约里那句没跟着改——读者会以为红线还是"仅供参考、不生效"。
> **正确读法**：该段**是否生效取决于项目是否声明**（消费项目可以只留注释骨架）；声明了就是**生效的项目事实**，未声明才按"未声明"处理。**不要把"某个项目当时的形态"写成本契约的固定描述。**

## 开发环境访问（凭证走 credentials 受管，**取值一律不进契约**）

**本契约只规定"怎么取"，不记录"取什么"。** 主机、端口、账号、库名、schema 都是**项目事实**，
写在这里就违反了本模式最基本的一条分工——**共享契约随 `.dsh/` 分发到每一个项目**，
在里面写某一个项目的内网地址，等于把它复制给所有项目。

Access 约定（通用，与本仓库/本项目无关）：

1. **凭证本体一律不落规则文件**，经 DSH `credentials` 解析引用
   （`~/.dsh/.credentials.yaml` 的 refs；2026-08-25 用户决策"全量"）。
   规则文件里只允许出现 `credential:<KEY>` 这样的**引用**，不允许出现明文值。
2. **主机 / 端口 / 账号 / schema 属于项目事实**，登记在**本项目的** `.dsh/profile.yaml`
   （或本项目自己的 skill）里——**不进共享契约**。
3. **需要鉴权的克隆/调用，密码不写在命令行历史里**：用
   `git -c credential.helper= -c "http.extraHeader=Authorization: Basic <base64>"`
   这类一次性注入方式，`<base64>` 由 credentials 运行时解析得到。

> ⚠️ 本契约中若出现任何具体主机名、IP、端口或账号，**那是缺陷，不是示例**——
> 应当移到项目侧的 profile / 项目自己的 skill。判据：**删掉这一行，别的项目会不会受影响？**
> 会 → 它属于共享契约；不会 → 它属于项目。
>
> 同理，**修订说明里也不得复述**被移除的具体取值——在"修正记录"里再写一遍等于换个地方再泄漏一次。
> 说明只写"移除了一类什么取值、为什么"，不写取值本身。

## 评分配方（通用方法论）
| 区间 | 规则 | 示例 |
|------|------|------|
| 正常范围（≤50%） | 不扣分，满分 | usage≤50%→100分 |
