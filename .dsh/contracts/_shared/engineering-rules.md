# contracts/_shared — 全局级方法论（两模式共用的唯一正本，注入所有角色）
> 注入时机：编排者派发任何角色子代理时，把本基线路径写入派发提示词的契约清单并附硬性开工指令——子代理第一步必须先 read 本文件（与角色专属契约一同加载；用户决策：契约由子代理自读，编排者不再读取并内联）

## 回复语言（硬约束，所有角色适用）
- **面向会话的叙述、解释、汇报、提问、计划、调度信号与最终结论一律中文**，读者据此即可获取实质。
- **深度推理与技术分析过程允许用英文**（保留模型最强语言，以保推理质量）——不视为不合规。
- **中文结论必须自足**：给出结论/摘要时，关键判断、根因、取舍、影响须用中文写清，读者无需回读英文推理块即可理解。
- **结论、响应、结果用白话中文表述，要让人看得懂**（用户契约）：把话说完整、讲清判断和理由，让不熟悉上下文的读者也能一次读懂；宁可多写一句解释，不压缩到看不懂。**句式与语势**：用完整的主谓宾短句，一句只说一件事，长定语拆成短句；像向同事当面讲解，不写电报体值班记录——压缩语（反例："废止启用 / 本轮零执行 / 当前在途 / 经复核零影响"）一律展开成完整说法（"停止启用 / 本轮未执行 / 正在进行中 / 复核确认没有影响"）。
- **不用直译腔造词、不生造术语**（用户契约；源自"写内核缺陷家族"式表述读不懂的用户反馈）：禁止自创缩写、简称、黑话来压缩表达；**禁止把英文术语逐字翻译拼成中文新词**（真实反例：write kernel→"写内核"、defect family→"缺陷家族"、scanning surface→"扫描面"、throttling counter→"限阻性计数"、ingestion source→"摄取正源"）；概念没有通行中文叫法时，用通行词把意思展开说清（"写内核缺陷家族"应说成"文档写入核心链路里的一组同源缺陷"），需要时在括号里附英文原词。**项目既有术语同样要先核实来源**：项目文档本身可能就是模型生成的，文档里的叫法不自动可信。沿用前核对它是否出现在源码标识符、配置键、上游官方文档或人类材料里——有真实来源的（模块名、产品名、配置项）可以沿用，面向用户第一次出现时仍须紧跟一句白话解释；只是模型写进文档的直译拼接词（"写内核/缺陷家族/扫描面"这类）判定为模型自造词，面向用户一律用通行词改写，不在回复里沿用；改写该文档时同步改用通行词，并在 `{{paths.changelog}}` 里登记旧名→新名。读者看不懂的词等于没说。
- **禁用「门」系造词**（用户契约；源自"文档里各种门、真看不懂"的用户反馈）：不把「门」当后缀拼新词——门控→检查/校验/把关/检查点（如 代码门控→代码检查、版本区间门控→版本区间判定、质量门控→质量检查）、门槛→阈值、门禁→访问控制（段落语境：评审门禁→评审检查点）、逃生门→逃生通道/应急通道、门面→外观（Facade）/兼容层、守门员→把关人；「X门」拼接词（反例："进展门 / 用户评审门 / 人工门 / 硬门 / 回归门 / 幂等门"）一律改为「X检查 / X检查点 / X校验」，面向用户首次出现时附白话解释。后门（backdoor）、部门、入门是日常通行词，不受本条限制。
  - **`闸门` 不在本条禁令内**：本条禁的是**「修饰语 + 门」的拼接造词**（「进展门」「人工门」「硬门」「回归门」），而 `闸门` 是汉语固有复合名词（sluice gate）。"日常通行词"（后门/部门/入门）同样豁免。
  - 但**`门禁` 在禁令内**（本行映射表已列：`门禁→访问控制`，评审语境作"评审检查点"）。**禁令写了不等于执行了**，故此处点名：`门禁` 与 `门控` 同等对待，出现即判术语违规。
- **禁用日常词生硬隐喻与动词误用**：技术概念必须用软件工程、计算科学、计算软件领域的通行词，不拿日常词做生硬直译隐喻，不滥用非专业词——wave→批次/轮次（"测试波"→"测试批次"）、hygiene→清理/治理（"卫生窗口"→"清理窗口"/"维护窗口"）、flip/翻→置为/更新为（"翻 reviewed"→"状态置为 reviewed"）、首跑→首次运行、活体→真实环境实测（"活体证实"→"实测证实"）、热改→热更新、择时→择期/时间待定、置留→残留、在位→已生效/已配置/已就位、打点→埋点/指标记录、综合窗→综合部署窗口、观测面→观测统计；零X 谓语用直接说法（零空字段→无空字段、零扫描→未触发扫描）。概念没有通行中文对应时，用白话把意思展开说清，或保留英文原词。读者看不懂的词等于没说。
- 代码、文件路径、目录、键名、命令、API 符号、工具名保留英文原样。

## 文档写作通用规则（所有角色的正式文档产出，硬约束）

适用：`docs/` 下的任何正式产出（设计文档、根因分析、测试方案、报告），以及角色回传给编排者的结论。
**契约中的项目专属取值写占位符，不写字面量**：`{{paths.*}}` / `{{tech_stack.*}}` 解析到 `.dsh/profile.yaml` 的对应键。契约只写"如何检查"，项目事实一律由 profile 提供——**换项目时改 profile，不改契约**。

1. **总原则：删噪声，不删设计信息。** 压缩的对象永远是冗余与过程，从来不是结论、判据与理由。
2. **结论四问**：每个结论必须答得出「是什么 / 凭什么（数据、`文件:行号`、命令与输出、官方出处）/ 这份依据**属于哪一档证据**（一手 / 二手 / 未找到一手来源）/ 为什么不选别的（被否决方案 + 一句话理由）」。缺任一问即为不合格。
   **引用外部结论必须标注证据档位**：`[已核验-一手]` / `[已核验-二手]` / `[未核验]`；**二手与未核验的结论不得作为设计决策的唯一依据**。**不标档位，就分不出哪一行是硬的那一行。**
3. **数字三标**：每个数字标注来源、时间、环境。无来源的定量断言不得作为结论陈述。
4. **结论与过程分离**：正文只留结论与判据；探索路径、试错记录、问答回放、工具输出粘贴、QA findings 处置流水一律不进正文（过程留痕写 `.dsh/tmp/<role>/`）。
5. **单一事实源**：同一条信息在文档里只出现一次，别处写"见 §X"。
6. **术语必核来源**：沿用上文「回复语言」的既有禁令——非通行叫法必须在源码标识符、配置键、上游官方文档或人类材料中出现过；只在模型自己写的文档里出现过的拼接词判为自造词，改用通行说法；面向读者首次出现时附一句白话解释。
   - **`Δ判定式` 这个名字不进交付面**：模式仓库的设计文档用「Δ判定式」指称上一条规则里的**净增长 ≤ 0**（`Δ` 取"变化量"义）——**但它是个只在模型自己写的文档里出现过的拼接词**，按本条正属自造词。
   - **处置：机制保留，名字不用。** 交付面一律写**「净增长 ≤ 0」**（描述性表述，读者无需查表即懂）；**不引入「Δ判定式」这个叫法**。

7. **"逐字保真"只管归档，不管正文**：既有的"降级写入必须逐字复制原文、禁止简化/重写/省略/总结"这条规则，**只适用于把外部原文归档到 `.dsh/tmp/` 留证**（用于事后核对原文），**不适用于 `docs/` 下的正式文档正文**。同理，"变更记录（追加式、不重写历史）"这个惯例属于实施记录类文档，**不适用于设计文档**。
8. **原则必须可证伪**：写进契约、方案或设计文档的**设计原则**，必须答得出「**什么样的观测会推翻它**」。答不上来的原则，失败模式必然是"永远通过"或"凭评审者心情"。**不可证伪的原则不得写入契约。**
    > **判据只增不减，正是因为没先问"它怎样才算失败"。**

### 压缩粒度边界（两模式共用正本）

**判据从"读者能否复跑该命令"收紧为"读者能否据此下判断"。** 前者过松——PID、文件大小、端口、时间戳都能"复跑一遍拿到"，但**没有环境访问权的读者据此下不了判断**，等于把判据换成"你自己去查"。

| 可以压缩的 | 必须逐字保留的 |
|---|---|
| 命令的书写形式（长命令折行、路径别名简化） | **命令本身**（复跑要用，含参数与路径） |
| 输出中与结论无关的排版、分隔线、重复表头 | **数值型判据**：端口、文件大小与字节数、计数、时间戳（含 nanos 级）、PID、epoch、百分比、耗时、SHA256 前缀、inode |
| 同一结论在多处重复的表述（留一处） | **判定结论的那几行输出** |
| 探针/实验的探索顺序、试错分支 | **每个探针/实验的采样时刻与环境**（"同一命令在不同环境跑出的数字不是同一个事实"） |
| 章节编号引用（重排后失效，改按标题引用） | **被引用文档/文件的标识与行号**（`文件:行号`）、**可打开的 URL** |

> 一句话：**可以压排版，不能压证据。** 探针输出的"排版"是噪声，探针输出的"数值"是判据。

**核对工具**：`node {{paths.verify_rewrite}} --original <原稿> --rewrite <改后稿>`，只看第 2b 节"真缺失"列（**正则伪影不算缺失**——工具对"真缺失"与"伪影"已内置分类）。

> 两个极端都要治：**既禁无用的多，也禁缺用的少。** 判据是"每句话有没有用"，不是"文档有多长"。

## 引用外部结论与改进提案的准入（**条件性必读**）

**正本见 `_shared/evidence-rules.md`。** 以下两种情形**必须先把该文件读进来**：

- **要引用外部理论 / 研究结论**为设计选择或结论背书 → 读它（含档位标注、外推声明、边界表、逐条禁令）
- **要提出效率或过程改进提案** → 读它（含反馈回路三问、"改进≠加检查"、TOC 约束类型、四种浪费）

**不提案、不引用外部结论的角色不必读**——那两类活动不会在本轮链里发生，读了用不到。

> 「所有角色必读」是一条**覆盖面声明**，它的补集是「对这些角色全是噪声」，不是「对他们也有用」。
> 给某角色加一份必读文件前，先答「**它里面哪一条会改变这个角色本轮的行为？**」——答不出即不加。

## 工程规范（通用基线）
1. **自研代码须经测试**：测试通过后才能报告成功
2. **开源基础上的自研**：遵循分支管理规范
3. **语义分离**：同一变量不同上下文语义不同须明确分离
4. **去硬编码**：参数/环境变量/配置尽可能参数驱动、配置驱动、DB驱动
5. **如实报告（零臆造）**：一切"已完成/已通过/已修复"的声称必须可复现验证（命令可重跑、文件可检查、输出可核对）；禁止虚报状态、伪造命令输出、臆造文件内容——QA 审计发现虚报直接判 FAIL

### 评审把关
- 所有开发内容（新特性/阻塞问题/遗留问题修复方案）都须经用户评审，评审通过后方可动手
- 我提出评审意见，要先评估、调整方案，再提交评审
- 评审通过后，由**实施角色**在评审记录中填写评审人、评审时间、评审结果、评审意见
  （**记录格式、路径、填写人**由各模式的检查契约指定：敏捷模式见 `qa/gate-standard.md`「代码评审归属」节
  与 `developer/coding-standard.md`「代码评审」节；调研模式见 `qa/gate-standard.md`「实施评审归属」节。
  **这里只写"要记"，不写死路径**——写死路径就会在另一种模式下落空。）

## 分支管理（通用）
| 分支类型 | 命名格式 | 用途 | 合并目标 |
|---------|---------|------|---------|
| main/master | `main`/`master` | 生产稳定分支 | 仅用户合并 |
| develop | `develop` | 开发主线 | → main（用户评审） |
| feature | `feature-xxx` | 新需求 | → develop（测试后确认） |
| fix | `fix-xxx` | 问题修复 | → develop（测试后确认） |

规则：
1. **AI 不操作 main/master**，所有提交在 develop 或功能分支
2. 功能/修复分支代码须经调试测试 → 用户确认 → 合入 develop
3. develop → main 由用户负责

> 注：红线为**契约规则**（角色必须遵守，QA 审计将其作为检查项）；工具层兜底由 dsh 原生机制提供——
> sandbox 模式（workspace-write 围栏写权限）+ approval（ask 策略，越权操作自动升级用户审批）。
> 项目级红线事实声明见 `.dsh/profile.yaml` 的 security 段。
> **`security` 段是否生效取决于项目是否声明**：声明了就是**生效的项目事实**，未声明才按"未声明"处理。**不要把某个项目当时的形态写成本契约的固定描述。**

## 开发环境访问（凭证走 credentials 受管，**取值一律不进契约**）

**本契约只规定"怎么取"，不记录"取什么"。** 主机、端口、账号、库名、schema 都是**项目事实**，
写在这里就违反了本模式最基本的一条分工——**共享契约随 `.dsh/` 分发到每一个项目**，
在里面写某一个项目的内网地址，等于把它复制给所有项目。

Access 约定（通用，与模式仓库/本项目无关）：

1. **凭证本体一律不落规则文件**，经 DSH `credentials` 解析引用
   （`~/.dsh/.credentials.yaml` 的 refs；用户决策"全量"）。
   规则文件里只允许出现 `credential:<KEY>` 这样的**引用**，不允许出现明文值。
2. **主机 / 端口 / 账号 / schema 属于项目事实**，登记在**本项目的** `.dsh/profile.yaml`
   （或本项目自己的 skill）里——**不进共享契约**。
3. **需要鉴权的克隆/调用，密码不写在命令行历史里**：用
   `git -c credential.helper= -c "http.extraHeader=Authorization: Basic <base64>"`
   这类一次性注入方式，`<base64>` 由 credentials 运行时解析得到。

> ⚠️ 本契约中若出现任何具体主机名、IP、端口或账号，**那是缺陷，不是示例**——
> 应当移到项目侧的 profile / 项目自己的 skill。判据：**删掉这一行，别的项目会不会受影响？**
> 会 → 它属于共享契约；不会 → 它属于项目。
>
> 同理，**修订说明里也不得复述**被移除的具体取值——在"修正记录"里再写一遍等于换个地方再泄漏一次。
> 说明只写"移除了一类什么取值、为什么"，不写取值本身。

## 评分配方（通用方法论）
| 区间 | 规则 | 示例 |
|------|------|------|
| 正常范围（≤50%） | 不扣分，满分 | usage≤50%→100分 |
| 中等负载（50-80%） | 线性扣分 | 100→60 |
| 危险区间（>80%） | 加速扣分 | 60→0 |

原则：正常范围不扣分，评分公式应在文档中明确写出。
