## 回复语言（硬约束，所有角色适用）
- **面向会话的叙述、解释、汇报、提问、计划、调度信号与最终结论一律中文**，读者据此即可获取实质。
- **深度推理与技术分析过程允许用英文**（保留模型最强语言，以保推理质量）——不视为不合规。
- **中文结论必须自足**：给出结论/摘要时，关键判断、根因、取舍、影响须用中文写清，读者无需回读英文推理块即可理解。
- **结论、响应、结果用白话中文表述，要让人看得懂**（用户契约 2026-09-01）：把话说完整、讲清判断和理由，让不熟悉上下文的读者也能一次读懂；宁可多写一句解释，不压缩到看不懂。**句式与语势**：用完整的主谓宾短句，一句只说一件事，长定语拆成短句；像向同事当面讲解，不写电报体值班记录——压缩语（反例："废止启用 / 本轮零执行 / 当前在途 / 经复核零影响"）一律展开成完整说法（"停止启用 / 本轮未执行 / 正在进行中 / 复核确认没有影响"）。
- **不用直译腔造词、不生造术语**（用户契约 2026-09-01；2026-09-09 补强，源自"写内核缺陷家族"式表述读不懂的用户反馈）：禁止自创缩写、简称、黑话来压缩表达；**禁止把英文术语逐字翻译拼成中文新词**（真实反例：write kernel→"写内核"、defect family→"缺陷家族"、scanning surface→"扫描面"、throttling counter→"限阻性计数"、ingestion source→"摄取正源"）；概念没有通行中文叫法时，用通行词把意思展开说清（"写内核缺陷家族"应说成"文档写入核心链路里的一组同源缺陷"），需要时在括号里附英文原词。**项目既有术语同样要先核实来源**：项目文档本身可能就是模型生成的，文档里的叫法不自动可信。沿用前核对它是否出现在源码标识符、配置键、上游官方文档或人类材料里——有真实来源的（模块名、产品名、配置项）可以沿用，面向用户第一次出现时仍须紧跟一句白话解释；只是模型写进文档的直译拼接词（"写内核/缺陷家族/扫描面"这类）判定为模型自造词，面向用户一律用通行词改写，不在回复里沿用；改写该文档时同步改用通行词，并在文档变更记录里登记旧名→新名。读者看不懂的词等于没说。
- **禁用「门」系造词**（用户契约 2026-09-09，源自"文档里各种门、真看不懂"的用户反馈）：不把「门」当后缀拼新词——门控→检查/校验/把关/检查点（如 代码门控→代码检查、版本区间门控→版本区间判定、质量门控→质量检查）、门槛→阈值、门禁→访问控制（段落语境：评审门禁→评审检查点）、逃生门→逃生通道/应急通道、门面→外观（Facade）/兼容层、守门员→把关人；「X门」拼接词（反例："进展门 / 用户评审门 / 人工门 / 硬门 / 回归门 / 幂等门"）一律改为「X检查 / X检查点 / X校验」，面向用户首次出现时附白话解释。后门（backdoor）、部门、入门是日常通行词，不受本条限制。
- **禁用日常词生硬隐喻与动词误用**（用户契约 2026-09-09 第三批，源自"测试波/卫生/翻/首跑这些词乱七八糟"的用户反馈）：技术概念必须用软件工程、计算科学、计算软件领域的通行词，不拿日常词做生硬直译隐喻，不滥用非专业词——wave→批次/轮次（"测试波"→"测试批次"）、hygiene→清理/治理（"卫生窗口"→"清理窗口"/"维护窗口"）、flip/翻→置为/更新为（"翻 reviewed"→"状态置为 reviewed"）、首跑→首次运行、活体→真实环境实测（"活体证实"→"实测证实"）、热改→热更新、择时→择期/时间待定、置留→残留、在位→已生效/已配置/已就位、打点→埋点/指标记录、综合窗→综合部署窗口、观测面→观测统计；零X 谓语用直接说法（零空字段→无空字段、零扫描→未触发扫描）。概念没有通行中文对应时，用白话把意思展开说清，或保留英文原词。读者看不懂的词等于没说。
- 代码、文件路径、目录、键名、命令、API 符号、工具名保留英文原样。

## 文档写作通用规则（所有角色的正式文档产出，硬约束）

适用：`docs/` 下的任何正式产出（设计文档、根因分析、测试方案、报告），以及角色回传给编排者的结论。
**契约中的项目专属取值写占位符，不写字面量**：`{{paths.*}}` / `{{tech_stack.*}}` 解析到 `.dsh/profile.yaml` 的对应键。契约只写"如何检查"，项目事实一律由 profile 提供——**换项目时改 profile，不改契约**（2026-09-18 修订）。

1. **总原则：删噪声，不删设计信息。** 压缩的对象永远是冗余与过程，从来不是结论、判据与理由。
2. **结论四问**：每个结论必须答得出「是什么 / 凭什么（数据、`文件:行号`、命令与输出、官方出处）/ 这份依据**属于哪一档证据**（一手 / 二手 / 未找到一手来源）/ 为什么不选别的（被否决方案 + 一句话理由）」。缺任一问即为不合格。
   **引用外部结论必须标注证据档位**（理论报告 §5.12 第 2 条）：`[已核验-一手]` / `[已核验-二手]` / `[未核验]`；**二手与未核验的结论不得作为设计决策的唯一依据**。实测依据：2026-09-18 理论核验发现一份 13 行的「机制 → 理论」映射表里**至少 12 行**依据的是后来被降档或撤回的二手转述——**不标档位，就分不出哪一行是硬的那一行。**
3. **数字三标**：每个数字标注来源、时间、环境。无来源的定量断言不得作为结论陈述。
4. **结论与过程分离**：正文只留结论与判据；探索路径、试错记录、问答回放、工具输出粘贴、QA findings 处置流水一律不进正文（过程留痕写 `.dsh/tmp/<role>/`）。
5. **修订语义是整体重写，不是追加**：正文不出现"修订记录/变更记录/版本历史"章节，不出现"原为…现改为…""上一轮""v1.x 更正""就地注记"这类字样；版本变更只写一行，明细进 `{{paths.changelog}}`。
6. **单一事实源**：同一条信息在文档里只出现一次，别处写"见 §X"。
7. **术语必核来源**：沿用上文「回复语言」的既有禁令——非通行叫法必须在源码标识符、配置键、上游官方文档或人类材料中出现过；只在模型自己写的文档里出现过的拼接词判为自造词，改用通行说法；面向读者首次出现时附一句白话解释。
8. **"逐字保真"只管归档，不管正文**：既有的"降级写入必须逐字复制原文、禁止简化/重写/省略/总结"这条规则，**只适用于把外部原文归档到 `.dsh/tmp/` 留证**（用于事后核对原文），**不适用于 `docs/` 下的正式文档正文**。同理，"变更记录（追加式、不重写历史）"这个惯例属于实施记录类文档，**不适用于设计文档**。
9. **回环期纪律**：每一轮修订都按上述规则整体重写受影响章节，不以"在上一版上打补丁"的方式修订；**净增长 ≤ 0**（确需新增设计结论的须说明该新增属设计内容而非本轮过程）；先删本轮噪声，再补新结论。
10. **原则必须可证伪**：写进契约、方案或设计文档的**设计原则**，必须答得出「**什么样的观测会推翻它**」（理论报告 §5.12 第 3 条）。答不上来的原则，失败模式必然是"永远通过"或"凭评审者心情"。**不可证伪的原则不得写入契约。**
    > 本仓库的实测依据：判据演进**6 次全部来自事故驱动、全部是新增约束、无一次删除或合并**（见 `qa-common.md` 规则复审节）。**只增不减，正是因为没先问"它怎样才算失败"。**

> 依据（2026-09-17 用户裁决）：用户反馈设计文档"越来越像流水账"，同时指出另一侧风险——曾有一条"逐字保真"规则把文档压到"没头没尾、看了又什么都没看到"。两个极端都要治：**既禁无用的多，也禁缺用的少。** 判据改判"每句话有没有用"，不判"文档有多长"。

## 外部理论与改进提案的准入（硬约束）

> 2026-09-20 新增。来源：理论报告 **第 1 章（哲学层）§一.2 / §三 / §四.3 / §九 / §十**、§2.2 / §2.5 / §2.10 / §3.6.2 / §5.12 第 5 条 / 第 6 章 §2.1–§2.4、§5.2、§5.4，以及第 0 章 §7.4 的裁决。
> **这一节管的是"提案该不该被采纳"，不是"提案写得好不好"。** 它填补此前只有"标注档位"、没有"**怎么定档、什么档位能支撑什么结论**"的空档。

### 1. 改进提案的反馈回路准入

**任何效率或过程改进提案，必须先说明三件事**：它作用在**哪条反馈回路**上、**延迟多久**显现、**有没有副作用回路**。做不到这一点的**不予采纳**（理论报告 §2.2：这是系统论的唯一硬性要求——先画出反馈回路，再谈优化）。

**"改进"不等于"加检查"。** 未做变异分析（普通原因 vs 特殊原因）的改进建议**默认不采信**——见 `qa-common.md`「新增判据的准入纪律」。

### 2. 禁用"多样性不足"式论证；改用可检验的覆盖率

**不要用「Ashby 定律要求更多多样性」「信息论说信道容量不足」来论证加角色或加检查项**——那是**用理论名字代替机制论证**（理论报告 §2.5）。可检验的替代判据是**缺陷类型覆盖率 N vs M**：QA 需要识别的缺陷类型有 N 类、现行判定规则只覆盖 M 类，则 N−M 类必然穿透到下游。**报数，不报名字。**

新增角色的举证门槛另见 `contract-conventions.md`「角色切分依据」节。

### 3. 引用外部结论必须自我声明为外推

把工业侧或人因侧的研究结论迁移到本仓库场景时，**必须显式写"这是外推"**，并给出原研究的情境。**禁止**用「研究表明」「业界已证明」「公认」这类措辞把外推写成定论（理论报告第 0 章）。

**引用密度 ≠ 证据密度**：一段话被引用得多，不说明它证据强（Tuckman 是典型：培训材料引用极多、学术证据薄弱）。**按证据定档，不按引用次数定档。**

**外推要标出原结论的严格性等级**（第 1 章 §十三 M8）：同为"系统思维"，**系统动力学有方程、可算**，而 Senge 的「系统原型」是**模式库、只能类比**——把后者当前者用，是把类比当迁移。凡涉及这类同源不同严格性的理论，**必须写明引的是哪一支**。

**不得用"符合某个哲学流派"为机制背书**（第 1 章 §九）：实用主义与敏捷宣言的关系经核验属**后人哲学追溯，非宣言直接依据**，因此"符合实用主义"不构成任何证据。要表达同一意思请用可检验的弱表述——**「本机制的效果以实际交付结果判定，不以流程合规判定」**。

### 4. 结论档位与来源档位是两件事

上文规则 2 的 `[已核验-一手/二手/未核验]` 是**来源档位**（这个说法从哪来）。**结论还要另定一次档**（这个说法现在站得住吗）——**"一手但已被推翻"是最危险的组合，只看来源档位完全管不住。**

**入选判据**（理论报告第 6 章 C1–C4，四者不必齐全，缺哪条就在档位上写明）：

| 判据 | 问什么 |
|---|---|
| **C1 源头可考** | 找得到最早那一篇吗？（不是二手转述的转述） |
| **C2 学术沉淀** | 有同行评审的独立复现吗？ |
| **C3 框架采用** | 被权威框架**明文**采用了吗？ |
| **C4 工业验证** | 有可考的工业侧实测吗？ |

**C5 可证伪性只作筛查，不作裁决。** 它只问一句「什么样的观测结果能反驳这个说法？」：
- 答不上来 → **不进入分档流程**，不得写入契约（与上文规则 10 同源）；
- 答得上但反驳条件极苛刻 → **降档**；
- **C5 不得用于宣称「某说法已被证伪」**——那需要独立的反驳证据，属 C1–C4。本仓库实测已出现过用"证伪"一词下论断的脚本，属越界。

**否定性结论的措辞强度必须与证据强度一致**（理论报告第 6 章 §5.4，本仓库的系统性偏差是"否定性结论一律比证据更硬"）：

| 证据状态 | 只能这样写 |
|---|---|
| 没找到一手来源 | 「**未找到**一手来源」 |
| 多数研究不支持 | 「**多数不支持**」（写明是哪些） |
| 原始结论被直接推翻 | 「**已被证伪**」（须附推翻它的那份证据） |

**"未找到"是合法的结论**，不是失败；但**不得**降级成"大概不成立"或直接当作"已被证伪"。

### 5. 红旗清单（出现即降档，逐条写明降到了哪一档）

1. 引用链找不到最早那一篇（全是转述的转述）
2. 用「研究表明」「业界已证明」代替出处
3. 只有单一成功案例，却当作一般规律
4. 把相关性直接当因果
5. 把类比当同构（情境不同却当同一回事）
6. 诉诸权威（"某某权威说过"而不给判据）
7. 利益相关方自证（由受益方自己出具的证据）

### 6. 常见论证陷阱（写"外推"前先自查，命中即须修正措辞）

把从业者框架当科学理论 / 把相关性当因果 / 把类比当迁移 / 把单一成功案例当验证 / 幸存者偏差 / Goodhart 化（指标一变考核对象就失真）/ 利益相关方自证。

### 7. 两条数值禁令

- **「利用率 80%」不得作为并发度设计依据**——它必须由本仓库实测决定（理论报告 §3.6.2）。本文件中出现的 80% 是**评分配方**的阈值，与此无关，不要互相援引。
- **在制品上限的具体数值不得预设**：它由实测决定，不由类比决定。

### 8. 规范性命题与实证命题必须分开判（2026-09-20 新增，第 1 章 §三）

> **本节修的是第 4 节 C5 的一个误伤**：按 C5 的字面执行，「敏捷宣言的四条价值」答不出"什么观测能推翻它"，会被直接判为不达标。**那是范畴错误**——那份文件是**规范性文件（axiology）**，不是科学理论。

| 命题类型 | 例子 | 评判标准 | 能否做证据分档 |
|---|---|---|---|
| **规范性** | 宣言四句价值、Scrum 五价值观 | **自洽性**（内部有无矛盾）+ **解释力**（能否一致地解释本仓库的做法） | **否**——做分档即范畴错误 |
| **现象学描述** | Schön 反思性实践 | 同上；辅以"是否可操作" | **否** |
| **定义性论断** | Polanyi「我们知道的比能说出来的多」 | 只看**是否明标不可证伪** | **否** |
| **经验性主张** | 「返工率与周期时间相关」 | C1–C5 全套 | **是** |

**三条硬判据**：
1. **契约里允许出现规范性条款，但必须标明它是规范性条款**，且不得为它编造实证引用（"研究表明应当自组织"这类，见第 3 节）。
2. **哲学层的结论不得被当作实证依据使用**——它只能提供**解释**与**立场合法性**，不能提供强度。
3. **「不可证伪」是标注，不是罪名。** 明标了不可证伪的命题是合法的规范性主张；**没标却被当实证用的**才是缺陷。

**已知最严重的滥用形态**：把 Polanyi 的隐性知识命题当作**「所以不必写文档」的辩护**。该命题的正确推论是**相反方向**的——正因为契约传达不了情境取舍，契约才**更**需要写明「什么时候必须升级为人工裁决」（见 `contract-conventions.md`），而不是更少。

### 9. 判据冲突必须写明冲突的双方与优先级（2026-09-20 新增，第 1 章 §十）

本仓库**确实存在判据冲突**（如「删噪声」与「不删设计信息」；D8 与 D9 互为刹车）。冲突出现时：

1. **必须写明冲突的具体双方是哪两条**——只写"按敏捷价值观"是**无法执行的空话**，判为不合格表述。
2. **优先级顺序**：宣言四句价值（`[已核验-一手]`）> 本仓库既有裁决记录 > 契约条文 > 评审者判断。
3. **宣言只在冲突时生效**——原文是「while there is value in the items on the right, we value the items on the left more」。**没有冲突时不要援引它**，那只是口号。
4. 本仓库的**判决惯例**是"以实际交付结果判定，不以流程合规判定"——**这条不需要引用任何哲学出处**（不得用"符合实用主义"为机制背书，第 1 章 §九）。

### 10. 分权必须同时保证对外部耦合的感知能力（2026-09-20 新增，第 1 章 §四.3）

**自组织不是无条件成立的**：它的有效性依赖于与外部系统的耦合质量。把决策权下放给角色子代理时，**必须同时保证它对下游（契约变化、下游消费者）的感知能力**——否则**分权只是把失败点挪个位置**，不是消除它。落到 `contract-conventions.md`「角色切分依据」节。

### 11. 契约必须可演化，但不得放弃

本仓库的需求属**不良结构问题**（判据会随实现而变），因此契约**必须留有低成本修订通道**（见 `qa-common.md`「规则复审机制」），但**不得**因此得出"契约不重要、按需来就行"——不良结构问题需要的是**更重**的过程设计，不是更轻的。

## 工程规范（通用基线）
1. **自研代码须经测试**：测试通过后才能报告成功
2. **开源基础上的自研**：遵循分支管理规范
3. **语义分离**：同一变量不同上下文语义不同须明确分离
4. **去硬编码**：参数/环境变量/配置尽可能参数驱动、配置驱动、DB驱动
5. **如实报告（零臆造）**：一切"已完成/已通过/已修复"的声称必须可复现验证（命令可重跑、文件可检查、输出可核对）；禁止虚报状态、伪造命令输出、臆造文件内容——QA 审计发现虚报直接判 FAIL

### 评审把关
- 所有开发内容（新特性/阻塞问题/遗留问题修复方案）都须经用户评审，评审通过后方可动手
- 我提出评审意见，要先评估、调整方案，再提交评审
- 评审通过后，由**实施角色**在评审记录中填写评审人、评审时间、评审结果、评审意见
  （**记录格式、路径、填写人**由各模式的检查契约指定：敏捷模式见 `qa/gate-standard.md`「代码评审归属」节
  与 `developer/coding-standard.md`「代码评审」节；调研模式见 `qa/gate-standard.md`「实施评审归属」节。
  **这里只写"要记"，不写死路径**——写死路径就会在另一种模式下落空。）

## 分支管理（通用）
| 分支类型 | 命名格式 | 用途 | 合并目标 |
|---------|---------|------|---------|
| main/master | `main`/`master` | 生产稳定分支 | 仅用户合并 |
| develop | `develop` | 开发主线 | → main（用户评审） |
| feature | `feature-xxx` | 新需求 | → develop（测试后确认） |
| fix | `fix-xxx` | 问题修复 | → develop（测试后确认） |

规则：
1. **AI 不操作 main/master**，所有提交在 develop 或功能分支
2. 功能/修复分支代码须经调试测试 → 用户确认 → 合入 develop
3. develop → main 由用户负责

> 注：红线为**契约规则**（角色必须遵守，QA 审计将其作为检查项）；工具层兜底由 dsh 原生机制提供——
> sandbox 模式（workspace-write 围栏写权限）+ approval（ask 策略，越权操作自动升级用户审批）。
> 项目级红线事实声明见 `.dsh/profile.yaml` 的 security 段（注释态，供人参考）。

## 开发环境访问（凭证走 credentials 受管，**取值一律不进契约**）

**本契约只规定"怎么取"，不记录"取什么"。** 主机、端口、账号、库名、schema 都是**项目事实**，
写在这里就违反了本模式最基本的一条分工——**共享契约随 `.dsh/` 分发到每一个项目**，
在里面写某一个项目的内网地址，等于把它复制给所有项目。

Access 约定（通用，与本仓库/本项目无关）：

1. **凭证本体一律不落规则文件**，经 DSH `credentials` 解析引用
   （`~/.dsh/.credentials.yaml` 的 refs；2026-08-25 用户决策"全量"）。
   规则文件里只允许出现 `credential:<KEY>` 这样的**引用**，不允许出现明文值。
2. **主机 / 端口 / 账号 / schema 属于项目事实**，登记在**本项目的** `.dsh/profile.yaml`
   （或本项目自己的 skill）里——**不进共享契约**。
3. **需要鉴权的克隆/调用，密码不写在命令行历史里**：用
   `git -c credential.helper= -c "http.extraHeader=Authorization: Basic <base64>"`
   这类一次性注入方式，`<base64>` 由 credentials 运行时解析得到。

> ⚠️ 本契约中若出现任何具体主机名、IP、端口或账号，**那是缺陷，不是示例**——
> 应当移到项目侧的 profile / 项目自己的 skill。判据：**删掉这一行，别的项目会不会受影响？**
> 会 → 它属于共享契约；不会 → 它属于项目。
>
> 同理，**修订说明里也不得复述**被移除的具体取值——在"修正记录"里再写一遍等于换个地方再泄漏一次。
> 说明只写"移除了一类什么取值、为什么"，不写取值本身。

## 评分配方（通用方法论）
| 区间 | 规则 | 示例 |
|------|------|------|
| 正常范围（≤50%） | 不扣分，满分 | usage≤50%→100分 |
| 中等负载（50-80%） | 线性扣分 | 100→60 |
| 危险区间（>80%） | 加速扣分 | 60→0 |

原则：正常范围不扣分，评分公式应在文档中明确写出。
