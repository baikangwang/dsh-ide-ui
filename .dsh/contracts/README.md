# .dsh/contracts/README — 约定式 workspace 契约结构（敏捷模式 agile）

> 这是"零代码新项目接入"的规范说明。任何项目在本 workspace 的 `.dsh/` 下按此约定放置文件，
> 敏捷模式编排人格（预设内建，非外部插件）会话开始时自动读取；派发时把契约清单写进派发提示词、由子代理开工前自读契约（2026-09-09 用户决策），**无需编写任何 host 逻辑**。
> 敏捷模式自身足迹（技术骨架 / 角色契约 / skill + 临时工作区）全部收进 `<cwd>/.dsh/`，不污染真实项目根。

## 目录约定

```
<workspace>/.dsh/
├── profile.yaml                # 声明式技术骨架（项目事实声明）
├── contracts/
│   ├── _shared/                # 全局通用方法论基线（所有角色子代理必读）
│   ├── architect/              # 架构师契约（设计模板/根因/文档规范/契约维护）
│   ├── developer/              # 开发专家契约（编码规范/接口契约/包结构）
│   ├── tester/                 # 测试专家契约（数据驱动/双层断言/报告）
│   ├── deployer/               # 部署专家契约（Makefile/部署验证/脚本复用）
│   └── qa/                     # QA 检查标准（D/C/P 检查项/回环）
├── skills/                     # 项目级 skill（低频大知识）挂载源（官方 skill-filesystem 发现根）
├── tools/                      # 模式能力脚本（随项目分发；用法见 skills，触发见契约）
├── reports/                    # 临时产物（链级闭环随 .dsh/tmp/ 一并**删除**，不保留永久档案）
└── tmp/                        # 临时工作区（一次性轮级产物，闭环**删除**）
    ├── architect/  developer/  tester/  deployer/   # 各角色一次性草稿/探针/中间物
    └── audits/                               # QA 每轮审计（中间轮随轮级闭环清理）
```

## 目录契约：闭环白名单是**两态划分**（2026-09-18 修订，同日由三态改回两态）

> **第一次修订原因**：原白名单只有"清理"与"不清理"两栏，导致三个同源缺陷——能力脚本目录在哪一栏都不在、`.dsh/archive/` 无处声明、根目录出现 13 个 `.dsh-tmp-*` 逃逸件。
> 根因是**目录归属没有单一事实源**。故改为三态，并要求**完整性**。
>
> **第二次修订原因（2026-09-18 用户裁决）**：三态里的第三态 `.dsh/archive/` 被论证为**有害**。
> 它的规则是"闭环只移动不删除"，理由是"本仓库不是 git 仓库"。实测该规则被执行成垃圾堆积，
> **且堆在交付件内部**：`.dsh/archive/` 长到 **1341 文件 / 23.9 MB，占整个 `.dsh/` 的 97%**。
> 交付单位既然是 `.dsh/`，**每个接入的项目都会收到这 23.9 MB**。
> 现删除该态：**闭环直接删除临时产物**，需要留的证据在删除**之前**摘进正式产出。
> 详见 `.dsh/README.md`「两态划分」。

### 交付单位是 `.dsh/` + `.env`（2026-09-18 修订）

**敏捷模式交付给实际项目的东西，只有 `.dsh/` 与 `.env` 两样。** 仓库根的 `docs/` 与 `tools/` **不是交付件**——它们是模式自身的开发工作区。

由此推出两条硬规则：

1. **凡"运行模式所需要的资产"都必须在 `.dsh/` 内**（契约 / skill / 工具三类之一）。落在 `docs/` 或 `tools/` 就等于**其他项目拿不到**，只能跨工作区读取——那是不可能的。
2. **`.dsh/` 必须自包含**：把本仓库的 `.dsh/` 整体拷到目标项目，就应当得到一个可运行的模式。

> **此前违反这两条的实例**：能力脚本正本原先放在仓库根 `tools/`，于是"拷 `.dsh/`"得到的交付件里**没有工具**，只能靠模式仓库的分发器另行推送；`docs/06`（写法指南样例）、`docs/07`（B 类清洗方法）、`docs/08`（A 类重写派发模板）都是运行时要用的资产却躺在 `docs/` 下。**均已迁入 `.dsh/`。**

### 能力脚本位置（2026-09-18 修订）

**正本在 `.dsh/tools/`，随 `.dsh/` 整体交付。**

> **为什么这里不给分发器的文件名**：它是**模式仓库的运维脚本，不随 `.dsh/` 交付**。
> 契约（交付件）里写一个拿不到的文件名，读者会去找它而找不到——那正是本节开头要堵的"悬空引用"。
> **凡是"只在模式仓库存在"的东西，契约里一律只描述职责，不写路径。** 其他项目的 `.dsh/tools/` 是由**模式仓库的分发器**生成的**副本**（带两行副本头）。

| 角色 | 路径 | 内容 |
|---|---|---|
| 本仓库 `.dsh/tools/` | **正本** | 无副本头 |
| 其他项目 `.dsh/tools/` | 副本 | 带副本头（`正本：agent-mode 仓库 .dsh/tools/<名>`） |

分发器 **显式排除正本所在仓库自己的 `.dsh/tools/`**（那是正本，不是副本）。

> **此前三处引用悬空的真正成因**：契约与预设写死 `.dsh/tools/`，而正本当时在 `tools/`，源仓库**没有**该目录；分发器里"排除正本所在仓库"这条例外**未被记录**。**把正本搬进 `.dsh/tools/` 后，此特例自然消失，`paths.tools` 对所有项目取值一致。**

| 态 | 路径 | 闭环动作 |
|---|---|---|
| **正式产出**（长存，参与编排） | `{{paths.source}}`、`{{paths.docs}}`、`.dsh/{profile.yaml, contracts, skills, tools}` | **绝不清理** |
| **临时产物**（删除） | `.dsh/tmp/**`、`.dsh/reports/**` | **链级闭环直接删除** |

**两条硬要求**：

1. **完整性**：`.dsh/` 下的每一个路径必须**恰好落进上述两态之一**。新增目录时同步更新本表——**未声明的目录是缺陷，不是自由**。
2. **先摘录，后删除**：闭环删除临时产物之前，把需要留的证据（运行台账行、审计结论、数值）**写进正式产出**。
   顺序不能反——**先删后摘等于把证据弄丢**。

> **为什么推翻"只移动不删除"**：它把"不可恢复"当成了保留的理由。
> 但临时产物**按定义就是过程证物**——结论已经进了正式产出与运行台账，留着的是**副本**不是证据；
> 而且**没有任何消费者**：没有角色读它、没有契约引用它的内容、没人会去看它。
> "不可恢复"只说明**删除要谨慎**，不说明**必须永久搬运**。

**临时产物一律写入 `.dsh/tmp/<role>/` 或 `.dsh/reports/`**，按目录收敛清理，**禁止硬编码文件名**，**禁止写到仓库根**（仓库根的核心工具如 `tools/` 下的正本脚本，不受影响）。

## 角色切分依据（2026-09-18 补写）

**切分依据 = 产出物所有权互斥 + 活动阶段。**

- **所有权互斥**：两个角色不同时拥有同一类产出物的写权。
- **活动阶段**：设计 / 实现 / 验证 / 交付 / 把关 五个阶段各设一个角色。

**它不是认知负荷切分。** 认知负荷理论用于设计团队边界**未找到对照实验**，属外推，不作为依据。可用口径仅是操作性的：*若一次注入的规则无法在单次判断中全部用完，即属外在负荷，应继续切分*。

**角色数量上限未声明**；当前为 1 个常驻编排者 + 5 个专业角色（架构师 / 开发专家 / 测试专家 / 部署专家 / QA）+ 用户人工卡点。**任何新增角色的提议须先回答：为什么此前被主动削减的角色不该回来。**

## 层内三种形态的分工（骨架 / 契约 / skill）

| 形态 | 载体 | 性质 | 加载方式 | 何时用 |
|------|------|------|---------|--------|
| **骨架** | `.dsh/profile.yaml` | 声明式**数据** | 编排者会话开始读取 tech_stack/deploy 骨架作为项目事实 | 可结构化的技术事实：语言/构建/包结构/端口/部署骨架/安全红线 |
| **契约** | `.dsh/contracts/<role>/*.md` | 结构化**文本** | 派发时把契约清单写进派发提示词，子代理开工前自读（硬性开工指令） | 可叙事、需模型理解的契约：设计模板、编码约束、检查标准、语义约定 |
| **skill** | `.dsh/skills/{project}-*.md` | 项目级 **skill** | 按需 skill() 拉取（官方发现根 `.dsh/skills`） | 大体积低频参考知识：工程规范全文、部署 SOP、测试方法论、**模式能力脚本的用法** |

> **这三种形态都在 C 层（`.dsh/`）内部。** A/B/C 三个字母已专指三层部署架构
> （A 通用引擎 / B 入口预设 / C workspace = `.dsh/` + `.env`），见 `.dsh/README.md`
> 「三层架构，以及 A/B/C 是*哪*三层」一节。层内三样不再用字母，以免与层级混淆（2026-09-20）。

**能力脚本（`{{paths.tools}}`）的三分法**（2026-09-18 确立）：**触发规则 → 契约**；**用法说明 → skill**；**脚本本体 → 留在 `{{paths.tools}}`，不搬进 skill**。搬进 skill 会与分发器形成**第二套副本**，即该脚本自己警告的"副本漂移"事故。

## 按角色 × 按 workspace 加载

- **按项目**：编排者读取 `.dsh/profile.yaml` → 项目骨架/红线事实（tech_stack/deploy/security）。
- **按角色**：编排者调度到某角色时，把该角色 `.dsh/contracts/<role>/` + `_shared` 基线的文件清单写进派发提示词并附硬性开工指令，由 subagent 开工前自读；未调度角色不加载 → 上下文受控、token 不浪费（2026-09-09 用户决策：子代理自读替代编排者读+内联）。

## 回环控制律的唯一事实源

**回环的停止条件只由编排者（preset persona）定义。** 契约只描述"发现什么"，**不描述"何时停"**——契约中不得出现任何重派次数、重试上限或停止条件表述。

> 2026-09-18 修订：此前同一控制律在三处各说各话——QA 契约"回环不设固定次数上限"、编排者"最多重派 2 次"、测试契约"retry≤2"。**调节器需要单一控制律；两套互斥控制律同时存在，等于没有确定策略。**

## 新项目接入步骤（零代码）

1. 在 workspace 的 `.dsh/` 下新建 `profile.yaml`（声明语言/构建/包结构/部署骨架/安全红线）。
2. 可选的：`.dsh/contracts/<role>/` 放该项目特有的角色契约；没有就不建（用通用契约）。
3. 可选的：`.dsh/skills/` 放该项目大知识库（需 frontmatter：`name`/`description`）；没有就不建。
4. 跑**就绪检查**（引用完整性 + 环境 + persona + preset 健康），任一不过即阻断。
5. 完成——会话选择"敏捷模式"即自动生效。无需改引擎、无需写代码。

> **契约中不得出现本仓库专属路径字面量。** 项目相关的取值一律由 `profile.yaml` 提供；**填不上就删掉整句，不留指向空处的路径**——悬空引用正是"填不上却留着"的产物。

> 每个契约文件顶部保留 `来源基线` 注释，指向**模式仓库**的 `baseline/` 备份，保证可追溯与审计。
> **该路径只存在于模式仓库 agent-mode，不是交付件**——注释现已自带这一作用域，
> 免得消费项目去找一个不存在的 `baseline/`。
