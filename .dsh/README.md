# `.dsh/` — 模式容器

**这个目录就是交付单位。** 把 `.dsh/` 和一个 `.env` 拷到任意项目根，那个项目就接入了模式；
不需要别的任何东西，**也不需要读本仓库的 `docs/`、`dev/`、`baseline/`**
（那三个是模式仓库自己的开发工作区，见下「交付件之外还有什么」）。

> **为什么要把这条写在最前面**：在 2026-09-18 之前，模式的价值有一半在交付单元之外——
> 能力脚本正本原先在仓库根 `tools/`、文档写法样例在 `docs/`。于是"拷 `.dsh/`"拿到的交付件
> **既没有工具、也没有样例**。这不是"放错地方"，是**交付不完整**：别的项目要跨工作区读取
> 才拿得到。凡运行所需的资产，现在一律在 `.dsh/` 内。

## 目录

```
.dsh/
  profile.yaml            A 形态：本项目的骨架声明（技术栈 / 路径 / 部署 / 红线）
  contracts/              B 形态：**本项目所用模式的契约**。消费项目里这里是它自己那一套
                          （敏捷 7 份 / 调研 8 份，按 `profile.yaml` 的 `meta.kind` 区分）；
                          模式仓库里这里是**敏捷**契约正本
  contracts-research/     B 形态：**调研**契约正本。**只在模式仓库里有**——交付给调研项目时，
                          它的 8 份内容会落进那个项目的 `contracts/`，本目录不会出现在消费项目里
                          （2026-09-19 澄清：本 README 逐字交付给两种模式，原先只写"两个正本目录"，
                          会让调研项目读到"`contracts/` = 敏捷契约正本"这种与事实相反的说明）
  skills/                 C 形态：模式自带 skill，经 skill() 按需拉取
  tools/                  能力脚本（19 个文件 = 18 支 .mjs + REGISTRY.md 登记册）
  tests/                  交付件自检（3 支：交付自包含、行数口径、门禁三态）——**随 .dsh/ 交付**
  tmp/                    临时产物（**闭环时直接删除**）
  reports/                临时产物（**闭环时直接删除**）
```

**没有 `archive/`。** 见下「两态划分」。

## 交付件之外还有什么（**这些都不随 `.dsh/` 走**）

本仓库根目录另有三个**模式自身的开发工作区**。它们的共同点是：
**换个环境就没有意义**，或者**只在模式仓库里才有对象**——所以**不是交付件**。

| 目录 | 是什么 | 为什么不是交付件 |
|---|---|---|
| `dev/` | **模式仓库的开发脚本（9 支）**，见下表 | 分两类：**探本机环境的**、**操作模式仓库与兄弟项目的**。两类都只在模式仓库有意义 |
| `docs/` | 模式自身的开发记录、评审取证、理论研究 | 消费项目不需要读它；契约若引用 `docs/` 则是缺陷 |
| `baseline/` | 契约的**历史溯源材料** | 只是「这份契约从哪来」的出处，消费项目不需要 |

**`dev/` 里的 9 支，两类各是什么**：

| 类别 | 脚本 | 输入来源 |
|---|---|---|
| **① 模式运维** | `adapt-project.mjs`（交付/体检）、`sync-tools.mjs`（分发正本）、`gen-tool-registry.mjs`（生成登记册）、`project-conformance-check.mjs`（**逐字节核验兄弟项目的交付件是否与正本一致**）、`profile-template-check.mjs`（**核验 profile 模板覆盖了契约引用的全部键**） | **模式仓库本身 + 兄弟项目**。以 `adapt-project` 为例：`SRC = <模式仓库>/.dsh`，目标 = 别的项目——**在消费项目里跑它，源和目标会指向同一处**，那是没有意义的自拷贝 |
| **② 本机环境探针** | `preset-health-check-a1.mjs`、`persona-schema-check.mjs`、`workspace-env-check.mjs`、`_dsh-install.mjs` | **本机 harness 预设（`$USERPROFILE/.dsh/.agent-presets`）、npx 缓存、兄弟目录**。换个环境即失效 |

> **为什么要在 README 里显式列出**：**"不是交付件"必须被写下来**，否则下一个人看到 `.dsh/tests/`
> 里少了预设检查、`.dsh/tools/` 里少了交付工具，会以为是漏拷；看到仓库根有 `dev/`，
> 会以为是残留垃圾——**然后把它"清理"掉**。
>
> - **第七轮**：本机环境探针 4 支曾放在 `.dsh/tests/`，会随交付件拷进每个消费项目。
> - **第八轮**：模式运维 3 支曾放在 `.dsh/tools/`，同样会随交付件走——**而这 3 支在被交付的
>   那一刻就已经失去意义**（它们的源和目标都是模式仓库）。
>
> 判据见 `docs/CHANGELOG-调研报告.md` 第七、八轮。

> **一条容易忽略的连带后果**：分发器 `dev/sync-tools.mjs` 会**清理"正本已删、副本还在"的孤儿**。
> 所以把 3 支移出 `.dsh/tools/` 之后，**消费项目里那 3 支的副本会被自动清掉**——
> 这不是副作用，正是想要的结果：它们本来就不该在那里。

## 两套契约，一个目标布局

| 模式 | 正本（本仓库） | 交付到目标的位置 |
|---|---|---|
| 敏捷 | `.dsh/contracts/` | `<目标>/.dsh/contracts/` |
| 调研 | `.dsh/contracts-research/` | `<目标>/.dsh/contracts/` |

**目标项目一侧永远是扁平的 `.dsh/contracts/<role>/`。** 模式区分只存在于本仓库，
所以**两个 preset 的角色路径都不需要感知模式**——只有交付工具需要。

> **为什么不能像以前那样**：调研契约原先住在 `D:\working\projects\dsh\.dsh\contracts\`，
> 而 `dsh` 是一个**被调研的对象项目**，不是模式的家。后果是部署调研模式只能从 `dsh`
> **整目录拷**——`zsvirt` 正是这样做的，于是**带上了 dsh 的项目级 skill、又漏掉了 `.dsh/tools/`**。
> 契约现在有家了，这条路被切断。

## 怎么接入一个项目

**这三条命令在模式仓库根执行**（`adapt-project.mjs` 是模式运维脚本，在 `dev/`，**不随 `.dsh/` 交付**）：

```bash
node dev/adapt-project.mjs plan   <目标项目根> [--mode agile|research]   # 只报告，不写盘
node dev/adapt-project.mjs init   <目标项目根> [--mode agile|research]   # 实际交付
node dev/adapt-project.mjs doctor <目标项目根>                            # 体检
```

> **为什么交付工具自己不随交付件走**：它的输入是**模式仓库**（`SRC = <模式仓库>/.dsh`），
> 输出是**别的项目**。在消费项目里跑它，源和目标会指向同一处——那是没有意义的自拷贝。
> **"谁来交付"和"交付了什么"是两件事**，前者属于模式仓库。

- 交付的只有 `.dsh/{contracts,skills,tools}` + 生成的 `profile.yaml` + `.env` 脚手架。
- **`profile.yaml` 必须按目标项目真实技术栈填**（模板里写「待填」），否则契约的占位符
  会解析到占位文本、检查项会打在不存在的目录上。
- **同名但内容不同 = 冲突，不是"已存在"**：`init` 会因此中止。目标项目可能装的是
  另一个模式的契约——改 `--mode`，或用 `--only skills,tools` 只交付共享部分。

## 两态划分（每个路径恰好属于一态）

| 态 | 路径 | 闭环时 |
|---|---|---|
| 正式产出 | `docs/`、`.dsh/{profile.yaml,contracts,contracts-research,skills,tools}` | 绝不清理 |
| 临时产物 | `.dsh/tmp/`、`.dsh/reports/` | **直接删除** |

**为什么从"三态"改回"两态"，以及为什么反过来删掉归档（2026-09-18 用户裁决）**：

原三态里的第三态是 `.dsh/archive/`，规则是"**闭环只移动不删除**"——理由是"本工作区与
调研项目 `dsh` 都不是 git 仓库，删除不可恢复"。

**这条规则被执行成了垃圾堆积，而且堆在交付件内部。** 实测：`.dsh/archive/` 长到
**1341 文件 / 23.9 MB，占整个 `.dsh/` 交付件的 97%**——其中 1252 件是历次闭环搬进来的旧
`.dsh/tmp/` 内容，另有 66 支过期脚本、旧 docs 副本、根目录逃逸产物。
**后果是具体的：交付单位既然是 `.dsh/`，每个接入的项目都会收到这 23.9 MB。**

原理由的毛病在于**把"不可恢复"当成了保留的理由**：
- 临时产物**按定义就是过程证物**，它的结论已经进了正式产出与运行台账，留着不是"证据"而是**副本**；
- "不可恢复"只说明**删除要谨慎**，不说明**必须永久搬运**——这两件事被混为一谈了；
- 归档没有任何消费者：没有角色读它、没有契约引用它的内容、没人会去看。

**现规则**：闭环时 `.dsh/tmp/` 与 `.dsh/reports/` **直接删除**（`rm -rf`）。
需要留的证据在删除**之前**摘进正式产出（运行台账、审计结论）——**先摘录，再删除**。

> **一条仍然有效的边界**：文档清洗用的回滚副本 `.dsh/tmp/cleanup/archive/` 也在 `.dsh/tmp/` 下，
> 因此**随闭环一并删除**。这是对的——回滚窗口是**清洗期间**，链闭环后 `docs/` 已定稿。
> 但正因为如此，**清洗链在闭环前不要仓促收口**。
